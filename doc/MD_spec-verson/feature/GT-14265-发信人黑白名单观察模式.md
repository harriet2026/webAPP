# GT-14265 发信人黑白名单观察模式

## 1. 需求背景

发信人黑白名单模块的规则一旦启用即会立即对命中邮件执行拦截、隔离或放行动作。用户在新建规则或调整已有规则的匹配范围时，缺少一种"先观察命中情况、再正式生效"的过渡手段，容易因规则配置不准确而误伤正常邮件或漏拦风险邮件。

本需求在发信人黑白名单模块新增"观察模式"能力：规则开启观察模式后仅记录命中日志，不实际执行规则动作，帮助用户在正式启用前验证规则的影响范围。

本次为纯前端交付，使用 mock 数据模拟观察模式的开启/关闭状态，暂不涉及后端接口改造。

## 2. 需求目标

- 在"新建/编辑"抽屉的"基础设置"区域，增加观察模式的启用/禁用开关。
- 在规则列表增加"观察模式"表头字段，并支持直接在列表中启用/禁用。
- 观察模式状态与规则的启用/禁用状态（`is_active`）互相独立，两者可分别控制。
- 复用项目现有国际化框架和 `Switch` 组件形态，不引入新的交互范式。
- 不修改发信人黑白名单之外的其他功能模块。

## 3. 最终实现方案

### 3.1 数据模型

- `SenderFilterRuleView` 增加只读字段 `observe_mode: boolean`，随行数据一起下发给列表和抽屉。
- `SenderFilterFormData` 增加可选字段 `observe_mode?: boolean`，供抽屉表单读写。
- 由于后端暂无承载该状态的字段，`observe_mode` 的值由 `SenderFilterPage` 维护的本地 mock 态注入到每一行，不进入规则的真实 CRUD 请求体，不随规则的创建、编辑、删除请求持久化到后端。

### 3.2 新建/编辑抽屉——基础设置（操作级说明）

- **打开抽屉**：用户在规则列表点击"新建规则"或某一行的"编辑"操作，抽屉展开，"基础设置"区域渲染在最上方。
- **字段位置与结构**：在"基础设置"区域、启用状态（`is_active`）字段的下方新增一行"观察模式"字段，结构为：字段标签 + 帮助图标（Tooltip 触发器）+ 右侧 `Switch` 组件 + Switch 右侧的状态文案。
- **默认值填充（新建场景）**：
  1. 用户点击"新建规则"。
  2. 表单以空白态初始化，`observe_mode` 字段默认值为 `false`（关闭）。
  3. 观察模式 Switch 渲染为"关闭"态，右侧状态文案显示"禁用"。
- **回填（编辑场景）**：
  1. 用户点击某一行的"编辑"。
  2. 表单读取该行 `SenderFilterRuleView.observe_mode` 的当前值。
  3. 观察模式 Switch 按该值渲染为开启或关闭态，右侧状态文案同步显示"启用"或"禁用"。
- **交互——切换开关**：
  1. 用户点击观察模式 Switch。
  2. Switch 视觉状态立即切换（开启 ↔ 关闭），右侧状态文案同步切换为"启用"/"禁用"。
  3. 表单内部字段 `observe_mode` 的值随之更新，但不触发提交，也不影响表单内其他字段（匹配范围、动作类型、启用状态等）的值。
- **交互——查看帮助说明**：
  1. 用户将鼠标悬停（或聚焦）在字段标签旁的帮助图标。
  2. 弹出 Tooltip，文案为"启用后规则仅记录命中情况，不实际执行动作，用于验证规则效果"。
  3. 鼠标移出或失焦后 Tooltip 自动关闭。
- **交互——保存**：
  1. 用户点击抽屉底部的"保存"按钮。
  2. 表单当前的 `observe_mode` 值随表单其余字段一起提交给页面级状态更新逻辑（本次为纯前端 mock，不发起真实网络请求持久化该字段）。
  3. 抽屉关闭，规则列表对应行（新建则新增一行）按最新的 `observe_mode` 值重新渲染观察模式列。

### 3.3 规则列表——观察模式列（操作级说明）

- **列位置**：在规则列表表头新增"观察模式"列，紧邻现有的"启用状态"列右侧（或左侧，视现有列顺序而定），列宽与其他状态类列保持一致。
- **单元格渲染**：
  1. 页面渲染规则列表时，每一行按 `row.original.observe_mode` 的值渲染观察模式列的 `Switch` 组件：`true` 渲染为开启态，`false` 渲染为关闭态。
  2. Switch 旁不额外展示文案（列表场景仅用开关的开/关视觉状态表达，抽屉场景才展示文案），Switch 的 `aria-label` 使用国际化的"启用观察模式"/"禁用观察模式"文案，保证屏幕阅读器可读。
- **交互——列表内直接切换**：
  1. 用户点击某一行观察模式列的 Switch。
  2. Switch 视觉状态立即切换（开启 ↔ 关闭）。
  3. 该操作调用页面级 `onToggleObserve(id, observeMode)` 回调，仅更新对应规则行本地 mock 状态中的 `observe_mode` 字段，同一行的其余字段（匹配范围、动作类型、`is_active`、命中统计等）保持不变，不重新拉取整张列表。
  4. 操作不需要二次确认，不弹出额外的保存/取消对话框（即时生效于本地 mock 状态）。
- **与其他列的独立性**：切换"观察模式"列不影响"启用状态"列（`is_active`）的显示与取值，两者在同一行内并存、互不联动；反之，切换"启用状态"也不会重置该行的观察模式取值。

### 3.4 国际化

- 在 `senderFilter` 命名空间新增 `observeMode`（"观察模式"）和 `observeModeHelp`（帮助文案）两个键。
- 中文资源使用 UTF-8 编码，不引入 Unicode replacement character 或异常全角问号字符。
- 同步在英文、俄文、泰文资源文件补齐对应翻译，保持四语言 key 集合一致。

### 3.5 Mock 数据与测试

- Mock 数据层为规则行附加初始 `observe_mode` 值，覆盖开启和关闭两种状态，便于前端联调和视觉验证。
- 补充/更新单元测试，覆盖抽屉表单默认值、编辑回填、列表 Switch 渲染与切换回调三个关键路径。

## 7. 关联功能模块变更

发信人黑白名单新增规则/观察模式能力后，为保证该模块在统计与运营侧的可观测性，同步在以下关联模块落地了配套实现：

### 7.1 规则效能统计——发信人黑白名单规则效能 mock 数据

- **需求背景**：发信人黑白名单规则上线（含观察模式）后，需要在"规则效能统计"模块中看到该模块下每条规则的独立效能表现，并能体现策略版本管理（规则修改后版本号递增、可追溯历史版本的效能对比），而非仅有模块级汇总。
- **实现内容**：
  - 在 `src/lib/mock/fixtures.ts` 的 `MOCK_RULE_EFFECTIVENESS_ROWS` 中，按发信人黑白名单现有的 5 条规则逐条补充效能统计行（命中量、拦截/放行动作分布、观察时长等指标），供正常网络 mock 分发路径（`dispatcher.ts`）使用。
  - 在 `src/lib/mock/rule-effectiveness-prototype.ts` 中补充同一模块的 `policy_module` 类型定义与对应 mock 行，供"Mock 模式"本地开关（`osgateway_mock_enabled`）路径使用；该文件此前未包含 `sender_filter` 模块，是"效能明细看不到发信人黑白名单数据"问题的根因，本次已补齐两条数据源，两者保持一致口径。
  - 其中至少 2 条规则（钓鱼域名、内部财务组相关规则）设置 `version: 2` 并生成对应的历史版本快照（`MOCK_OBSERVATION_HISTORY` / `mockObservationVersions`），体现规则修改后版本递增、历史版本效能可追溯的策略版本管理能力。
  - `src/components/statistics/rule-effectiveness/constants.ts` 中确认并复用已有的 `sender_filter` 模块筛选项与配色，未新增筛选维度。
- **验收要点**：
  - 规则效能统计——效能明细表格中，无论"Mock 模式"开关处于何种状态，均可看到发信人黑白名单模块的 5 条规则效能数据。
  - 展开效能明细中的版本历史行，可看到发信人黑白名单规则的历史版本记录及对应效能对比。
- **涉及文件**：`src/lib/mock/fixtures.ts`、`src/lib/mock/rule-effectiveness-prototype.ts`、`src/lib/mock/rule-effectiveness-mock.test.ts`。

### 7.2 规则效能统计——效能明细分页

- **需求背景**：效能明细表此前一次性渲染全部规则行（含新增的发信人黑白名单数据后行数进一步增多），缺少分页，长列表浏览体验和性能均不理想。
- **实现方案**：复用"邮件处置中心"（`email-disposal/center`）已有的分页组件与交互范式 `src/components/shared/server-pagination.tsx`（`ServerPagination`），不新建分页 UI 组件：
  - 在 `RuleEffectivenessPage.tsx` 增加 `page`/`pageSize` 本地状态（默认每页 20 条，支持切换每页条数），对筛选后的 `rows` 做前端切片得到当前页数据。
  - 时间范围、模块筛选、观察时长筛选变化导致数据集变化时，自动重置回第 1 页，避免停留在空页。
  - 在 `DetailTable.tsx` 表格下方渲染 `ServerPagination`（`data-testid="rule-effectiveness-detail-pagination"`），展示"共 N 条 / 每页条数 / 第 x / y 页"及首页、上一页、下一页、末页操作，与处置中心视觉和交互保持一致。
- **说明**：本次仅在"规则效能统计"侧复用了处置中心的分页组件与范式，**未修改邮件处置中心自身的任何代码、数据或交互逻辑**。
- **涉及文件**：`src/components/statistics/rule-effectiveness/RuleEffectivenessPage.tsx`、`src/components/statistics/rule-effectiveness/DetailTable.tsx`。

### 7.3 邮件处置中心——与观察模式的现有关联关系（操作级说明）

邮件处置中心（`email-disposal/center`）本身**未新增任何代码改动**；本节记录该模块与发信人黑白名单观察模式之间已经存在的关联行为，作为本需求落地后的行为基线说明，便于后续验收与排期参考。

- **关联点一：处置中心"一键加黑/加白"生成的规则默认不进入观察模式**
  1. 用户在处置中心的邮件详情页（`entity-detection.tsx` 所在的实体检测 Tab），针对邮件的发信人执行"加入黑名单"或"加入白名单"操作。
  2. 系统调用 `disposal-detail-api.ts` 中的 `addSenderFilterRule(sender, kind, requestFn, priority, opts)`，向后端提交一条 `page: 'sender_filter'`、`rule_class: 'action'`、`is_active: true` 的统一规则；该请求体不包含 `observe_mode` 字段。
  3. 因此，从处置中心一键生成的发信人黑白名单规则，在前端 mock 视图层落地后 `observe_mode` 呈**关闭（禁用）**态——与用户"直接加黑/加白、立即生效"的操作意图一致，不会被观察模式拦下。
  4. 用户后续如需对该新规则做"先观察、再生效"的验证，需要跳转到发信人黑白名单模块的规则列表或编辑抽屉，手动打开该规则的"观察模式"开关（见 3.2、3.3 节的操作步骤），处置中心本身不提供直接开启观察模式的入口。
- **关联点二：规则效能统计跳转回处置中心时的上下文提示条已兼容 `sender_filter` 模块**
  1. 用户在"规则效能统计"页面点击发信人黑白名单某条规则的效能明细行、并跳转到该规则命中的邮件处置详情。
  2. 跳转链接携带 `source=rule_effectiveness`、`policy_key=sender_filter`、`sub_strategy`、`strategy_name`、`observe_window_from`/`observe_window_to` 等查询参数。
  3. 处置中心详情页顶部渲染 `RuleEffectivenessContextBanner`（`data-testid="disposal-rule-effectiveness-context-banner"`），对 `policy_key === 'sender_filter'` 的情况，直接取 `strategy_name` 查询参数作为路径文本展示（不走多级策略路径拼接），并展示 `observe_window_from`~`observe_window_to` 的观察起始时间区间。
  4. 用户点击提示条右侧的"返回"按钮，若浏览历史可回退则调用 `router.back()` 返回规则效能统计页面，否则直接跳转到 `/statistics/rule-effectiveness`。
  5. 该组件对"是否开启观察模式"的规则均适用同一套展示逻辑——即无论规则当前 `observe_mode` 为开启或关闭，只要携带上述查询参数跳转到处置中心，均会展示一致的来源上下文提示，本次未对该组件做任何修改。
- **未变更声明**：`src/components/email-disposal/lib/disposal-detail-api.ts`、`src/components/email-disposal/sections/overview/entity-detection.tsx`、`src/components/email-disposal/rule-effectiveness-context-banner.tsx`、`src/components/email-disposal/hooks/use-detection-stages.ts` 等处置中心相关文件本次均未修改代码，本节内容仅为对既有行为的梳理说明。
