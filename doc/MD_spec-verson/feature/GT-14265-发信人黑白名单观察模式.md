# GT-14265 发信人黑白名单观察模式

## 1. 需求背景

发信人黑白名单模块的规则一旦启用即会立即对命中邮件执行拦截、隔离或放行动作。用户在新建规则或调整已有规则的匹配范围时，缺少一种"先观察命中情况、再正式生效"的过渡手段，容易因规则配置不准确而误伤正常邮件或漏拦风险邮件。

本需求在发信人黑白名单模块新增"观察模式"能力：规则开启观察模式后仅记录命中日志，不实际执行规则动作，帮助用户在正式启用前验证规则的影响范围。

本次为纯前端交付，使用 mock 数据模拟观察模式的开启/关闭状态，暂不涉及后端接口改造。

## 2. 需求目标

- 在"新建/编辑"抽屉的"基础设置"区域，增加观察模式的启用/禁用开关。
- 在规则列表增加"观察模式"表头字段，并支持直接在列表中启用/禁用。
- 观察模式状态与规则的启用/禁用状态（`is_active`）互相独立，两者可分别控制。
- 复用项目现有国际化框架和 `Switch` 组件形态，不引入新的交互范式。
- 不修改发信人黑白名单之外的其他功能模块。

## 3. 最终实现方案

### 3.1 数据模型

- `SenderFilterRuleView` 增加只读字段 `observe_mode: boolean`，随行数据一起下发给列表和抽屉。
- `SenderFilterFormData` 增加可选字段 `observe_mode?: boolean`，供抽屉表单读写。
- 由于后端暂无承载该状态的字段，`observe_mode` 的值由 `SenderFilterPage` 维护的本地 mock 态注入到每一行，不进入规则的真实 CRUD 请求体，不随规则的创建、编辑、删除请求持久化到后端。

### 3.2 新建/编辑抽屉——基础设置

- 在"基础设置"区域、启用状态字段附近增加"观察模式"字段：
  - 使用项目现有 `Switch` 组件，`checked` 绑定表单字段 `observe_mode`。
  - 字段标签旁附带帮助图标和 Tooltip，说明"启用后规则仅记录命中情况，不实际执行动作，用于验证规则效果"。
  - Switch 右侧展示当前状态文案（启用/禁用），文案随开关状态实时切换。
  - 新建规则默认 `observe_mode` 为关闭（`false`）；编辑已有规则时，表单从该行的 `observe_mode` 回填。

### 3.3 规则列表——观察模式列

- 在规则列表表头增加"观察模式"列，位于现有状态列附近。
- 单元格使用 `Switch` 组件直接展示和切换该行的观察模式状态，`checked` 绑定 `row.original.observe_mode`。
- 切换操作调用页面级 `onToggleObserve(id, observeMode)` 回调，更新对应规则行的本地 mock 状态，不影响该行其余字段。
- Switch 的 `aria-label` 使用国际化的启用/禁用文案，保证可访问性。

### 3.4 国际化

- 在 `senderFilter` 命名空间新增 `observeMode`（"观察模式"）和 `observeModeHelp`（帮助文案）两个键。
- 中文资源使用 UTF-8 编码，不引入 Unicode replacement character 或异常全角问号字符。
- 同步在英文、俄文、泰文资源文件补齐对应翻译，保持四语言 key 集合一致。

### 3.5 Mock 数据与测试

- Mock 数据层为规则行附加初始 `observe_mode` 值，覆盖开启和关闭两种状态，便于前端联调和视觉验证。
- 补充/更新单元测试，覆盖抽屉表单默认值、编辑回填、列表 Switch 渲染与切换回调三个关键路径。

## 6. 变更范围

本需求仅覆盖发信人黑白名单模块新建/编辑抽屉的基础设置区域、规则列表表头与交互、相关数据类型、mock 数据以及对应国际化文案。不改变发信人黑白名单以外的其他安全策略模块，不改变现有规则的创建、编辑、删除、筛选、分页、导入导出等业务逻辑，不涉及后端接口改造。

## 7. 关联功能模块变更

发信人黑白名单新增规则/观察模式能力后，为保证该模块在统计与运营侧的可观测性，同步在以下关联模块落地了配套实现：

### 7.1 规则效能统计——发信人黑白名单规则效能 mock 数据

- **需求背景**：发信人黑白名单规则上线（含观察模式）后，需要在"规则效能统计"模块中看到该模块下每条规则的独立效能表现，并能体现策略版本管理（规则修改后版本号递增、可追溯历史版本的效能对比），而非仅有模块级汇总。
- **实现内容**：
  - 在 `src/lib/mock/fixtures.ts` 的 `MOCK_RULE_EFFECTIVENESS_ROWS` 中，按发信人黑白名单现有的 5 条规则逐条补充效能统计行（命中量、拦截/放行动作分布、观察时长等指标），供正常网络 mock 分发路径（`dispatcher.ts`）使用。
  - 在 `src/lib/mock/rule-effectiveness-prototype.ts` 中补充同一模块的 `policy_module` 类型定义与对应 mock 行，供"Mock 模式"本地开关（`osgateway_mock_enabled`）路径使用；该文件此前未包含 `sender_filter` 模块，是"效能明细看不到发信人黑白名单数据"问题的根因，本次已补齐两条数据源，两者保持一致口径。
  - 其中至少 2 条规则（钓鱼域名、内部财务组相关规则）设置 `version: 2` 并生成对应的历史版本快照（`MOCK_OBSERVATION_HISTORY` / `mockObservationVersions`），体现规则修改后版本递增、历史版本效能可追溯的策略版本管理能力。
  - `src/components/statistics/rule-effectiveness/constants.ts` 中确认并复用已有的 `sender_filter` 模块筛选项与配色，未新增筛选维度。
- **验收要点**：
  - 规则效能统计——效能明细表格中，无论"Mock 模式"开关处于何种状态，均可看到发信人黑白名单模块的 5 条规则效能数据。
  - 展开效能明细中的版本历史行，可看到发信人黑白名单规则的历史版本记录及对应效能对比。
- **涉及文件**：`src/lib/mock/fixtures.ts`、`src/lib/mock/rule-effectiveness-prototype.ts`、`src/lib/mock/rule-effectiveness-mock.test.ts`。

### 7.2 规则效能统计——效能明细分页

- **需求背景**：效能明细表此前一次性渲染全部规则行（含新增的发信人黑白名单数据后行数进一步增多），缺少分页，长列表浏览体验和性能均不理想。
- **实现方案**：复用"邮件处置中心"（`email-disposal/center`）已有的分页组件与交互范式 `src/components/shared/server-pagination.tsx`（`ServerPagination`），不新建分页 UI 组件：
  - 在 `RuleEffectivenessPage.tsx` 增加 `page`/`pageSize` 本地状态（默认每页 20 条，支持切换每页条数），对筛选后的 `rows` 做前端切片得到当前页数据。
  - 时间范围、模块筛选、观察时长筛选变化导致数据集变化时，自动重置回第 1 页，避免停留在空页。
  - 在 `DetailTable.tsx` 表格下方渲染 `ServerPagination`（`data-testid="rule-effectiveness-detail-pagination"`），展示"共 N 条 / 每页条数 / 第 x / y 页"及首页、上一页、下一页、末页操作，与处置中心视觉和交互保持一致。
- **说明**：本次仅在"规则效能统计"侧复用了处置中心的分页组件与范式，**未修改邮件处置中心自身的任何代码、数据或交互逻辑**。
- **涉及文件**：`src/components/statistics/rule-effectiveness/RuleEffectivenessPage.tsx`、`src/components/statistics/rule-effectiveness/DetailTable.tsx`。
