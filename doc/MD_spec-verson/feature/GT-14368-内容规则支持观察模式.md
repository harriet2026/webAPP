# GT-14368 内容规则支持观察模式

## 1. 需求背景

内容规则模块的规则一旦启用即会立即按方向（收信/发信）执行审核、隔离、丢弃或拒收等动作。用户在新建规则或调整已有规则的关键字、正则、附件类型等匹配条件时，缺少一种"先观察命中情况、再正式生效"的过渡手段，容易因匹配条件设置不合理而误伤正常邮件或漏拦异常邮件。

本需求在内容规则模块新增"观察模式"能力：规则开启观察模式后仅记录命中日志，不实际执行规则动作，帮助用户在正式启用前验证规则的影响范围。该能力与"发信人黑白名单"（GT-14265）、"发信行为管控"（GT-14367）已落地的观察模式保持一致的交互范式和数据口径。

本次为纯前端交付，使用 mock 数据模拟观察模式的开启/关闭状态，暂不涉及后端接口改造。

## 2. 需求目标

- 在"新建/编辑"抽屉的基础设置区域，增加观察模式的启用/禁用开关。
- 在规则列表增加"观察模式"表头字段，并支持直接在列表中启用/禁用。
- 观察模式状态与规则的启用/禁用状态（`is_active`）互相独立，两者可分别控制。
- 复用项目现有国际化框架和 `Switch` 组件形态，不引入新的交互范式。
- 不修改内容规则之外的其他功能模块（不含第 7 章记录的关联模块配套变更）。

## 3. 最终实现方案

### 3.1 数据模型

- `ContentRule` 类型（`src/types/content-rules.ts`）的规则实体上定义必填字段 `observe_mode: boolean`，表单态类型 `ContentRuleFormData` 上定义可选字段 `observe_mode?: boolean`，供抽屉表单读写。
- 由于后端暂无承载该状态的字段，`observe_mode` 的值由 `ContentRulesPage` 维护的本地 mock 态（`observeModeById: Record<number, boolean>`，以规则 `id` 为键）注入到每一行，不进入规则的真实 CRUD 请求体，不随规则的创建、编辑、删除请求持久化到后端。

### 3.2 新建/编辑抽屉——基础设置（操作级说明）

- **打开抽屉**：用户在规则列表点击"新建规则"或某一行的"编辑"操作，抽屉展开，基础设置区域渲染在最上方。
- **字段位置与结构**：在基础设置区域、"生效截止日期"（`effective_until`）字段的下方新增一行"观察模式"字段（`ContentRuleDrawer.tsx`），结构为：字段标签 `contentRules.observeMode` + 提示文案 `contentRules.observeModeHint` + 右侧 `Switch` 组件 + Switch 右侧的状态文案（复用现有的 `common.enabled`/`common.disabled` 文案键）。
- **默认值填充（新建场景）**：
  1. 用户点击"新建规则"。
  2. 表单以空白态初始化（`ContentRuleDrawer.tsx` 中新建默认草稿），`observe_mode` 字段默认值为 `false`（关闭）。
  3. 观察模式 Switch 渲染为"关闭"态，右侧状态文案显示"禁用"。
- **回填（编辑场景）**：
  1. 用户点击某一行的"编辑"，或通过效能明细/处置中心携带的 `rule_id` 深链自动定位到该规则的编辑抽屉。
  2. `ContentRulesPage` 从本地 `observeModeById` 状态中按 `rule.id` 取出当前观察模式值（未记录过则默认 `false`），拼装进 `editingRule.observe_mode` 传给抽屉。
  3. 观察模式 Switch 按该值渲染为开启或关闭态，右侧状态文案同步显示"启用"或"禁用"。
- **交互——切换开关**：
  1. 用户点击观察模式 Switch。
  2. Switch 视觉状态立即切换（开启 ↔ 关闭），右侧状态文案同步切换为"启用"/"禁用"。
  3. 表单内部字段 `draft.observe_mode` 的值随之更新，但不触发提交，也不影响表单内其他字段（关键字、正则、附件类型、方向、动作类型、优先级、生效截止日期、启用状态等）的值。
- **交互——保存**：
  1. 用户点击抽屉底部的"保存"按钮。
  2. 表单当前的 `observe_mode` 值随保存数据 `data.observe_mode` 一并提交给 `ContentRulesPage`；页面据此更新本地 `observeModeById[savedId]`（新建规则则写入新分配的 `id`），本次为纯前端 mock，不发起真实网络请求持久化该字段。
  3. 抽屉关闭，规则列表对应行（新建则新增一行）按最新的 `observe_mode` 值重新渲染观察模式列。

### 3.3 规则列表——观察模式列（操作级说明）

- **列位置**：在规则列表表头新增"观察模式"列（`ContentRulesTable.tsx` 中列 id 为 `observe_mode`，表头文案 `contentRules.observeMode`）。
- **单元格渲染**：
  1. 页面渲染规则列表时，每一行按注入到行数据上的 `row.original.observe_mode` 值渲染观察模式列的 `Switch` 组件：`true` 渲染为开启态，`false` 渲染为关闭态。
  2. Switch 的 `aria-label` 使用国际化的"观察模式"文案（`contentRules.observeMode`），保证屏幕阅读器可读。
- **交互——列表内直接切换**：
  1. 用户点击某一行观察模式列的 Switch。
  2. `onToggleObserve(row.original.rule.id, enabled)` 回调触发，`ContentRulesPage.handleToggleObserve` 更新本地 `observeModeById` 状态中对应 `id` 的值，Switch 视觉状态立即切换（开启 ↔ 关闭）。
  3. 该操作仅更新对应规则行本地 mock 状态中的 `observe_mode` 字段，同一行的其余字段（关键字、正则、附件类型、方向、动作类型、`is_active`、命中统计等）保持不变，不重新拉取整张列表。
  4. 操作不需要二次确认，不弹出额外的保存/取消对话框（即时生效于本地 mock 状态）。
- **与其他列的独立性**：切换"观察模式"列不影响"启用状态"列（`is_active`）的显示与取值，两者在同一行内并存、互不联动；反之，切换"启用状态"也不会重置该行的观察模式取值。

### 3.4 国际化

- 在 `contentRules` 命名空间下新增/复用 `observeMode`、`observeModeHint` 键，Switch 状态文案复用已有的 `common.enabled`/`common.disabled` 键，未引入重复的语义键。
- 中文资源使用 UTF-8 编码，不引入 Unicode replacement character 或异常全角问号字符。
- 英文、俄文、泰文资源文件已同步补齐对应翻译，保持四语言 key 集合一致。

### 3.5 Mock 数据与测试

- Mock 数据层为规则行的观察模式状态由页面本地 `observeModeById` 状态承载，覆盖开启和关闭两种状态，便于前端联调和视觉验证。
- 已有单元测试（`ContentRuleDrawer.test.tsx`、`ContentRulesTable.test.ts`）覆盖抽屉字段渲染与列表相关路径；后续如涉及观察模式回填/保存逻辑变更需同步补充断言。

## 7. 关联功能模块变更

### 7.1 规则效能统计——内容规则规则效能口径

- **需求背景**：内容规则支持观察模式后，需要在"规则效能统计"模块中看到该模块下规则的效能表现（命中量、动作分布、观察时长等），并支持从效能明细的"前往策略配置"跳转回对应的内容规则编辑抽屉，以及从"命中详情"跳转到邮件处置中心查看命中详情。
- **实现内容**：`src/lib/mock/rule-effectiveness-prototype.ts` 中已包含 `content_rules` 模块类型（`policy_module: 'content_rules'`）、跳转路径映射（`config_path.content_rules = '/security/pipeline?module=content'`，并按 `rule_id` 拼接查询参数用于深链定位）以及该模块的可执行动作口径（`reject`/`discard`/`quarantine`/`audit`）；`src/components/statistics/rule-effectiveness/constants.ts` 中已包含该模块的筛选项与专属配色（`#EC4899`）。
- **涉及文件**：`src/lib/mock/rule-effectiveness-prototype.ts`、`src/components/statistics/rule-effectiveness/constants.ts`。

#### 7.1.1 点击"前往策略配置"后的交互（操作级说明）

以下以内容规则效能明细行为例，逐步说明点击操作按钮到落地具体规则编辑抽屉的完整链路：

1. **用户操作**：用户在"规则效能统计"页效能明细表某一条 `policy_module = 'content_rules'` 的数据行上，点击"前往策略配置"操作按钮。
2. **触发回调**：`RuleEffectivenessPage.handleNavigateToConfig(row)` 被调用。
   - 若该行携带租户归属信息（`row.backend` 存在）且当前用户是系统管理员，先切换当前查看视角为该租户（`setViewer('tenant')`、`setSelectedTenant(row.backend.tenant_id)`），保证跳转后的配置页展示的是该规则所属租户的数据，而不是系统管理员当前所在的租户视角。
   - 取该行自带的 `row.config_path`（mock 数据中已按具体规则拼接为 `/security/pipeline?module=content&rule_id=<该规则的数据库 id>`）；若该字段为空则回退到模块级映射 `CONFIG_PATH_BY_MODULE.content_rules`（`/security/pipeline?module=content`，不含 `rule_id`）。
   - 在取到的路径后追加查询参数 `source=rule_effectiveness`（已含 `?` 则用 `&` 连接），得到最终跳转地址，例如 `/zh/security/pipeline?module=content&rule_id=1&source=rule_effectiveness`。
   - 调用 `router.push(...)` 完成页面跳转，浏览历史新增一条记录（用于后续"返回"操作回退）。
3. **落地页面解析深链**：跳转到的 `PolicyPipelinePage` 在渲染时调用 `parsePipelineDeepLink(searchParams)`：
   - 读取 `module=content`，匹配到 `PipelineModuleKey = 'content'`，对应 `stage = 3`（第三阶段"内容与附件检测"）。
   - 读取 `rule_id=1`，赋值为 `ruleRef='1'`，并通过 `parseRuleDatabaseID` 解析出纯数字的 `ruleDatabaseID=1`。
   - 若 `module` 缺失或不在已知模块表中，`parsePipelineDeepLink` 返回 `undefined`，深链失效，页面按默认态渲染（不自动展开任何抽屉）。
4. **自动展开抽屉并定位阶段**：
   - `PolicyPipelinePage` 依据解析出的 `deepLink.stage = 3` 自动将当前显示阶段切换到第三阶段。
   - 由于 `deepLinkAllowed` 为真（存在有效深链，且不是被 `lockStage1` 锁定的第一阶段场景），页面初始化时即把 `drawerOpen` 置为 `true`，`activeDrawerPolicy` 置为该 `deepLink`，即打开的第一时间就是内容规则的配置抽屉区域，而非停在流水线阶段总览让用户自己再点开。
   - 抽屉内渲染 `ContentRulesPage`（或其内嵌视图）时，将 `deepLinkRuleID={deepLink.ruleDatabaseID}`、`deepLinkRuleRef={deepLink.ruleRef}` 传入；`ContentRulesPage` 据此在其规则列表中查找 `id === 1` 的规则，自动打开该条规则的"编辑"抽屉（而不是内容规则的列表页或新建态）。
   - 若传入的 `ruleDatabaseID` 在当前规则列表中找不到匹配项（例如规则已被删除），则不自动打开编辑抽屉，页面停留在内容规则列表页，由用户自行确认规则状态。
5. **深链上下文提示**：抽屉内固定展示一行深链上下文提示文案（`t('pipeline.deepLinkRuleContext', { ruleId: deepLink.ruleRef })`），明确告知用户当前打开的抽屉是从规则 ID `1` 的深链跳转而来。
6. **来源上下文与返回入口**：由于 URL 携带 `source=rule_effectiveness`，页面额外计算出 `backContextNameKey`（取当前 `deepLink.key` 对应模块在流水线导航项中的名称 key），用于在页面顶部渲染"来源：规则效能统计 / 当前模块名"的上下文提示条，并提供"返回"入口：点击后若浏览历史可回退则 `router.back()` 直接回到规则效能统计页原有的筛选状态和分页位置；否则跳转到 `/statistics/rule-effectiveness` 兜底。
7. **编辑抽屉内的观察模式回显**：进入该规则的编辑抽屉后，抽屉内的观察模式开关按 3.2 节所述从 `observeModeById` 回填当前状态，用户可在该抽屉内直接查看/调整观察模式，无需再返回列表页操作。

### 7.2 邮件处置中心——上下文提示条对内容规则的兼容支持

- **需求背景**：在"规则效能统计"模块中，点击内容规则的"命中详情"跳转到邮件处置中心后，页面顶部需渲染来源上下文提示条，并提供可用的"返回"按钮返回规则效能统计页面，与发信人黑白名单、发信行为管控的既有体验保持一致。
- **实现内容**：
  1. `RuleEffectivenessContextBanner`（`rule-effectiveness-context-banner.tsx`）的模块白名单中已包含 `'content_rules'`，命中该 `policy_key` 时提示条正常渲染。
  2. 对 `policy_key === 'content_rules'` 的情况，与 `sender_filter`、`BEHAVIOR` 采用相同的路径展示策略：直接取 URL 上的 `strategy_name` 查询参数作为路径文本展示（不走多级策略路径拼接），并展示 `observe_window_from`~`observe_window_to` 的观察起始时间区间。
  3. "返回"按钮逻辑：若浏览历史可回退则调用 `router.back()` 返回规则效能统计页面，否则直接跳转到 `/statistics/rule-effectiveness`。
- **验证**：已核实代码逻辑——从规则效能统计模块点击内容规则的"命中详情"，跳转到邮件处置中心后顶部可正常展示来源上下文提示条（模块路径、观察时间区间），点击"返回"按钮可正常回到规则效能统计页面。
