# GT-14387 收件人检测支持观察模式

## 1. 需求背景

收件人检测模块包含两类独立策略：

- 数量限制策略：限制单封邮件的最大收件人数，并按收件方向执行阻断、审核、隔离等动作。
- 存在性验证策略：根据本地通讯录或目录数据验证收件人是否存在，并对验证失败的邮件执行配置动作。

当前两类策略命中后会直接执行配置的处置动作。为降低策略上线初期的误拦截风险，需要分别提供观察模式，使管理员可以先观察命中情况，再决定是否正式执行动作。

本需求只涉及收件人检测模块，不改变其他安全策略模块的功能、交互或文案。

## 2. 需求目标

- 数量限制策略拥有独立的观察模式开关。
- 存在性验证策略拥有独立的观察模式开关。
- 两个观察模式开关互不影响，分别控制对应策略。
- 观察模式开启后，策略仅记录命中情况，不执行该策略配置的真实处置动作。
- 观察模式与策略自身的启用状态独立存在。
- 观察模式文案和交互样式与“身份认证与仿冒检测”模块保持一致。
- 观察模式状态支持保存、读取和回填，不能仅依赖刷新前的页面临时状态。
- 规则效能统计和邮件处置中心能够识别两类策略的观察数据来源。
- 不修改收件人检测以外的其他功能模块。

## 3. 术语与策略边界

### 3.1 数量限制策略

- 策略标识：`recipient_limit`。
- 原有启用状态：`limit.is_active`。
- 观察模式状态建议字段：`limit.observe_mode`。
- 适用范围：精细化分方向配置，以及外发/域内合并控制配置下的数量限制。
- 观察对象：收件人数量超过配置阈值的邮件。
- 观察模式下保留：命中判断、方向判断、阈值判断、动作计算、日志记录。
- 观察模式下跳过：阻断、审核、隔离、丢弃等真实处置动作。

### 3.2 存在性验证策略

- 策略标识：`recipient_existence`。
- 原有启用状态：`check.existence_enabled`。
- 观察模式状态建议字段：`check.observe_mode`。
- 适用范围：收件人存在性验证及验证失败后的动作配置。
- 观察对象：收件人不存在、目录不可用或存在性验证失败的邮件。
- 观察模式下保留：目录查询、存在性判断、失败原因、命中日志。
- 观察模式下跳过：针对验证失败结果执行的阻断、隔离、审核等真实处置动作。

### 3.3 独立性要求

- `limit.observe_mode` 只影响数量限制策略。
- `check.observe_mode` 只影响存在性验证策略。
- 打开数量限制观察模式，不得改变存在性验证的开关或执行动作。
- 打开存在性验证观察模式，不得改变数量限制的阈值、方向配置或执行动作。
- 两类策略可以同时关闭、同时开启，或仅开启其中一个。
- 策略启用状态与观察模式状态分别维护：
  - 策略关闭时，该策略不参与检测，观察模式状态保留但不生效。
  - 策略开启且观察模式关闭时，按现有配置执行真实动作。
  - 策略开启且观察模式开启时，只记录命中，不执行真实动作。

## 4. 页面交互方案

### 4.1 页面进入

1. 用户进入“安全策略”页面。
2. 用户在左侧阶段 2“收发信人策略”中点击“收信人检测”。
3. 页面读取当前租户的收件人检测配置。
4. 页面分别读取数量限制策略和存在性验证策略的启用状态、观察模式状态及其详细配置。
5. 在两个策略卡片的标题区域分别渲染观察模式开关。
6. 未完成配置加载前，不展示错误的默认观察模式状态。

### 4.2 数量限制策略观察模式

1. 用户定位到“数量限制策略”卡片。
2. 用户看到数量限制策略的原有主开关、标题、说明，以及右侧独立的观察模式开关。
3. 观察模式关闭时，开关为关闭态，旁边显示“观察模式”或项目统一的关闭态文案；具体显示方式与“身份认证与仿冒检测”一致。
4. 用户点击数量限制观察模式开关。
5. 开关立即切换视觉状态，并显示与参考模块一致的观察状态 Badge/提示文案。
6. 数量限制策略的观察模式状态写入当前页面配置草稿。
7. 页面不修改以下内容：
   - 数量限制主开关；
   - 精细化分方向配置或合并配置；
   - 收件方向；
   - 最大收件人数阈值；
   - 执行动作；
   - 存在性验证策略及其观察模式。
8. 用户点击“保存”后，数量限制观察模式状态随收件人检测配置一并提交。
9. 保存成功后，重新读取或更新本地缓存中的数量限制观察模式状态。
10. 用户重新进入页面时，开关回填保存后的状态。

### 4.3 存在性验证策略观察模式

1. 用户定位到“存在性验证策略”卡片。
2. 用户看到存在性验证策略的原有主开关、标题、说明，以及右侧独立的观察模式开关。
3. 观察模式关闭时，开关为关闭态，旁边显示与“身份认证与仿冒检测”一致的关闭态文案。
4. 用户点击存在性验证观察模式开关。
5. 开关立即切换视觉状态，并在开启时显示统一的观察状态 Badge/提示文案。
6. 存在性验证观察模式状态写入当前页面配置草稿。
7. 页面不修改以下内容：
   - 存在性验证主开关；
   - 通讯录/目录可用性状态；
   - 验证失败动作；
   - 数量限制策略及其观察模式。
8. 用户点击“保存”后，存在性验证观察模式状态随收件人检测配置一并提交。
9. 保存成功后，重新读取或更新本地缓存中的存在性验证观察模式状态。
10. 用户重新进入页面时，开关回填保存后的状态。

### 4.4 样式与提示文案

观察模式开关必须复用“身份认证与仿冒检测”已有的视觉和交互模式，不新造一套样式。

- 使用项目现有的 `Switch` 组件。
- 使用与参考模块一致的开关尺寸、间距、状态色和布局。
- 开启时显示与参考模块一致的观察状态 Badge/状态文案，例如“观察中”。
- 关闭时使用“观察模式”作为截图要求的对应文案，不显示“正常执行”。
- 提示文案：
  - 中文：`启用后规则仅记录命中情况，不实际执行处置动作，用于验证规则效果。`
  - 英文、俄文、泰文按照现有国际化资源补齐，不改变 key 结构。
- 两个策略的开关都必须有独立的可访问名称：
  - `数量限制策略观察模式开关`。
  - `存在性验证策略观察模式开关`。
- 开关应支持键盘聚焦和屏幕阅读器读取。

### 4.5 模块级禁用

1. 用户关闭“收信人检测”模块总开关。
2. 数量限制策略和存在性验证策略的内容区域进入现有的禁用视觉状态。
3. 两个观察模式开关同步不可操作。
4. 观察模式当前值不被重置。
5. 用户重新启用收信人检测模块后，两个观察模式开关恢复此前保存的值。

### 4.6 保存与失败处理

1. 用户点击“保存”。
2. 页面校验数量限制阈值、动作配置及存在性验证配置。
3. 校验失败时：
   - 不提交任何配置；
   - 保留用户填写内容；
   - 在对应字段展示现有错误提示；
   - 两个观察模式开关状态不回滚。
4. 校验通过后，提交包含两类观察模式字段的收件人检测配置。
5. 保存成功时，提示保存成功，并保留当前页面状态。
6. 保存失败时，提示失败原因，保留用户当前草稿，允许重试。
7. 保存过程中禁用保存按钮，避免重复提交。
8. 保存过程不得修改其他安全策略模块的配置。

## 5. 数据模型与接口契约

### 5.1 前端配置类型

建议将观察模式字段放在对应策略对象内，而不是使用模块级单一字段：

```ts
type RecipientLimitConfig = {
  is_active: boolean;
  observe_mode: boolean;
  mode: 'detailed' | 'merged';
  inbound_limit?: RecipientDirectionConfig;
  outbound_limit?: RecipientDirectionConfig;
  internal_limit?: RecipientDirectionConfig;
  merged_limit?: RecipientDirectionConfig;
};

type RecipientCheckConfig = {
  existence_enabled: boolean;
  observe_mode: boolean;
  existence_action: RecipientCheckAction;
};
```

字段命名如与后端既有契约不一致，应以最终后端接口字段为准，但必须保持两个策略字段分别存在，不能合并为 `recipient_check.observe_mode`。

### 5.2 读取接口

读取收件人检测配置时必须返回：

- 数量限制策略观察模式状态；
- 存在性验证策略观察模式状态；
- 两个策略各自的启用状态；
- 其余现有配置字段。

服务端未返回字段时的兼容默认值：

- `limit.observe_mode` 默认为 `false`；
- `check.observe_mode` 默认为 `false`。

默认值仅用于兼容旧配置，不能把一个策略的状态复制给另一个策略。

### 5.3 保存接口

保存请求应同时携带两类策略的观察模式字段：

```json
{
  "limit": {
    "is_active": true,
    "observe_mode": false
  },
  "check": {
    "existence_enabled": true,
    "observe_mode": true
  }
}
```

保存接口必须做到：

- 对两个字段分别校验布尔类型；
- 未提交某一策略字段时，不覆盖该策略已有值；
- 不能把 `limit.observe_mode` 错写到 `check.observe_mode`；
- 不能因为一类策略保存失败而静默丢失另一类策略的值；
- 返回保存后的完整配置，供页面回填。

## 6. 邮件处理引擎执行语义

### 6.1 数量限制策略

1. 邮件进入收件人数检测阶段。
2. 系统依据现有方向判断逻辑确定 inbound、outbound、internal 或合并方向。
3. 系统读取对应阈值。
4. 当收件人数未超过阈值时，按现有逻辑继续处理，不产生策略命中。
5. 当收件人数超过阈值时，记录：规则标识、租户、方向、阈值、实际收件人数、原计划动作、时间、邮件关联标识。
6. 若 `limit.observe_mode = true`：
   - 将命中标记为观察命中；
   - 记录“原计划动作”；
   - 不执行阻断、审核、隔离或其他真实处置动作；
   - 继续后续允许观察模式继续的处理流程。
7. 若 `limit.observe_mode = false`：按原有逻辑执行配置动作。
8. 观察模式不能改变命中条件，也不能改变命中统计口径。

### 6.2 存在性验证策略

1. 邮件进入收件人存在性验证阶段。
2. 系统读取通讯录/目录状态。
3. 系统按现有逻辑判断每个收件人是否存在。
4. 当验证通过时，按现有逻辑继续处理。
5. 当验证失败时，记录：规则标识、失败类型、收件人数量、原计划动作、目录状态、时间、邮件关联标识。
6. 若 `check.observe_mode = true`：
   - 将命中标记为观察命中；
   - 记录“原计划动作”；
   - 不执行阻断、审核、隔离或其他真实处置动作；
   - 保留后续分析所需的检测结果。
7. 若 `check.observe_mode = false`：按原有逻辑执行配置动作。
8. 目录不可用与收件人不存在必须保留不同的失败原因，不能因观察模式而合并。

### 6.3 两类策略同时命中

1. 数量限制和存在性验证分别独立计算命中结果。
2. 两个策略分别读取各自的观察模式状态。
3. 数量限制开启观察模式、存在性验证关闭时：前者只记录，后者执行原有动作。
4. 数量限制关闭观察模式、存在性验证开启时：前者执行原有动作，后者只记录。
5. 两者均开启时：两者均只记录，不执行对应真实动作。
6. 两者均关闭时：两者均按原有动作执行。
7. 处置动作合并时必须保留每个策略的来源和原计划动作，避免一个策略的观察状态覆盖另一个策略的执行状态。

## 7. 规则效能统计关联变化

收件人检测是模块级配置，不是可单独编辑的规则列表。因此规则效能统计不应伪造不存在的收件人检测规则 ID，也不应将两类策略错误合并为一个规则。

### 7.1 模块与策略口径

建议新增模块标识：`recipient_check`。

建议新增两个策略标识：

- `recipient_limit`：数量限制策略。
- `recipient_existence`：存在性验证策略。

效能统计行至少应包含：

- `policy_module = 'recipient_check'`；
- `sub_strategy_id = 'recipient_limit'` 或 `'recipient_existence'`；
- 策略名称快照；
- 观察窗口起止时间；
- 观察命中数；
- 原计划动作分布；
- 实际执行动作分布；
- 观察模式状态；
- 可归因状态。

### 7.2 规则效能统计页面操作

1. 用户进入“规则效能统计”。
2. 用户在“策略模块”筛选器选择“收件人检测”。
3. 页面展示“数量限制策略”和“存在性验证策略”两条独立策略统计行。
4. 用户查看数量限制策略时，只看到数量限制策略的命中、原计划动作和观察窗口，不混入存在性验证数据。
5. 用户查看存在性验证策略时，只看到存在性验证策略的命中、失败原因和观察窗口，不混入数量限制数据。
6. 用户点击“前往策略配置”：
   - 数量限制策略跳转到收信人检测页面，并定位/高亮数量限制策略；
   - 存在性验证策略跳转到收信人检测页面，并定位/高亮存在性验证策略。
7. 跳转不得打开其他策略模块，也不得只打开收信人检测页面后丢失策略上下文。
8. 用户点击“查看命中邮件”时，跳转到邮件处置中心，并携带：
   - `source=rule_effectiveness`；
   - `policy_key=recipient_check`；
   - `sub_strategy=recipient_limit` 或 `recipient_existence`；
   - `strategy_name`；
   - `observe_window_from`；
   - `observe_window_to`。

### 7.3 统计口径

- 观察模式命中计入“命中数”。
- 观察模式命中的“原计划动作”计入动作分布。
- 观察模式命中的“实际执行动作”应为“未执行/仅观察”，不能误记为阻断、隔离或审核成功。
- 观察模式不会把正常通过邮件计入命中数。
- 数量限制和存在性验证分别聚合，不允许仅按 `recipient_check` 做不可拆分的总计。
- 若后端暂未提供真实统计数据，可先提供 mock 数据，但 mock 行必须明确标记来源为 mock，不能伪装为真实生产统计。

## 8. 邮件处置中心关联变化

### 8.1 上下文提示条

当用户从规则效能统计进入邮件处置中心时，处置中心需要识别 `policy_key=recipient_check`，并根据 `sub_strategy` 展示正确的来源：

- `sub_strategy=recipient_limit`：显示“收件人检测 / 数量限制策略”。
- `sub_strategy=recipient_existence`：显示“收件人检测 / 存在性验证策略”。

提示条应展示：

- 来源模块；
- 来源策略；
- 观察窗口起止时间；
- 返回规则效能统计的入口。

### 8.2 命中邮件列表筛选

1. 用户从数量限制策略点击“查看命中邮件”。
2. 处置中心读取 `policy_key=recipient_check` 与 `sub_strategy=recipient_limit`。
3. 处置中心只筛选数量限制策略命中邮件。
4. 用户从存在性验证策略点击“查看命中邮件”。
5. 处置中心读取 `policy_key=recipient_check` 与 `sub_strategy=recipient_existence`。
6. 处置中心只筛选存在性验证策略命中邮件。
7. 两类策略都必须保留观察命中标识，不能因处置中心默认动作状态而将观察命中误显示为已阻断或已隔离。

### 8.3 处置动作展示

对于观察模式命中邮件，处置中心应区分：

- 检测结果：已命中收件人检测策略；
- 原计划动作：按照策略配置本应执行的动作；
- 实际执行结果：观察模式，未执行原计划动作。

处置中心不得将“观察模式”显示为一种新的拦截动作，也不得将观察命中直接归入已处置邮件。

### 8.4 返回操作

1. 用户在处置中心打开来源上下文提示条。
2. 用户点击“返回”。
3. 若存在浏览历史，调用浏览器历史返回规则效能统计页面。
4. 若不存在可回退历史，跳转到 `/statistics/rule-effectiveness`。
5. 返回后保留原有筛选条件、时间范围和策略定位信息（若当前路由支持）。

### 8.5 不属于本需求的处置中心行为

- 不在邮件处置中心增加收件人检测配置编辑入口。
- 不在邮件处置中心增加观察模式开关。
- 不改变现有一键阻断、隔离、审核、放行等处置动作。

## 12. 测试与验证

### 12.1 单元测试

- 页面初始状态：两个观察模式字段默认关闭。
- 数量限制开关切换：只更新 `limit.observe_mode`。
- 存在性验证开关切换：只更新 `check.observe_mode`。
- 两个开关同时切换：状态分别保持正确。
- 配置序列化：两个字段写入正确对象路径。
- 配置反序列化：后端返回值分别正确回填。
- 兼容旧配置：缺少字段时两个字段分别默认 `false`。
- 国际化 key 校验：zh/en/ru/th 四份资源结构一致。
- 规则效能统计：两个子策略能分别生成统计行。
- 处置中心上下文：`recipient_limit` 与 `recipient_existence` 分别展示正确来源。

### 12.2 浏览器验证

1. 打开收件人检测页面。
2. 确认数量限制策略和存在性验证策略各有一个观察模式开关。
3. 只打开数量限制观察模式，确认存在性验证观察模式保持关闭。
4. 只打开存在性验证观察模式，确认数量限制观察模式保持关闭。
5. 同时打开两个开关，确认均显示“观察中”。
6. 关闭收件人检测模块，确认两个开关不可操作但状态不丢失。
7. 保存并刷新页面，确认两个开关分别回填。
8. 打开规则效能统计，确认能区分两类收件人检测策略。
9. 从数量限制策略进入处置中心，确认上下文显示“收件人检测 / 数量限制策略”。
10. 从存在性验证策略进入处置中心，确认上下文显示“收件人检测 / 存在性验证策略”。
11. 确认观察命中显示原计划动作和实际未执行结果。
12. 点击返回，确认回到规则效能统计页面。
