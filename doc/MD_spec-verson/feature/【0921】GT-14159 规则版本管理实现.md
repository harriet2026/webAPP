## A.1 实质性与非实质性变更统一判定

### A.1.1 实质性变更

实质性变更是指会改变规则的匹配范围、判定结果、处置结果、执行方式或统计归属的配置变化。发生实质性变更时必须创建新版本，并执行以下动作：

- 当前版本标记为 `superseded`，新版本从实际生效时间开始统计。
- 新版本重新记录 `effective_at`、观察开始时间和版本配置快照。
- 观察模式下，命中数、处置结果、风险指标和趋势从新版本生效时间重新计算。
- 旧版本保持只读，可用于历史效能查询和审计对比。

通用实质性字段包括：

| 字段类别 | 典型字段 | 变更影响 |
|---|---|---|
| 规则开关 | `enabled`、规则整体启用/停用 | 改变规则是否参与执行 |
| 观察状态 | `observe_mode` | 改变规则是否以观察方式运行；关闭本身的统计状态变化见下方例外 |
| 处置动作 | `action`、`disposition` | 改变命中后的投递、隔离、审核、拒收或丢弃结果 |
| 匹配条件 | 阈值、相似度、主题匹配方式、对齐模式、必选条件 | 改变命中范围或判定结果 |
| 作用域 | `scope`、方向、租户、域名、IP 范围 | 改变规则适用对象 |
| 例外范围 | `exception_domains`、`exception_ips`、白名单/黑名单 | 改变规则排除或纳入对象 |
| 执行策略 | 检测模式、聚合/按方向独立模式、协议检查参数 | 改变规则执行逻辑或统计边界 |

### A.1.2 非实质性变更

非实质性变更是指不改变规则匹配、判定、处置、执行范围和统计归属的变化。非实质性变更不得创建新版本，不得重置观察时间、命中数或效能统计起点。

通用非实质性字段包括：

| 字段类别 | 典型字段 | 处理方式 |
|---|---|---|
| 展示名称 | `display_name`、页面标题、规则别名 | 更新展示文案，不创建新版本 |
| 描述信息 | `description`、帮助说明、备注 | 更新说明，不创建新版本 |
| 审计信息 | 操作备注、变更原因、工单号 | 写入审计记录，不改变版本统计 |
| 展示排序 | `sort_order`、卡片顺序、Tab 顺序 | 仅影响页面展示 |
| 展示偏好 | 展开/收起、默认 Tab、筛选条件、分页 | 仅影响当前用户界面 |
| 历史查看 | 打开历史抽屉、查看快照、导出历史 | 只读操作，不创建新版本 |

### A.1.3 边界判定与例外

- 字段是否实质性，以其是否改变规则执行结果或统计归属为准，不能只按字段名称判断。
- 关闭观察模式本身不创建新版本；它只将当前版本从 `observing` 切换为静态状态，并停止累加观察时长。若关闭观察模式同时修改了匹配条件、处置动作或其他实质性字段，则创建新版本。
- 单纯修改变更原因、备注或操作人信息不创建新版本，但必须写入审计日志。
- 前端未改变配置值而重复保存，不创建新版本。
- 一次保存包含多个实质性字段变化，只创建一个新版本，并在变更摘要中列出所有变化字段。

# 一、相似检测模块

## 1.1 术语与版本归属原则

### 0.1 策略类型

“相似邮件检测”和“相同主题检测”是两个独立策略，不共享版本号、当前版本、观察周期、命中统计或版本历史。

- `similar_email`：相似邮件检测。
- `same_subject`：相同主题检测。

页面 Tab 切换时，必须同时切换当前策略的版本摘要、观察数据和版本历史入口。

### 0.2 策略版本作用域

版本归属采用三级作用域：

```text
策略类型 → 检测模式 → 方向
```

具体规则如下：

| 层级 | 取值 | 版本历史规则 |
|---|---|---|
| 策略类型 | 相似邮件检测、相同主题检测 | 两个策略各自维护版本链 |
| 检测模式 | 全方向聚合 | 当前策略使用一套聚合版本历史 |
| 检测模式 | 按方向独立检测 | 当前策略下每个启用方向拥有独立版本历史 |
| 方向 | 接收、外发、域内 | 只在按方向独立检测时作为版本作用域 |

因此，以下记录互不混用：

- 相似邮件检测 / 全方向聚合 / v5。
- 相似邮件检测 / 接收方向 / v2。
- 相同主题检测 / 全方向聚合 / v3。

### 0.3 版本创建原则

- 规则配置实际发生变化时创建新版本。
- 仅打开或关闭页面、展开历史抽屉、切换 Tab 不创建新版本。
- 版本历史不可因观察模式关闭而删除。
- 版本快照必须能够支持审计、对比和回滚预览。
- 版本号在策略作用域内递增，不使用跨两个策略的全局连续编号。

## 1. 功能概述

规则版本管理用于记录相似检测策略的配置变更、观察周期和命中结果，使管理员能够区分两个策略、不同检测模式及不同方向的规则状态，并在模式切换后保留完整的审计链路。

### 1.1 功能点

- 在“相似邮件检测”和“相同主题检测”两个 Tab 内分别展示当前策略版本。
- 每个策略独立维护版本历史。
- 全方向聚合模式下，一个策略使用一套版本历史。
- 按方向独立检测模式下，一个策略按接收、外发、域内方向分别维护版本历史。
- 版本历史默认收起，通过右侧抽屉查看。
- 聚合模式与独立模式切换时记录模式切换事件。
- 观察模式关闭后仍保留当前版本和历史版本，但当前摘要不得继续显示“观察中”的动态语义。
- 所有用户可见文案通过项目国际化框架提供。

### 1.2 相似检测字段变更分类

#### 实质性字段

以下字段任一发生变化，均创建相似检测子策略的新版本，并从新版本生效时间重新统计规则效能：

- 相似邮件检测或相同主题检测的 `enabled`。
- `action`、`disposition` 等命中后的处置动作。
- 相似度阈值、主题匹配阈值、匹配算法或标准化方式。
- 检测方向和作用域：聚合模式、按方向独立模式、接收、外发、域内。
- 适用租户、域名、IP 范围以及白名单、例外域名、例外 IP。
- 去重窗口、时间窗口、重复命中合并规则等会改变命中集合的参数。

#### 非实质性字段

以下字段变化不创建新版本，不重置观察周期或效能统计：

- 子策略显示名称、描述、帮助文本和变更备注。
- 历史抽屉是否展开、默认选择的方向、页面排序和筛选条件。
- 仅修改工单号、操作原因等审计补充信息。

检测模式从聚合切换为按方向独立，或从按方向独立切换为聚合，会改变统计作用域，因此属于实质性变更；仅切换页面查看方向不属于配置变更。

### 1.2.1 具体规则：相似邮件检测

相似邮件检测的版本归属为 `similar_email`。版本作用域由检测模式决定：

| 检测模式 | 版本作用域 | 统计作用域 |
|---|---|---|
| 全方向聚合 | `similar_email / aggregate` | 接收、外发、域内合并统计 |
| 按方向独立检测 | `similar_email / receive`、`send`、`internal` | 每个启用方向独立统计 |

#### 全方向聚合模式的字段判定

| 配置项 | 示例字段 | 变更性质 | 处理方式 |
|---|---|---|---|
| 检测模式 | `detection_mode: aggregate` | 实质性 | 创建新的 `aggregate` 版本，重新确定统计起点 |
| 启用状态 | `enabled` | 实质性 | 创建新版本；停用版本不再计入当前策略数 |
| 相似度阈值 | `similarity_threshold` | 实质性 | 创建新版本；阈值变化会改变命中集合 |
| 匹配算法 | `match_algorithm` | 实质性 | 创建新版本；算法或标准化方式变化会改变判定结果 |
| 时间窗口 | `dedup_window`、`lookback_window` | 实质性 | 创建新版本；影响可比较邮件集合 |
| 命中处置 | `action`、`disposition` | 实质性 | 创建新版本；影响命中后的处置结果 |
| 方向开关 | `receive_enabled`、`send_enabled`、`internal_enabled` | 实质性 | 创建新版本；改变聚合统计纳入的流量范围 |
| 例外范围 | `exception_domains`、`exception_ips`、白名单 | 实质性 | 创建新版本；改变规则适用对象 |
| 显示名称 | `display_name` | 非实质性 | 仅更新展示，不重置观察统计 |
| 规则说明 | `description`、`help_text` | 非实质性 | 仅更新说明，不创建新版本 |
| 审计信息 | `change_reason`、`ticket_id`、`operator_note` | 非实质性 | 写入审计日志，不改变效能统计 |

聚合模式下，单独修改接收、外发或域内方向的开关仍属于实质性变更，因为它会改变 `aggregate` 版本的统计样本范围；但不创建方向级版本。

#### 按方向独立检测模式的字段判定

按方向独立模式下，每个方向拥有自己的版本链。只修改接收方向时，不得递增外发和域内方向版本。

| 配置项 | 变更性质 | 处理方式 |
|---|---|---|
| `detection_mode: separate` | 实质性 | 为启用方向创建或更新方向级版本 |
| 启用/停用某个方向 | 实质性 | 仅该方向创建版本；停用方向不计入当前策略数 |
| 某方向的相似度阈值 | 实质性 | 仅该方向版本递增，效能统计从新版本生效时间开始 |
| 某方向的匹配算法或标准化方式 | 实质性 | 仅该方向版本递增 |
| 某方向的时间窗口、去重窗口 | 实质性 | 仅该方向版本递增 |
| 某方向的处置动作 | 实质性 | 仅该方向版本递增 |
| 某方向的域名、IP、租户范围或例外范围 | 实质性 | 仅该方向版本递增 |
| 方向显示名称、描述、备注 | 非实质性 | 不创建版本，不重置统计 |
| 页面当前查看方向 | 非实质性 | 只改变页面视图，不改变配置或统计 |
| 历史抽屉筛选、排序、展开状态 | 非实质性 | 只读交互，不创建版本 |

#### 模式切换的版本处理

- `aggregate → separate`：属于实质性变更；记录模式切换事件，为每个启用方向创建初始化版本。聚合版本的历史数据不得复制计入各方向。
- `separate → aggregate`：属于实质性变更；创建新的聚合版本，记录来源方向版本列表。各方向历史数据不得直接相加伪装为新的聚合版本数据。
- 模式切换后的效能统计从新版本实际生效时间开始，切换前数据只作为历史版本或来源参考展示。

### 1.2.2 具体规则：相同主题检测

相同主题检测的版本归属为 `same_subject`，字段判定与相似邮件检测一致，但阈值字段使用 `subject_similarity_threshold` 或 `subject_match_mode`。具体规则如下：

- 全方向聚合模式下，主题阈值、主题标准化、时间窗口、方向开关、处置动作和例外范围属于实质性字段，任何变化都创建 `same_subject / aggregate` 新版本。
- 按方向独立模式下，上述字段只影响对应方向版本，不影响其他方向版本。
- 显示名称、描述、帮助文本、审计备注、页面筛选和历史查看均为非实质性变化。
- 聚合与独立模式互切创建新版本，历史统计不跨模式合并。

### 1.3 不在本次范围内

- 不新增新的策略类型。
- 不改变相似检测规则的匹配算法、执行动作或方向配置规则。
- 不改变租户权限模型。
- 不删除历史版本。
- 不在页面中直接实现服务端数据库迁移；正式存储由后端接口负责。

## 2. 页面信息架构

### 2.1 策略 Tab

页面顶部保留两个策略 Tab：

- 相似邮件检测。
- 相同主题检测。

每个 Tab 的内容区独立渲染以下模块：

1. 当前策略版本摘要。
2. 当前策略配置。
3. 检测模式和方向配置。
4. 版本历史入口。

切换 Tab 时，版本摘要和历史抽屉必须跟随当前策略切换，不能继续显示上一个策略的版本数据。

### 2.2 当前版本摘要

当前版本摘要采用紧凑横向布局，不再在页面内默认展开完整历史列表。摘要至少包含：

- 当前策略版本号。
- 观察开始时间。
- 观察时长。
- 当前版本命中数。
- 版本历史入口及历史版本数量。

当观察模式关闭时：

- 保留当前策略版本和历史入口。
- 状态文案显示“观察模式已关闭”或等价的国际化文案。
- 不显示会误导用户的实时“观察中”文案。
- 上一个观察周期作为历史信息保留。

### 2.3 版本历史抽屉

版本历史通过右侧 Sheet 抽屉查看，避免历史列表占据主页面高度。

抽屉要求：

- 标题包含当前策略名称和“版本历史”。
- 展示当前作用域：全方向聚合，或具体方向。
- 按时间倒序展示版本记录。
- 每条记录展示版本号、生效时间、变更摘要和历史命中数。
- 空历史显示明确空状态。
- 在按方向独立检测模式下提供方向切换控件。
- 抽屉关闭后，当前页面配置位置和滚动位置不应发生无意义跳变。

## 3. 核心交互

### 3.1 策略 Tab 切换

IA-01：用户从“相似邮件检测”切换到“相同主题检测”时：

1. 当前策略作用域切换为 `same_subject`。
2. 当前版本摘要切换为 `same_subject` 的版本状态。
3. 版本历史数量和历史记录切换为 `same_subject` 的数据。
4. 当前策略配置切换为相同主题检测配置。
5. 相似邮件检测的未保存修改不得静默覆盖相同主题检测配置。

反向切换时遵循同样规则。

### 3.2 全方向聚合

全方向聚合下，当前策略使用 `aggregate` 作用域：

```text
当前策略 / aggregate / 当前版本
当前策略 / aggregate / 历史版本列表
```

接收、外发和域内方向不产生独立版本链；方向配置仅作为聚合策略的配置内容保存。

### 3.3 按方向独立检测

按方向独立检测下，当前策略按启用方向维护版本历史：

```text
当前策略 / receive / 版本历史
当前策略 / send / 版本历史
当前策略 / internal / 版本历史
```

历史抽屉中的方向切换只改变当前查看的作用域，不改变当前策略 Tab。

### 3.4 聚合切换为独立

当当前策略从全方向聚合切换为按方向独立检测时：

- 记录一条模式切换事件。
- 记录切换前策略类型和聚合版本。
- 为每个启用方向生成初始化版本。
- 初始化版本标记来源为“由聚合版本初始化”。
- 切换前的聚合命中数不得重复计入每个方向的独立命中数。
- 切换前的聚合历史作为来源参考保留，不伪装成方向历史。

示例：

```text
相似邮件检测 / aggregate / v5
切换事件：aggregate → separate
相似邮件检测 / receive / v1，来源：aggregate v5
相似邮件检测 / send / v1，来源：aggregate v5
```

### 3.5 独立切换为聚合

当当前策略从按方向独立检测切换为全方向聚合时：

- 记录一条模式切换事件。
- 记录切换前各方向最后生效版本。
- 创建新的聚合版本。
- 聚合版本记录来源方向版本列表。
- 如果各方向配置不一致，保存前必须明确冲突解决结果。
- 不得静默选择某一个方向配置覆盖其他方向配置。

可选冲突解决方式：

- 使用指定方向配置。
- 手动合并配置。
- 取消本次模式切换。

### 3.6 配置保存与版本递增

- 只有当前策略 Tab 的实际配置变化会递增该策略版本。
- 保存相似邮件检测不会递增相同主题检测版本。
- 保存相同主题检测不会递增相似邮件检测版本。
- 保存按方向独立检测配置时，只影响当前策略及对应方向作用域。
- 保存失败时不应更新前端显示的版本号或历史记录。
- 版本冲突时应保留用户编辑内容并提示重新加载或合并。

## 4. 数据模型与接口契约

### 4.1 策略级版本状态

当前前端配置通过 `policy_versions` 区分两个策略：

```ts
policy_versions: {
  similar_email?: SimilarDetectionPolicyVersionState;
  same_subject?: SimilarDetectionPolicyVersionState;
}
```

每个策略版本状态至少包含：

- `version`：当前策略版本号。
- `observation_started_at`：当前版本观察开始时间。
- `observation_days`：当前版本观察时长。
- `hit_count`：当前版本命中数。
- `history_by_scope`：按聚合或方向保存版本快照。

### 4.2 版本历史快照

```ts
SimilarDetectionVersionSnapshot {
  version: number;
  created_at: string;
  observation_started_at: string;
  observation_days: number;
  hit_count: number;
  change_summary: string;
  config: SimilarDetectionConfig;
}
```

正式接口实现时，快照中的配置应为不可变快照，不得随着当前配置对象变化而被引用修改。

### 4.3 模式切换事件

```ts
SimilarDetectionModeTransition {
  id: string;
  from_mode: 'aggregate' | 'separate';
  to_mode: 'aggregate' | 'separate';
  created_at: string;
  source_version: number;
  target_scopes: ('aggregate' | 'receive' | 'send' | 'internal')[];
  summary: string;
}
```

模式切换事件必须归属于当前策略类型，不能成为两个策略共享的全局事件。

### 4.4 兼容旧接口

当后端暂未返回 `policy_versions` 时，前端可以回退使用旧的 `version`、`history` 和 `history_by_scope` 字段展示；回退只用于兼容旧数据，不代表两个策略在业务上共享版本。

正式接口完成后，应以策略级版本字段为唯一事实源，并逐步移除跨策略的旧字段依赖。

## 5. 观察模式语义

### 5.1 观察模式开启

展示：

- 当前策略版本。
- 观察开始时间。
- 观察时长。
- 当前版本命中数。
- 版本历史入口。

### 5.2 观察模式关闭但规则仍生效

仍展示当前版本和版本历史，状态明确标记为：

> 规则生效，观察模式已关闭。

保留上一次观察周期和历史命中数据，但不继续累加观察时长或显示“观察中”。

### 5.3 规则整体停用

仍展示最后生效版本和版本历史，状态标记为“规则已停用”。页面不展示当前运行中的观察数据；历史观察周期仍可追溯。

### 5.4 关闭观察模式的版本规则

关闭观察模式本身不自动创建新版本，也不删除版本。只有规则配置发生实际变更时才创建新版本，并记录变更摘要。

## 6. 异常与边界场景

| 场景 | 处理要求 |
|---|---|
| 当前策略没有历史 | 抽屉显示空状态，不影响配置编辑 |
| 后端缺少策略级版本字段 | 使用兼容字段展示，并避免把两个策略的历史合并 |
| 当前方向被取消启用 | 保留该方向历史，只从可选查看方向中移除 |
| 模式切换后无启用方向 | 阻止保存并提示至少启用一个方向 |
| 独立模式配置存在冲突 | 显示冲突解决界面，不静默覆盖 |
| 保存版本冲突 | 保留用户输入，提示刷新或合并 |
| 观察模式关闭 | 保留历史和当前版本，切换为静态状态文案 |
| 权限不足 | 禁止修改并按现有权限体系展示只读状态 |

## 1.7 关联功能模块：规则效能统计

相似检测增加策略版本维护后，规则效能统计页面必须以“策略版本”为统计边界，不能把不同版本的命中和处置结果合并为当前版本数据。

### 1.7.1 统计对象

相似检测包含两个独立子策略：

- `similar_email`：相似邮件检测。
- `same_subject`：相同主题检测。

每个子策略按自身的当前版本和作用域统计。若采用按方向独立检测，还需进一步按 `receive`、`send`、`internal` 分开统计。

```text
规则效能统计
├─ 相似邮件检测 / 当前有效版本 / 当前作用域
└─ 相同主题检测 / 当前有效版本 / 当前作用域
```

### 1.7.2 观察模式统计口径

当子策略启用观察模式时，规则效能统计默认只纳入当前有效且状态为 `observing` 的版本：

$$观察时长 = 当前时间 - 当前版本的 observed_since$$

$$观察策略数 = count(status = observing \land version = current)$$

当前版本的命中数、命中率、投递、隔离、审核、拒收、丢弃、召回以及误判/漏判风险，只统计该版本 `effective_at` 之后产生的数据。版本切换前的数据归入旧版本，不得回填到新版本。

### 1.7.3 页面展示要求

规则效能统计是多个独立版本链（`similar_email` 的聚合/按方向、`same_subject`）的汇总视图，不存在一个能代表全部策略的“页面版本”。因此页面顶部（KPI 卡上方筛选栏）**不得**提供“策略效能版本”这类全局版本选择器：全局下拉隐含“选一个版本，全页面跟随切换”的语义，但不同策略、不同方向的版本号互相独立，选中的版本号对其他行没有意义，会让用户误判筛选范围。

版本查看入口必须下沉到明细列表的**行级**，每个统计对象（策略、方向或规则）各自维护自己的版本入口：

- 明细表格每一行在策略/规则名称旁展示“当前 v{N}”标签，代表该行自身的当前有效版本号，与其他行无关。
- 每一行提供“版本历史”入口（按钮或行展开箭头），点击后仅展开或弹出该行自身的历史版本列表（版本号、生效时间段、命中数、处置分布、变更摘要），不影响其他行，也不影响页面顶部 KPI。
- KPI 卡（观察策略数、观察期总命中数、平均观察时长、待转正策略数）始终按“各行自身的当前有效版本”聚合，不随任何行的历史版本查看而变化。
- 历史版本展示时必须明确标注版本号、生效时间范围和“历史版本”状态，与当前版本区分。

旧版本不进入当前 KPI 和当前明细列表的汇总口径；只有在某一行主动展开“版本历史”时，才展示该行对应旧版本的独立统计。

### 1.7.4 统计隔离原则

- 相似邮件检测与相同主题检测不共享版本号、观察时长或效能统计。
- 聚合模式与按方向独立模式不混合统计；按方向独立时，`receive`、`send`、`internal` 在明细表中各自成行，各自维护独立的版本入口。
- 旧版本只读保留，用于历史追溯，不与当前版本合并。
- 非实质性变更不创建新版本，也不重置观察时间和效能统计起点。
- 实质性变更创建新版本，旧版本变为 `superseded`，新版本从实际生效时间开始统计。
- 统计页面显示的策略数、命中数和处置结果必须能够追溯到具体 `policy_id`、`version_id` 和 `effective_at`。
- 版本查看入口只能是行级交互（行内标签 + 版本历史按钮/展开），页面顶部筛选栏不得出现以版本号为选项的全局选择器。

### 1.7.5 关联接口建议

规则效能统计接口应支持以下筛选条件：

```ts
RuleEffectivenessQuery {
  policy_id: 'similar_email' | 'same_subject';
  version_id?: string;
  scope?: 'aggregate' | 'receive' | 'send' | 'internal';
  status?: 'observing' | 'active' | 'superseded' | 'disabled' | 'deleted';
  include_history?: boolean;
}
```

默认 `include_history = false`，接口返回当前有效版本；主动查看历史时必须显式传入 `version_id` 或 `include_history = true`，避免页面无意合并历史数据。

# 二、身份认证与仿冒检测模块

## 2.1 模块范围与规则归属

身份认证与仿冒检测中的每条可独立配置、独立启停、独立命中的规则分别维护自己的策略版本链，不按页面统计或整个模块生成版本。

当前纳入版本管理的规则：

| 规则标识 | 规则名称 | 版本归属 |
|---|---|---|
| `mailfrom_empty` | 空 MAIL FROM | 独立版本链 |
| `mailfrom_invalid` | 无效 MAIL FROM | 独立版本链 |
| `envelope_header_mismatch` | 信封与头部不匹配 | 独立版本链 |
| `spf_fail`、`spf_softfail`、`spf_none`、`spf_temperror`、`spf_permerror` | SPF 检查各判定结果（硬拒绝、软拒绝、未维护、查询失败、SPF 记录错误） | 每个判定结果各自独立版本链 |
| `dkim_fail`、`dkim_neutral`、`dkim_partial`、`dkim_none`、`dkim_temperror` | DKIM 检查各判定结果 | 每个判定结果各自独立版本链 |
| `dmarc_reject`、`dmarc_quarantine`、`dmarc_none`、`dmarc_no_record`、`dmarc_query_fail` | DMARC 检查各判定结果 | 每个判定结果各自独立版本链 |
| `ptr_noptr`、`ptr_nomatch`、`ptr_ehlo_mismatch` | PTR 检查各判定结果 | 每个判定结果各自独立版本链 |

**协议检查的版本归属单位是“协议 + 判定结果”的组合，不是整个协议。** 以 SPF 为例，“硬拒绝”“软拒绝”“未维护”“查询失败”“SPF 记录错误”分别对应界面上的一行处置配置，每一行都是一条独立的规则，各自维护自己的版本号、观察状态和历史记录；只修改“硬拒绝”这一行的处置动作，不会影响“软拒绝”等其他判定结果行的版本。DKIM、DMARC、PTR 的各判定结果行同理，均按各自的判定结果单独计版本，不按协议整体计版本。

页面上的“SPF”“DKIM”“DMARC”“PTR” Tab 仅用于分组展示，不是版本归属单位；Tab 本身不维护版本号，也不产生页面级或协议级的汇总版本。

页面汇总统计不是版本归属单位；一次修改多条规则时，只为实际变化的规则分别创建新版本，不创建批量版本记录。

## 2.2 身份认证与仿冒检测字段变更分类

#### 实质性字段

以下字段任一发生变化，均创建对应认证规则的新版本，并从新版本生效时间重新统计规则效能：

- 格式检查规则 `mailfrom_empty`、`mailfrom_invalid`、`envelope_header_mismatch` 的 `enabled`。
- 上述规则的 `action`、`disposition` 或其他命中处置动作。
- SPF、DKIM、DMARC、PTR 的启用状态、处置动作、阈值、对齐模式和必选条件。
- 认证协议检查的检测方向、作用域、例外域名、例外 IP 和租户范围。
- 会改变认证判定结果的协议参数、身份匹配条件、头部与信封比对条件。
- 观察模式下会改变规则执行方式的配置项；但单独关闭观察模式按统一边界规则处理。

#### 非实质性字段

以下字段变化不创建新版本，不重置观察周期或效能统计：

- 规则显示名称、描述、帮助文本和管理备注。
- 历史记录的查看、展开/收起、排序、筛选和导出。
- 仅补充工单号、变更原因或审计说明。
- 页面 Tab 切换，以及只读查看 SPF、DKIM、DMARC 或 PTR 的历史快照。

协议参数是否属于实质性变更，以其是否改变认证结果或适用范围为准。字段虽然名称相同，但若仅改变展示格式而不影响执行，则按非实质性变更处理。

## 2.3 功能概述与非目标

功能目标：在身份认证与仿冒检测页面中，为格式检查和协议检查提供规则级当前版本、历史版本、观察信息和配置快照。

- 格式检查规则与协议检查规则的版本链彼此独立。
- 规则版本历史通过对应规则行或协议 Tab 的历史入口查看。
- 页面不展示统一的“当前页面版本”或页面级版本历史模块。
- 观察模式关闭后保留当前版本和历史版本，不删除审计记录。

本模块不改变认证算法、规则执行顺序、权限模型或现有处置动作语义。

## 2.3 页面信息架构

```text
身份认证与仿冒检测
├─ 汇总统计
├─ 格式检查
│  ├─ 空 MAIL FROM        当前版本 / 查看版本历史
│  ├─ 无效 MAIL FROM      当前版本 / 查看版本历史
│  └─ 信封与头部不匹配   当前版本 / 查看版本历史
└─ 协议检查（Tab 仅分组展示，不维护版本）
   ├─ SPF Tab
   │  ├─ 硬拒绝（fail）        当前版本 / 查看版本历史
   │  ├─ 软拒绝（softfail）    当前版本 / 查看版本历史
   │  ├─ 未维护（none）        当前版本 / 查看版本历史
   │  ├─ 查询失败（temperror） 当前版本 / 查看版本历史
   │  └─ SPF 记录错误（permerror） 当前版本 / 查看版本历史
   ├─ DKIM Tab
   │  ├─ fail / neutral / partial / none / temperror 各判定结果  当前版本 / 查看版本历史
   ├─ DMARC Tab
   │  ├─ reject / quarantine / none / no_record / query_fail 各判定结果  当前版本 / 查看版本历史
   └─ PTR Tab
      ├─ noptr / nomatch / ehlo_mismatch 各判定结果  当前版本 / 查看版本历史
```

每条规则的历史抽屉只展示当前规则自身的版本。协议检查切换 Tab 只是切换分组展示范围，Tab 内的每个判定结果行仍各自维护独立的当前版本、观察数据和历史记录，互不影响。

## 2.4 核心交互与版本递增

- 只修改“空 MAIL FROM”时，仅该规则递增版本；无效 MAIL FROM、信封与头部不匹配及所有协议判定结果规则版本保持不变。
- 只修改某个协议下的某个判定结果（例如 SPF 的“硬拒绝”）时，仅该判定结果对应的规则递增版本；同一协议下的其他判定结果（如“软拒绝”“未维护”）版本保持不变。
- 修改多个规则时，分别生成各自版本，不记录批量变更记录。
- 仅打开历史抽屉、切换页面 Tab、切换观察展示状态不创建配置版本。
- 每个新版本保存变更前配置快照、变更摘要、创建时间和生效时间。
- 保存失败时不得更新前端版本号或历史列表。

## 2.5 数据模型与接口契约

格式检查规则沿用规则项中的独立字段：

```ts
CheckItem {
  version?: number;
  observation_started_at?: string;
  observation_days?: number;
  hit_count?: number;
  history?: AuthSpoofingRuleVersionSnapshot[];
}
```

协议检查的版本状态必须按“协议判定结果”键分组，不能按协议整体键分组。每个协议判定结果键形如 `{protocol}_{result}`（例如 `spf_fail`、`spf_softfail`、`dkim_neutral`、`dmarc_no_record`、`ptr_ehlo_mismatch`），各自独立维护版本号、观察信息和历史：

```ts
ProtocolChecksConfig {
  rule_versions?: Record<ProtocolResultRuleId, number>;
  rule_history?: Record<ProtocolResultRuleId, ProtocolRuleVersion[]>;
  rule_observation_started_at?: Record<ProtocolResultRuleId, string>;
  rule_observation_days?: Record<ProtocolResultRuleId, number>;
  rule_hit_count?: Record<ProtocolResultRuleId, number>;
}

type ProtocolResultRuleId =
  | 'spf_fail' | 'spf_softfail' | 'spf_none' | 'spf_temperror' | 'spf_permerror'
  | 'dkim_fail' | 'dkim_neutral' | 'dkim_partial' | 'dkim_none' | 'dkim_temperror'
  | 'dmarc_reject' | 'dmarc_quarantine' | 'dmarc_none' | 'dmarc_no_record' | 'dmarc_query_fail'
  | 'ptr_noptr' | 'ptr_nomatch' | 'ptr_ehlo_mismatch';
```

`ProtocolResultRuleId` 只用于版本、观察和历史的键控，不新增独立的协议判定接口；协议判定结果本身仍沿用 `ProtocolChecksSection.tsx` 中 `PROTOCOL_GROUPS` 定义的 `keys`（如 `fail`、`softfail`、`none` 等）与协议前缀组合而成，两处必须保持一致。

每条历史记录必须包含：版本号、创建时间、观察开始时间、观察时长、版本期间命中数、变更摘要和不可变配置快照。

## 2.6 观察模式语义

- 观察中：显示当前规则版本、观察开始时间、观察时长、命中数和历史入口。
- 观察模式关闭且规则仍生效：显示当前生效版本、最后一次观察结果和历史入口，状态文案不得继续显示“观察中”。
- 规则停用：保留最后生效版本和历史入口，不展示当前运行中的观察数据。
- 关闭观察模式本身不创建配置版本；如果同时修改规则配置，按实际配置变化创建新版本。

## 2.7 异常与边界场景

| 场景 | 处理要求 |
|---|---|
| 规则没有历史 | 规则历史抽屉显示空状态，不影响编辑 |
| 修改一条规则 | 仅该规则版本递增 |
| 一次修改多条规则 | 分别生成规则版本，不生成批量记录 |
| 规则停用 | 保留最后版本和历史，不清空数据 |
| 后端未返回版本字段 | 使用默认版本展示，保存后按规则补齐版本数据 |
| 权限不足 | 按现有权限体系展示只读或禁止编辑状态 |
| 版本保存冲突 | 保留用户编辑内容，提示重新加载或合并 |

## 2.8 关联功能模块：规则效能统计

身份认证与仿冒检测的规则效能统计必须按具体规则版本统计，不得按“身份认证与仿冒检测”页面整体汇总后再归属版本。

### 2.8.1 统计对象

格式检查和协议检查中的每条规则分别作为统计对象。协议检查的统计对象是“协议判定结果”，不是协议整体：

```text
格式检查：空 MAIL FROM、无效 MAIL FROM、信封与头部不匹配
协议检查（按判定结果拆分为独立统计对象，不按 SPF/DKIM/DMARC/PTR 整体聚合）：
  SPF：硬拒绝（fail）、软拒绝（softfail）、未维护（none）、查询失败（temperror）、SPF 记录错误（permerror）
  DKIM：fail、neutral、partial、none、temperror
  DMARC：reject、quarantine、none、no_record、query_fail
  PTR：noptr、nomatch、ehlo_mismatch
```

每条规则至少按 `rule_id`、`version_id` 和 `effective_at` 过滤。页面按协议 Tab 汇总时，只能对同一协议下各判定结果的当前版本结果求和用于展示，汇总值不产生新的版本，也不得把不同判定结果的历史版本数据混入当前汇总。

### 2.8.2 观察模式统计口径

规则启用观察模式后，规则效能统计默认只统计当前版本：

$$观察时长 = 当前时间 - 当前版本的 observed_since$$

$$观察策略数 = count(status = observing \land version = current)$$

当前版本的命中数、投递、隔离、审核、拒收、丢弃、召回以及误判/漏判风险，只统计当前版本实际生效后的数据。规则版本切换前的数据必须留在旧版本中，不能并入新版本的 KPI、趋势或明细。

### 2.8.3 版本切换与统计重置

- 实质性修改导致旧版本变为 `superseded`，新版本变为 `observing`，统计起点重置为新版本的 `effective_at`。
- 非实质性修改不创建新版本，不重置观察时间、命中数或效能统计。
- 观察模式关闭后，当前版本不再计入“观察策略数”，但历史观察结果仍可查看。
- 规则转正后状态变为 `active`，当前版本仍继续作为当前效能统计对象。
- 规则停用或删除后不计入当前策略数，但旧版本只读保留。

### 2.8.4 页面展示要求

格式检查、协议检查下的每条规则都维护各自独立的版本链，页面顶部（KPI 卡上方筛选栏）**不得**提供以版本号为选项的全局“策略效能版本”选择器——同一个版本号在不同规则之间没有可比性，全局选择器会让用户误以为一次选择能覆盖所有规则。

版本查看入口下沉到明细列表的**行级**，每条规则各自维护自己的版本入口：

- 明细表格每一行（对应一条格式规则或一个协议类型）在规则名称旁展示“当前 v{N}”标签和状态，仅代表该行自身。
- 每一行提供“版本历史”入口，点击后仅展开或弹出该规则自身的历史版本（版本号、生效时间段、命中数、处置结果分布、变更摘要），不影响其他规则的行，也不影响页面顶部 KPI。
- KPI 卡始终按“各规则自身的当前有效版本”聚合，不随任何一行的历史版本查看而变化。
- 历史版本必须明确标注“历史版本”标识、版本号和统计时间范围，与当前版本区分，且不进入当前 KPI 和当前明细列表的汇总口径。

### 2.8.5 关联接口建议

```ts
AuthSpoofingEffectivenessQuery {
  rule_id:
    | 'mailfrom_empty' | 'mailfrom_invalid' | 'envelope_header_mismatch'
    | 'spf_fail' | 'spf_softfail' | 'spf_none' | 'spf_temperror' | 'spf_permerror'
    | 'dkim_fail' | 'dkim_neutral' | 'dkim_partial' | 'dkim_none' | 'dkim_temperror'
    | 'dmarc_reject' | 'dmarc_quarantine' | 'dmarc_none' | 'dmarc_no_record' | 'dmarc_query_fail'
    | 'ptr_noptr' | 'ptr_nomatch' | 'ptr_ehlo_mismatch';
  version_id?: string;
  status?: 'observing' | 'active' | 'superseded' | 'disabled' | 'deleted';
  include_history?: boolean;
}
```

`rule_id` 不接受 `'spf'`、`'dkim'`、`'dmarc'`、`'ptr'` 这种协议整体标识；协议 Tab 的汇总视图由前端对同一协议下各判定结果的查询结果求和得到，不作为单独的 `rule_id` 传给接口。默认 `include_history = false`，只返回当前有效版本；查看历史必须显式指定版本，防止旧版本与当前版本被误合并。

## 2.9 当前实现映射与验收标准

| 需求 | 当前实现 |
|---|---|
| 格式规则独立版本 | `FormatChecksSection.tsx` 按规则键展示版本历史入口 |
| 三条格式规则版本 | `mailfrom_empty`、`mailfrom_invalid`、`envelope_header_mismatch` 各自维护 `version` 与 `history` |
| 协议判定结果规则独立版本 | `ProtocolChecksSection.tsx` 按 SPF、DKIM、DMARC、PTR Tab 分组展示，Tab 内每个判定结果行各自展示版本历史入口 |
| 协议版本数据按判定结果键控 | `ProtocolChecksConfig.rule_versions`、`rule_history`、观察字段均以 `{protocol}_{result}` 为键 |
| 页面级历史移除 | `AuthSpoofingPage.tsx` 不再展示统一页面版本历史 |
| mock 保存逻辑 | `fixtures.ts` 只为实际变更的规则递增版本 |

验收标准：

- AC-11：空 MAIL FROM、无效 MAIL FROM、信封与头部不匹配拥有独立版本链。
- AC-12：SPF、DKIM、DMARC、PTR 各自的每个判定结果（如 SPF 的硬拒绝、软拒绝、未维护、查询失败、SPF 记录错误）分别拥有独立版本链，版本归属单位是“协议 + 判定结果”，不是协议整体。
- AC-13：修改一条规则不会递增其他规则版本。
- AC-14：页面不展示统一页面级版本历史模块。
- AC-15：每条规则历史仅展示自身记录，包含配置快照和变更摘要。
- AC-16：观察模式关闭后仍可查看当前版本和历史，且不显示“观察中”。
- AC-17：一次修改多条规则不生成批量变更记录。
- AC-18：规则效能统计默认只统计当前有效观察版本。
- AC-19：实质性变更后，新版本从实际生效时间开始统计，旧版本不并入当前 KPI。
- AC-20：非实质性变更不创建新版本，也不重置观察时间和效能统计起点。
- AC-21：查看历史版本时，页面明确展示版本号、状态和统计时间范围。
- AC-22：文档明确列出各策略模块的实质性变更字段和非实质性变更字段。
- AC-23：实质性字段变化创建新版本，非实质性字段变化不创建新版本。
- AC-24：关闭观察模式的单独操作不创建新版本；与实质性字段同时变化时按实质性变更处理。
- AC-25：相似邮件检测在聚合模式下按一条 `aggregate` 版本链统计，方向开关变化会创建聚合新版本。
- AC-26：相似邮件检测在按方向独立模式下分别维护接收、外发、域内版本，修改一个方向不影响其他方向。
- AC-27：聚合模式与按方向独立模式互切时创建新版本，切换前统计不得复制或跨模式合并。
- AC-28：相似度阈值、匹配算法、时间窗口、处置动作和例外范围等字段属于实质性变更；名称、描述、备注和页面查看状态属于非实质性变更。
- AC-29：规则效能统计页面顶部筛选栏不展示以版本号为选项的全局“策略效能版本”选择器。
- AC-30：明细表格每一行独立展示“当前 v{N}”标签和“版本历史”入口，仅作用于该行自身，不影响其他行。
- AC-31：任一行展开或查看版本历史后，页面顶部 KPI 卡数值保持不变，不随该行的历史版本切换而重新计算。
- AC-32：策略编辑页面（相似检测、身份认证与仿冒检测）不展示版本号、版本历史入口，版本维护统一收敛在规则效能统计页面。
- AC-33：协议检查的版本、观察信息和历史记录按“协议 + 判定结果”键控（如 `spf_fail`、`spf_softfail`、`dkim_neutral`、`dmarc_no_record`、`ptr_ehlo_mismatch`），不得按 SPF、DKIM、DMARC、PTR 协议整体键控；修改某一判定结果的处置动作不影响同协议下其他判定结果的版本。
- AC-34：规则效能统计接口的 `rule_id` 取值只包含具体协议判定结果标识，不接受 `'spf'`、`'dkim'`、`'dmarc'`、`'ptr'` 这类协议整体标识；协议 Tab 的汇总数值由前端对同协议下各判定结果的当前版本结果求和得到。

# 三、钓鱼邮件智能体模块

## 3.1 模块范围与规则归属

钓鱼邮件智能体（Agent Center，路由 `/agent-center/overview?agent=phishing&tab=config`）包含三个独立的配置版本域，各自维护自己的版本链，彼此不共享版本号：

| 版本域 | 归属单位 | 版本字段 |
|---|---|---|
| 准入规则（Admission Rules） | 每条规则（`rule_uid`/`id`）各自独立版本链 | `revision` |
| 风险处置策略（`risk_policy`） | 分档阈值与四个风险等级处置作为一份整体配置，一条版本链 | `risk_policy.version` |
| 运行时策略（`runtime_policy`） | 运行模式与超时相关配置作为一份整体配置，一条版本链 | `runtime_policy.version` |
| 分析引擎配置（`analysis_config`） | 网盘相关识别开关作为一份整体配置，一条版本链 | `analysis_config.version` |

版本归属原则：

- 准入规则的版本归属单位是“规则”，风险处置策略、运行时策略、分析引擎配置的版本归属单位是“策略文档整体”，不按其内部字段（如某个风险等级或某个超时参数）拆分子版本。
- 上述四个版本域彼此独立：修改准入规则不影响风险处置策略、运行时策略或分析引擎配置的版本；修改风险处置策略不影响运行时策略或分析引擎配置的版本，反之亦然。
- 风险处置策略与运行时策略当前在同一个编辑面板（Sheet）中一起提交，但服务端以两个独立的 `expected_version` 分别做乐观锁校验，因此即使同一次提交，也必须分别判断、分别递增。
- 智能体整体启用/停用状态（`PhishAgentControl.revision`）是控制平面的乐观锁版本号，不代表业务规则版本，不纳入规则效能统计口径，也不与上述四个版本域共享编号。
- 页面顶部或智能体总览不生成汇总版本号。

## 3.2 钓鱼邮件智能体字段变更分类

#### 实质性字段

以下字段任一发生变化，均创建对应版本域的新版本，并从新版本生效时间重新统计规则效能：

准入规则（按每条规则独立判断）：

- `enabled`（规则启用/停用）。
- `directions`（生效方向：接收、外发、域内）。
- `recipient_groups`、`recipient_depts`、`recipient_emails`、`sender_groups`、`sender_depts`、`sender_emails`（作用范围）。
- `filter_on`、`require_url`、`max_size_mb`、`sender_first_seen`、`require_qrcode`、`require_executable`（准入判定条件）。

风险处置策略（`risk_policy`，整体一条版本链）：

- `cutoffs`（置信度分档阈值 low/medium/high）。
- 任一风险等级的 `base_disposition`（proceed/audit/quarantine/discard）。
- 任一风险等级的 `mark_positions`、`mark_text`（标记位置与标记文案）。

运行时策略（`runtime_policy`，整体一条版本链）：

- `run_mode`（realtime/observe）。
- `observe_action`、`observe_mark_enabled`。
- `timeout_minutes`、`max_recheck_minutes`、`timeout_async_enabled`。

分析引擎配置（`analysis_config`，整体一条版本链）：

- `netdisk_domain`、`netdisk_extract`、`netdisk_spoof`。

#### 非实质性字段

以下字段变化不创建新版本，不重置观察周期或效能统计：

- 准入规则名称、复制生成的规则副本命名后缀。
- 页面搜索关键字、列表排序、Tab 切换。
- 查看历史记录、展开/收起、导出等只读交互。
- 变更原因、工单号等审计补充信息。

智能体整体启用/停用（`PhishAgentControl`）改变的是控制平面运行状态，不是某条规则或某个策略文档的业务配置，因此不创建风险处置策略、运行时策略、分析引擎配置或任何准入规则的新版本；但会影响“观察策略数”等运行中指标是否计入当前统计（见 3.7、3.9.2）。

## 3.3 功能概述与非目标

功能目标：

- 为准入规则集合中的每条规则、风险处置策略、运行时策略、分析引擎配置分别提供当前版本、历史版本、观察信息和配置快照，且四个版本域彼此独立。
- 规则效能统计页面能够按上述版本域分别归属统计数据，不把不同版本域或不同规则的数据混合汇总。

非目标：

- 不改变准入规则、风险处置策略、运行时策略或分析引擎配置现有的校验规则和保存流程。
- 不改变 `PhishAgentControl` 控制平面的启用/停用流程和 `expected_revision` 乐观锁机制。
- 不新增智能体类型或页面导航结构。
- 不在页面中实现服务端持久化；正式版本存储由后端接口负责。

## 3.4 页面信息架构

```text
钓鱼邮件智能体（Agent Center）
├─ 总览 Tab（观察数据展示，不维护版本）
└─ 配置 Tab
   ├─ 准入规则
   │  ├─ 规则 A   当前版本 / 查看版本历史
   │  ├─ 规则 B   当前版本 / 查看版本历史
   │  └─ ...      各规则各自独立
   ├─ 风险处置策略（分档阈值 + 四个风险等级处置）  当前版本 / 查看版本历史（整体一份）
   ├─ 运行时策略（运行模式、超时设置）             当前版本 / 查看版本历史（整体一份，与风险处置策略独立）
   └─ 分析引擎配置（网盘相关识别开关）             当前版本 / 查看版本历史（整体一份，与前两者独立）
```

风险处置策略与运行时策略当前合并在同一个编辑面板中展示和提交，但版本入口、当前版本号和历史记录必须分别独立展示，不得合并为一个版本号。

## 3.5 核心交互与版本递增

- 新增、编辑、复制或删除一条准入规则时，仅该规则的版本（`revision`）发生变化，不影响其他准入规则、风险处置策略、运行时策略或分析引擎配置的版本。
- 编辑风险处置策略字段（`cutoffs` 或任一风险等级的处置动作/标记设置）时，`risk_policy.version` 递增；若本次编辑只涉及运行时策略字段，`risk_policy.version` 保持不变。
- 编辑运行时策略字段（`run_mode`、超时时间、自动放行相关字段）时，`runtime_policy.version` 递增；若本次编辑只涉及风险处置策略字段，`runtime_policy.version` 保持不变。
- 同一次提交中风险处置策略和运行时策略字段同时发生变化时，两个版本域分别独立递增；服务端可能返回“发布中”状态（`isPublicationPendingResponse`），前端据此分别推进两个版本号，不得只推进一个而遗漏另一个。
- 编辑分析引擎配置（网盘域名/取链/仿冒识别开关）时，仅 `analysis_config.version` 递增，不影响准入规则、风险处置策略或运行时策略版本。
- 保存失败或版本冲突（HTTP 409，`config_version_conflict`）时，不得更新前端显示的版本号；必须保留用户已编辑内容，并提示重新加载最新版本或合并。
- 仅打开/关闭编辑面板、查看历史、切换 Tab、搜索或排序不创建任何版本域的新版本。

## 3.6 数据模型与接口契约

准入规则（版本归属到规则本身）：

```ts
PhishAdmissionRule {
  id?: number;
  rule_uid?: string;
  revision?: string; // 规则自身的乐观锁版本标识
  enabled: boolean;
  directions: Array<'inbound' | 'outbound' | 'internal'>;
  // ...其余准入判定字段
}
```

风险处置策略与运行时策略（版本归属到策略文档整体）：

```ts
PhishAgentConfig {
  risk_policy: PhishRiskPolicy & { version: number; updated_at: string };
  runtime_policy: PhishRuntimePolicy & { version: number; updated_at: string };
}

PhishAgentConfigPutRequest {
  risk_policy: PhishRiskPolicy & { expected_version: number };
  runtime_policy: PhishRuntimePolicy & { expected_version: number };
}
```

分析引擎配置（版本归属到策略文档整体）：

```ts
PhishAnalysisConfig {
  netdisk_domain: boolean;
  netdisk_extract: boolean;
  netdisk_spoof: boolean;
  version: number;
  updated_at: string;
}
```

正式引入版本历史查看能力时，三类版本域均应补充历史快照结构，字段至少包含：版本号、创建时间、观察开始时间、观察时长、版本期间命中数、变更摘要和不可变配置快照，命名与相似检测、身份认证与仿冒检测模块的历史快照结构保持一致，便于规则效能统计页面统一渲染行级版本入口。

## 3.7 观察模式语义

钓鱼邮件智能体的观察语义由 `runtime_policy.run_mode` 决定：

- `run_mode = realtime`：规则按实时处置结果生效，不属于观察模式。
- `run_mode = observe`：规则处于观察模式，命中后按 `observe_action` 处理，页面展示当前运行时策略版本、观察开始时间、观察时长和命中数。
- 观察模式关闭（切换为 `realtime`）时，保留当前运行时策略版本和历史版本，状态文案改为规则生效但不再显示“观察中”；上一次观察周期作为历史信息保留。
- 智能体整体停用（`PhishAgentControl.enabled = false`）时，仍展示最后生效的风险处置策略、运行时策略和分析引擎配置版本，但不计入“观察策略数”等运行中指标；历史观察周期仍可追溯。
- 仅切换 `run_mode` 或仅停用智能体本身不创建风险处置策略或分析引擎配置的新版本；只有配套的实质性字段发生变化时才创建新版本。

## 3.8 异常与边界场景

| 场景 | 处理要求 |
|---|---|
| 某条准入规则没有历史 | 该规则历史入口显示空状态，不影响其他规则 |
| 风险处置策略与运行时策略同一次保存 | 分别判断、分别递增版本；发布中状态需分别推进两个版本号 |
| 保存版本冲突（409） | 保留用户编辑内容，提示重新加载最新版本或合并，不静默覆盖 |
| 分析引擎配置保存失败 | 不更新前端显示的 `analysis_config.version` |
| 智能体整体停用 | 保留三类版本域的最后生效版本和历史，不清空数据 |
| 准入规则被删除 | 该规则不再出现在当前列表，但历史统计数据可按 `rule_uid` 追溯保留 |
| 权限不足 | 按现有权限体系（`usePhishingAccess`）展示只读或禁止编辑状态 |
| 后端未返回版本字段 | 使用默认版本展示，保存成功后按返回数据补齐版本 |

## 3.9 关联功能模块：规则效能统计

钓鱼邮件智能体接入规则效能统计页面时，必须遵循与相似检测、身份认证与仿冒检测相同的统计隔离原则。

### 3.9.1 统计对象

钓鱼邮件智能体的统计对象按版本域拆分为三类，互不合并：

```text
钓鱼邮件智能体
├─ 准入规则（按 rule_uid 逐条统计，每条规则各自的当前版本）
├─ 风险处置策略（整体一条版本链，按 risk_policy.version 统计）
└─ 运行时策略（整体一条版本链，按 runtime_policy.version 统计；决定是否处于观察模式）
```

分析引擎配置（`analysis_config`）不直接产生命中或处置结果，不作为规则效能统计对象；如后续需要统计其影响，应作为单独指标呈现，不得并入准入规则或风险处置策略的命中口径。

### 3.9.2 观察模式统计口径

仅当 `runtime_policy.run_mode = observe` 时，规则效能统计纳入“观察策略数”：

$$观察时长 = 当前时间 - runtime\_policy 当前版本的观察开始时间$$

$$观察策略数 = count(run\_mode = observe \land version = current)$$

当前版本的命中数、处置结果分布，只统计对应版本域生效之后产生的数据；版本切换前的数据归入旧版本，不回填新版本。

### 3.9.3 页面展示要求

规则效能统计页面顶部（KPI 卡上方筛选栏）**不得**为钓鱼邮件智能体提供以版本号为选项的全局选择器，理由与相似检测、身份认证与仿冒检测模块一致：准入规则、风险处置策略、运行时策略三个版本域的版本号互相独立，全局选择器会让用户误判筛选范围。

版本查看入口下沉到明细列表的行级：

- 每条准入规则单独一行，展示“当前 v{N}”标签和“版本历史”入口，仅作用于该行自身。
- 风险处置策略作为一行，展示其自身的“当前 v{N}”标签和“版本历史”入口。
- 运行时策略作为另一行，展示其自身的“当前 v{N}”标签和“版本历史”入口，与风险处置策略行互不影响。
- KPI 卡始终按三类版本域各自的当前有效版本聚合，不随任一行的历史版本查看而变化。

### 3.9.4 统计隔离原则

- 准入规则之间不共享版本号或效能统计；风险处置策略与运行时策略也不共享版本号，即使二者在编辑面板中合并展示。
- 分析引擎配置不纳入命中类效能统计。
- 智能体整体启用/停用状态变化不创建风险处置策略、运行时策略或分析引擎配置的新版本，但会影响“观察策略数”等运行中指标是否计入当前统计。
- 非实质性变更（如规则名称、页面筛选、历史查看）不创建新版本，不重置统计起点。

### 3.9.5 关联接口建议

```ts
PhishingEffectivenessQuery {
  domain: 'admission_rule' | 'risk_policy' | 'runtime_policy';
  rule_uid?: string; // domain = 'admission_rule' 时必填
  version_id?: string;
  status?: 'observing' | 'active' | 'superseded' | 'disabled' | 'deleted';
  include_history?: boolean;
}
```

`domain = 'admission_rule'` 时必须携带 `rule_uid` 以定位具体规则；`domain = 'risk_policy'` 或 `'runtime_policy'` 时按策略文档整体查询，不接受额外的字段级拆分参数。默认 `include_history = false`，只返回当前有效版本；查看历史必须显式指定版本，避免旧版本与当前版本被误合并。

## 3.10 当前实现映射与验收标准

| 需求 | 当前实现 |
|---|---|
| 准入规则独立版本 | `AdmissionRulesSection.tsx`、`phishing-admission-rules.ts`；每条规则通过 `rule_uid`/`revision` 独立标识 |
| 风险处置策略独立版本 | `RuntimeRiskSection.tsx`、`phishing-config.ts`；`risk_policy.version` 独立递增 |
| 运行时策略独立版本 | `RuntimeRiskSection.tsx`、`phishing-config.ts`；`runtime_policy.version` 独立递增，与 `risk_policy.version` 互不影响 |
| 发布中状态的双版本推进 | `runtime-risk-section.tsx` 中 `isPublicationPendingResponse` 分支分别推进 `risk_policy.version` 与 `runtime_policy.version` |
| 分析引擎配置独立版本 | `phishing-analysis-config.ts`；`analysis_config.version` 独立递增 |
| 智能体控制平面版本 | `phishing-control.ts`；`PhishAgentControl.revision` 属于控制平面乐观锁，不代表业务规则版本 |

验收标准：

- AC-35：钓鱼邮件智能体的准入规则集合中，每条规则各自维护独立版本标识（`revision`），修改一条规则不影响其他规则。
- AC-36：风险处置策略（`risk_policy`）与运行时策略（`runtime_policy`）分别维护独立的 `version`，即使在同一编辑面板中一起提交，也分别独立判断是否递增。
- AC-37：同一次保存中风险处置策略和运行时策略字段同时变化时，两个版本号分别递增；服务端返回发布中状态时，前端必须分别推进两个版本号，不得遗漏其中一个。
- AC-38：分析引擎配置（`analysis_config`）维护独立版本，不与准入规则、风险处置策略或运行时策略共享版本号。
- AC-39：智能体整体启用/停用状态变化（`PhishAgentControl`）不创建风险处置策略、运行时策略或分析引擎配置的新版本。
- AC-40：规则效能统计页面顶部筛选栏不为钓鱼邮件智能体提供以版本号为选项的全局选择器；版本查看入口下沉到准入规则、风险处置策略、运行时策略各自的行级入口。
- AC-41：仅当 `runtime_policy.run_mode = observe` 时，钓鱼邮件智能体的规则计入“观察策略数”等观察态指标；切换为 `realtime` 或智能体整体停用后不计入，但历史观察数据仍可追溯。
- AC-42：保存版本冲突（HTTP 409，`config_version_conflict`）时，保留用户编辑内容，不静默覆盖，并提示重新加载或合并。

## 4. 国际化与字符编码要求

- 所有用户可见文案必须通过项目国际化框架提供。
- 中文资源必须使用 UTF-8 编码。
- 禁止在中文页面和中文资源中出现 Unicode 替换字符（U+FFFD）。
- 禁止新增异常全角问号字符；正常疑问句不应使用异常替换符号。
- 相似检测相关中文文案变更后，必须同步检查 `messages/zh.json` 的 JSON 格式。
- 英文、俄文和泰文资源应同步提供对应 key，避免语言回退造成页面显示异常。
