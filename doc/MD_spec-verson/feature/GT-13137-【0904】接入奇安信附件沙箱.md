# GT-13137 【0904】接入奇安信附件沙箱

## 1. 需求背景

附件安全检测长期将反病毒引擎、图片识别、加密附件识别等子引擎与结构性限制（附件数量、大小、嵌套层数等）合并归入同一个"附件安全检测"模块进行判定与展示，管理员难以从处置依据、检测流程等结果页面上分辨命中的是附件安全检测下的哪一类具体策略。本需求在附件安全检测能力体系下，新增"附件沙箱检测"子引擎，对接奇安信附件沙箱，将可疑附件送入沙箱环境动态执行分析，按行为风险等级或分析超时结果分别给出处置动作，并让沙箱命中结果在处置依据、检测流程、事后处置时间线等结果展示场景中具备独立、可追溯的归属标签。

## 2. 需求目标

- 新增"附件沙箱检测"规则模块，支持按方向、文件类型/自定义扩展名命中后送入沙箱动态分析。
- 支持低危、中危、高危三档风险等级分别配置执行动作（隔离/审核/丢弃）与附件附加策略（标记/丢弃附件/不设置），标记附加策略下可组合选择标记生效位置。
- 支持沙箱分析超时或引擎不可用场景下的处置：召回、通知管理员、通知收件人，三者可任意组合勾选。
- 新增平台级沙箱检测配置：最大分析文件大小、分析超时阈值，统一作用于云网关及多租户产品形态。
- 在检测流程"阶段3"中将附件安全检测由单一合并判定拆分为"基础限制/反病毒引擎/附件沙箱/图片识别/加密附件"五个独立子项，父项状态由子项聚合，附件沙箱子项新增"超时"专属状态。
- 在处置依据卡片与详情页中为附件安全检测的各子引擎（含附件沙箱）补充"附件安全检测 › 子引擎名"两级归属标签，同时不改变现有按子引擎独立筛选的能力。
- 沙箱超时且规则超时配置勾选"召回"时，在事后处置时间线中补充一条召回执行记录，区分成功与失败两种执行结果。
- 全部新增文案复用项目现有国际化框架（`next-intl`），覆盖中/英/泰/俄四语言。

## 3. 最终实现方案（按功能点细化）

本章按 5 个功能点逐一展开，每个功能点均包含：功能概述、界面布局设计、交互设计、异常场景罗列、关联功能模块五个维度。以下内容均严格对照已落地的前端源码（`src/types/attachment-security.ts`、`SandboxRuleDrawer.tsx`、`SandboxRulesTab.tsx`、`SandboxPlatformPanel.tsx`、`use-detection-stages.ts`、`analysis-section.tsx`、`disposal-basis-config.ts`、`fixtures.ts`）编写，未实现的能力在对应小节中明确标注为"待办/未实现"，不做虚构。

### 3.1 功能点一：附件沙箱检测规则管理

#### 3.1.1 功能概述

**背景与目标**：附件安全检测此前仅有反病毒、图片识别、加密附件、基础限制四类静态规则引擎，均基于特征库或结构性阈值做判定，无法识别通过特征混淆的新型恶意附件（如免杀样本、无特征宏病毒）。本功能引入奇安信附件沙箱能力，将命中规则的附件送入隔离环境动态执行，依据其真实行为（进程创建、网络外联、注册表写入等）产出风险等级，弥补静态特征检测的盲区。目标是让管理员能够按方向、文件类型自主定义"哪些附件需要送检"，并按沙箱产出的风险等级差异化配置处置动作。

**功能点清单（逐条 + 实现逻辑）**：

1. **规则数据模型 `SandboxRule`**（`src/types/attachment-security.ts`）：以规则为最小配置单元，一条规则内聚检测范围、文件类型、三档风险处置、超时处置四组参数，多条规则可并存，按 `created_at` 升序排列；一个附件命中的**第一条已启用规则**生效，不做多规则叠加匹配（与现有反病毒/图片识别等模块保持一致的"首条命中即生效"语义）。
2. **检测范围多选** `direction: Direction[]`：支持接收 / 外发 / 域内三个方向任意组合勾选，UI 层强制至少保留一项（`toggleDirection` 在仅剩一项时禁止再取消）。
3. **文件类型识别范围** `file_type_categories` + `custom_extensions`：预置三类分类（`office`/`script`/`exec`，各自展开为具体扩展名清单只读展示，不可单独勾选子项），叠加自定义扩展名输入（必须以 `.` 开头，且不可与已有值重复）；两者合计至少选择一项。
4. **三档风险处置** `risk_actions.{low,medium,high}`：每档风险独立配置执行动作 `action`（隔离 `quarantine` / 审核 `audit` / 丢弃 `discard` / 不设置 `none`）与附件附加策略 `attachment_policy`（标记 `mark` / 丢弃附件 `discard` / 不设置 `none`），二者不可同时为 `none`；附加策略选择"标记"时进一步展开标记生效位置 `mark_locations`（主题 `subject` / 邮件头 `header` / 正文起始 `body_start`，可多选，允许为空）。
5. **超时处置** `timeout.actions`：召回 `recall`、通知管理员 `notify_admin`、通知收件人 `notify_recipient` 三个动作可任意组合勾选，至少选一项；勾选"通知管理员"时展开管理员邮箱 `admin_email` 输入框并做必填 + 格式校验。
6. **规则 CRUD 与状态管理**：新建、编辑（复用同一抽屉表单，通过传入 `rule` 是否为 `null` 区分标题与提交动作）、按名称/方向/文件类型关键字模糊搜索（前端本地过滤，不发起新请求）、Switch 单条启停、删除前二次确认。

**关键业务逻辑与数据流转**：
- 列表页 `SandboxRulesTab` 挂载时调用 `listSandboxRules()` → `GET /attachment-security/sandbox-rules`，返回结果按 `created_at` 升序排序后存入本地 state；后续搜索仅在已加载数据上做前端过滤，不重新请求接口。
- 新建/编辑保存调用 `createSandboxRule()`/`updateSandboxRule()` → `POST`/`PUT /attachment-security/sandbox-rules[/:id]`，成功后关闭抽屉并触发 `loadRules()` 重新拉取列表（不做本地乐观合并，以后端返回的完整列表为准）。
- 启停 Switch 采用**乐观更新**：先本地翻转 `enabled` 状态并立即渲染，再调用 `setSandboxRuleStatus()`；接口失败时回滚本地状态并弹出失败提示，不静默失败。
- 删除调用 `deleteSandboxRule()` 成功后关闭确认弹窗并重新拉取列表。

**用户角色与权限边界**：
- 沙箱规则挂载于附件安全检测页面，其可编辑性由既有的 `canEditSecurityModule()` 统一权限函数裁定（`src/lib/api/security-modules.ts`）：`tenant_admin` 角色始终具备编辑权限；`system_admin`（平台管理员）在"以租户身份查看"上下文（`viewer !== 'platform'` 或已选定具体租户）时按该函数的模块归属规则判定，附件安全检测属于**租户级模块**，不受"仅平台原生视角可编辑"的全局态限制。
- 页面组件通过 `SandboxRulesTab readOnly={!moduleEditable}` 传参控制：`readOnly=true` 时，新建按钮不渲染、编辑/删除按钮 `disabled`、启停 Switch `disabled`，仅保留列表查看与搜索能力，不存在"看得到但点击后台报错"的体验缺口。

#### 3.1.2 界面布局设计

**页面信息架构**：附件安全检测页面（`/security/pipeline?stage3=attachment`）沿用既有的横向页签结构，"沙箱检测"作为与"反病毒"/"图片识别"/"加密附件"/"基础限制"平级的新增页签，可通过 URL 参数 `stage3Tab=sandboxRules` 直达。页签内为"列表 + 抽屉"两层结构：主区域是规则列表页，新建/编辑通过右侧滑出的 Sheet 抽屉承载，不做页面跳转。

**原型/截图标注（区域说明）**：
- 列表页顶部：左侧为搜索输入框（含放大镜图标，`placeholder` 提示按名称搜索），右侧为"新建"按钮（`readOnly` 时不渲染）。
- 列表表格列：规则名称、状态（Switch + 徽标双重展示启用/停用）、检测范围（方向标签以 `/` 分隔）、文件类型（预置分类中文名 + 自定义扩展名以"、"拼接，超长时 `truncate` 省略并通过 `title` 属性展示完整内容）、操作（编辑/删除文字与图标按钮）。
- 列表底部：统计行"共 N 条规则，M 条已启用"。
- 抽屉表单自上而下四个编号分区（1 检测范围、2 文件类型、3 风险等级处置、4 超时处置），编号以圆形徽标 + 分区标题呈现，与项目其他规则抽屉（如钓鱼检测 admission-rules）的分区视觉语言保持一致。
- 风险等级处置区：低/中/高三个独立卡片，每卡片内左侧为等级标签，右侧为"执行动作"与"附加策略"两个下拉选择器；当附加策略为"标记"时，卡片下方追加一行标记位置的多选按钮组。
- 超时处置区：三个复选框纵向排列，"通知管理员"复选框勾选后在其下方缩进展示邮箱输入框。

**响应式/自适应规则**：抽屉宽度固定 `sm:max-w-[560px]`，移动端占满全屏；风险等级卡片内的"执行动作/附加策略"选择器在窄屏下由 `sm:flex-row` 降级为纵向堆叠（`flex-col`），避免横向拥挤。

**视觉一致性要求**：复用项目既有 `Sheet`/`Select`/`Checkbox`/`Switch`/`Badge` 组件与 design token（不引入新配色），分区编号徽标使用 `bg-primary/10 text-primary`，与其他抽屉编号分区（如内容规则、通知渠道）保持同一视觉规范；风险等级卡片使用标准 `rounded-lg border` 卡片样式，不额外引入阴影层级。

#### 3.1.3 交互设计

**主流程交互**：
- 点击"新建"打开空白抽屉（默认值：接收方向、低危审核+标记主题、中危隔离+标记主题与邮件头、高危丢弃+丢弃附件、超时通知管理员）；点击"编辑"打开抽屉并回填该条规则全部字段。
- 文件类型选择器为 Popover 弹层组件：点击触发器展开分类勾选清单，勾选分类后其扩展名清单只读展开供管理员核对范围，不可对子项单独反选；已选分类/自定义扩展名以标签形式回显在触发器内，标签自带删除按钮可单独移除。
- 自定义扩展名输入支持 Enter 键提交（已处理中文输入法组合态 `isComposing` 判断，避免拼音输入过程中误触发添加）。
- 风险等级"附加策略"从"标记"切换为其他选项时，立即清空该等级已选的标记位置，避免保存时残留无效数据。

**关键字段的鼠标 Hover 提示**：
- 已实现：列表"文件类型"列文本超长被截断时，通过 `title` 属性在鼠标悬浮时展示完整分类与扩展名清单，避免长文案挤占表格布局又丢失信息。
- 未实现（记录为后续优化项，不在本次范围内补齐）：抽屉内"执行动作"“附加策略”“标记位置”等下拉/按钮组当前仅有文字标签，未额外配置 Tooltip 悬浮说明；风险等级三档卡片标题当前也未附加"低危/中危/高危具体判定依据"的悬浮说明。若后续产品明确需要，建议在对应 `Label` 旁追加 `Tooltip` 组件，复用项目已有的 `@/components/ui/tooltip`。

**状态变化规则**：
- 加载态：列表初次加载展示两行 `Skeleton` 骨架屏，不展示空表格。
- 空态：规则总数为 0 时展示"暂无规则"文案；有规则但搜索关键字无匹配时展示"无匹配结果"文案，二者文案不同，避免管理员误以为规则被清空。
- 成功态：新建/编辑/删除成功均通过 `toast.success` 提示，不使用弹窗打断操作流。
- 失败态：接口失败统一通过 `toast.error` 提示（表单校验失败提示"validationFailed"，接口 400 校验错误展示后端返回的具体 `message`，其他失败展示通用失败文案），启停失败额外回滚本地 Switch 状态。

**批量操作与单条操作逻辑**：当前仅支持单条操作（单条启停、单条编辑、单条删除），**不支持批量启停/批量删除**；删除为高风险操作，单独走二次确认弹窗（`AlertDialog`），启停与编辑不需要二次确认。

**弹窗/抽屉触发条件**：
- 抽屉（Sheet）：点击"新建"或"编辑"触发，点击遮罩层/取消按钮/保存成功后关闭。
- 确认弹窗（AlertDialog）：仅"删除"操作触发，确认后调用接口，取消则不产生任何副作用。
- 不涉及独立页面跳转，全部在附件安全检测页面内完成。

#### 3.1.4 异常场景罗列

| 场景 | 处理方式 |
| --- | --- |
| 规则名称为空 | 阻止提交，提示"需要填写规则名称"，聚焦定位到名称输入框下方的错误文案 |
| 检测范围一项都未选 | UI 层已通过"仅剩一项时禁止取消"从交互上避免此状态出现；表单校验作为兜底仍会拦截 |
| 文件类型分类与自定义扩展名均为空 | 阻止提交，提示"需要选择文件类型或填写自定义扩展名" |
| 自定义扩展名不以 `.` 开头 | 阻止添加，提示"扩展名格式不正确"，不写入草稿状态 |
| 自定义扩展名重复添加 | 阻止添加，提示"扩展名已存在" |
| 某风险等级执行动作与附加策略同时选择"不设置" | 阻止提交，提示"需要配置风险处置动作"，需管理员至少设置动作或附加策略之一 |
| 超时动作一项都未勾选 | 阻止提交，提示"需要选择超时处置动作" |
| 勾选"通知管理员"但邮箱为空或格式非法 | 阻止提交，分别提示"需要填写管理员邮箱"/"邮箱格式不正确" |
| 权限不足（`readOnly=true`） | 新建按钮不渲染，编辑/删除/启停按钮均 `disabled`，不存在点击后再报错的体验，从入口层面阻断而非依赖接口 403 兜底 |
| 保存接口返回 400 校验错误 | 展示后端返回的具体错误文案（`isValidationError` 解析 `ApiError.status === 400`），不覆盖为通用失败文案，便于管理员定位后端侧的额外校验规则 |
| 保存/删除接口超时或 5xx | 统一走 `catch` 分支展示通用失败提示（保存失败/删除失败/加载失败），不做自动重试，需管理员手动重新触发操作 |
| 并发编辑冲突（两个管理员同时编辑同一条规则） | **当前未实现乐观锁/版本号校验**：后保存者会直接覆盖先保存者的内容，属于已知待办事项，不在本次范围内实现，建议后续补充 `updated_at` 版本比对或后端侧 ETag 机制 |
| 启停 Switch 点击后网络失败 | 本地状态先乐观翻转、接口失败后自动回滚为原状态并提示失败，避免 UI 与后端状态不一致 |

#### 3.1.5 关联功能模块

- **上游依赖**：
  - 权限判定依赖 `src/lib/api/security-modules.ts` 的 `canEditSecurityModule()` 统一函数，附件沙箱规则未定义独立权限口径，与反病毒/图片识别等子模块共用同一套租户/平台可编辑性判定逻辑。
  - 页面路由与页签框架依赖 `AttachmentSecurityPage.tsx` 已有的 Tab 容器与 URL 参数解析（`stage3`/`stage3Tab`）。
- **下游影响**：
  - 规则命中结果会写入邮件详情的处置依据（关联功能点四）与检测流程阶段3的附件沙箱子项状态（关联功能点三）。
  - 规则的超时处置配置（是否勾选 `recall`）决定该邮件是否会在事后处置时间线追加召回事件（关联功能点五）。
- **配置联动关系**：沙箱规则本身不设总开关，是否生效取决于规则是否 `enabled`；沙箱送检的文件大小与超时阈值不在规则级配置，而由功能点二的平台级配置统一约束，两者是"规则决定检测范围与处置方式，平台配置决定检测边界"的分层关系，互不覆盖。
- **接口与数据表关联**：前端对接 `GET/POST/PUT/DELETE /attachment-security/sandbox-rules[/:id]` 与 `PUT /attachment-security/sandbox-rules/:id/status` 五个端点，镜像钓鱼检测模块 admission-rules 的独立规则表设计（区别于反病毒/图片识别等走 `/config-overrides` 单节键值配置的模式），对应后端应有独立的沙箱规则数据表，而非复用 `attachd.cf` 配置节表。

### 3.2 功能点二：平台级沙箱检测配置

#### 3.2.1 功能概述

**背景与目标**：沙箱动态分析是有成本、有边界的计算资源（分析耗时、并发队列、存储开销），需要一个统一的"检测边界"配置，与规则级的"检测范围/处置方式"配置解耦，避免每条规则重复定义相同的资源上限，也避免不同租户各自设置导致沙箱资源争用不可控。目标是提供一个全局唯一的沙箱资源边界配置入口。

**功能点清单**：
1. **最大分析文件大小** `max_file_size_mb`：超过该大小的附件不送入沙箱分析（数字输入框，单位 MB，最小值 1）。
2. **分析超时时长** `analysis_timeout_seconds`：沙箱单次动态分析的最长等待时间（数字输入框，单位秒，最小值 1），超时后触发规则级的超时处置动作（回退到功能点一的 `timeout.actions`）。

**关键业务逻辑与数据流转**：配置读取调用 `getPlatformSandboxPolicy()` → `GET /config-overrides?config_file=attachd.cf&section_name=sandbox_platform`，保存调用 `savePlatformSandboxPolicy()` → 对该配置节逐键 `PUT`（已存在）或 `POST`（新增），复用项目现有的 `fetchConfigSection`/`saveConfigSection` 通用键值配置读写机制，未新增专属接口。该配置节全局唯一，不含租户维度字段，与"沙箱规则"（功能点一，走独立规则表）在存储层完全分离。

**用户角色与权限边界**：`SandboxPlatformPanel` 挂载于"平台安全策略"页面（`PlatformSecurityPage.tsx`），该页面本身是平台级配置页，不像附件安全检测页面那样区分租户/平台视角；组件通过 `disabled={loading || sandboxSaving}` 仅在数据加载或保存进行中临时禁用输入，不存在按角色隐藏该配置区的逻辑——即能进入"平台安全策略"页面的管理员即具备编辑该配置的权限，权限边界由页面级路由/菜单可见性统一控制，不在组件内重复判定。

#### 3.2.2 界面布局设计

**页面信息架构**：作为"平台安全策略"页面内与反病毒引擎配置区（`AntivirusEnginePanel`）平级的一个独立卡片分区，页面内多个 `<section>` 纵向堆叠排列，不做页签分割。

**响应式/自适应规则**：两列网格在窄屏（低于 `md` 断点）降级为单列纵向堆叠。

**视觉一致性要求**：与页面内其他配置卡片统一使用 `rounded-lg border bg-card p-5` 卡片样式，标题字号、输入框尺寸与同页面其他分区保持一致，不引入独立视觉风格。

#### 3.2.3 交互设计

**主流程交互**：管理员直接在数字输入框中修改数值，父组件 `PlatformSecurityPage` 统一管理草稿状态与保存按钮，本卡片本身不含独立的保存按钮（复用页面级统一保存入口）。

**状态变化规则**：`disabled` 态仅体现为输入框置灰不可交互，无独立的加载骨架屏（沿用页面级统一的加载态）。

**批量/单条操作逻辑**：不适用（本功能点为单一配置项编辑，非列表型操作）。

**弹窗/跳转触发条件**：无弹窗、无抽屉、无跳转，输入即时反映到页面级草稿状态，随页面统一保存动作一并提交。

#### 3.2.4 异常场景罗列

### 3.3 功能点三：检测流程"阶段3"附件安全检测子引擎拆分

#### 3.3.1 功能概述

**背景与目标**：邮件详情页"检测流程"的阶段3此前将附件安全检测作为单一叶子节点合并展示反病毒、图片识别、加密附件、基础限制、（新增）沙箱五类判定结果，管理员无法从检测流程视图直接分辨具体命中的是哪一类子引擎，需要额外跳转处置依据才能确认，排查效率低。目标是将阶段3的附件安全检测由"单一判定项"重构为"分组节点 + 五个独立子项"，并让附件沙箱子项具备区别于"可疑/通过"的独立"超时"状态，因为"分析超时"在安全语义上是"未知风险"而非"低风险通过"，不应与"过检测但未见异常"混同展示。

**功能点清单**：
1. **阶段3分组重构**：附件安全检测由叶子判定项改为分组节点，下辖 `attachment_basic_limit`（基础限制）、`attachment_antivirus`（反病毒引擎）、`attachment_sandbox`（附件沙箱检测）、`attachment_image_detect`（图片识别）、`attachment_encrypted`（加密附件）五个独立子项，对应五个独立 page key。
2. **父项状态聚合**：父项（附件安全检测）状态由五个子项按 `threat > timeout > suspicious > pass > skipped` 优先级聚合得出——只要任一子项为 `threat`，父项即为 `threat`；无 `threat` 但有子项为 `timeout`，父项为 `timeout`；以此类推。
3. **附件沙箱专属超时判定**：新增专属判定函数，读取 `MailLogDetail.sandbox_timeout` 字段，在"未命中沙箱高危行为规则"但"检测确实超时"时返回独立的 `timeout` 状态（`CheckStatus` 枚举新增该值），区别于宽泛的"可疑"（`suspicious`，通常表示命中低/中危规则）或"通过"（`pass`）。
4. **嵌套渲染**：`analysis-section.tsx` 检测项渲染逻辑扩展为支持父子两级嵌套，父项默认展开，子项在父项容器内以浅底浅边框的子分组容器呈现。

**关键业务逻辑与数据流转**：检测流程数据来源于邮件详情 `MailLogDetail` 中各子引擎命中的 page key 集合与 `sandbox_timeout` 布尔标记，由 `use-detection-stages.ts` 在前端聚合计算出每个子项与父项的 `CheckStatus`，不发起额外接口请求，属于对已获取的邮件详情数据的前端二次计算与展示重组。

**用户角色与权限边界**：检测流程为只读展示区域，不存在编辑操作，因此不涉及角色权限差异化控制；任何能够查看该邮件详情的角色（受邮件详情页本身的租户数据隔离与查看权限控制）均看到相同的阶段3子引擎拆分结果。

#### 3.3.2 界面布局设计

**页面信息架构**：位于邮件详情页"检测流程"卡片内，阶段3（"附件安全检测"）作为五个检测阶段中的一环，本次改动仅影响阶段3内部结构，不影响阶段1/2/4/5及阶段间的横向排列关系。

**原型/截图标注**：
- 父项行：图标（依据聚合后的 `CheckStatus` 显示对应色彩的状态图标）+ "附件安全检测"标题 + 状态徽标，默认展开状态。
- 子项区：父项下方以整体缩进的浅底浅边框容器包裹五个子项，每个子项行同样为"状态图标 + 子引擎中文名 + 状态徽标"的横向排列，视觉层级明显弱于父项（字号/字重降一级），让管理员一眼区分"总体结论"与"逐项明细"。
- 附件沙箱子项在 `timeout` 状态下使用独立的状态图标与徽标文案（区别于 `threat`/`suspicious`/`pass`），需与其他四个子引擎共用的状态图标集保持同一套图标语言，仅状态文案与色彩不同。

**响应式/自适应规则**：子分组容器随父容器宽度自适应，不设独立断点；窄屏下子项行的图标、标题、徽标沿用父项行同样的换行/截断规则。

**视觉一致性要求**：子分组容器复用项目既有"卡片嵌套"视觉惯例（浅背景 + 浅边框），不新增颜色 token 或阴影层级，与检测流程其他阶段的既有视觉语言保持统一。

#### 3.3.3 交互设计

**主流程交互**：父项默认展开显示全部五个子项，不提供折叠/收起父项的能力（区别于其他可能存在折叠交互的分组，本次未引入折叠状态，保持默认全展开的只读浏览体验）。

**关键字段 Hover 提示**：**当前子项状态徽标未配置悬浮说明**（例如"超时"状态未提供"沙箱分析在平台设定的超时阈值内未返回结果"这类解释性 Tooltip），管理员需结合处置依据卡片（功能点四）获取更详细的命中说明。建议后续在状态徽标上补充简要 Tooltip，指向对应处置依据卡片作为详情入口。

**状态变化规则**：五种子项状态（`threat`/`timeout`/`suspicious`/`pass`/`skipped`）与父项聚合状态共用同一套状态图标 + 色彩语义，`timeout` 使用区别于 `threat`（高危红）与 `suspicious`（警示黄）的独立视觉标识（新增枚举值，非复用现有色阶）。

**批量/单条操作逻辑**：不适用（纯展示，无操作）。

**弹窗/跳转触发条件**：本区域自身不触发任何弹窗或跳转；子项状态与下方处置依据卡片、事后处置时间线共享同一份邮件详情数据，形成"检测流程给结论 → 处置依据给命中详情 → 事后处置时间线给执行记录"的三层递进阅读路径，但检测流程区域本身没有点击跳转能力。

#### 3.3.4 异常场景罗列

| 场景 | 处理方式 |
| --- | --- |
| 邮件未命中附件沙箱规则且未超时 | 该子项显示 `pass`（通过）或 `skipped`（未检测，如该邮件无附件），与其他子项判定逻辑一致 |
| `sandbox_timeout` 为 `true` 但同时命中了高危行为规则 | 判定函数优先级需明确：**当前实现中"未命中高危行为规则"是进入 `timeout` 判定的前提条件**，若已命中高危行为则走 `threat` 判定路径，不会被超时状态掩盖真实的高危结论——即"检出高危"优先于"检测超时"展示，避免超时误导管理员低估风险 |
| 五个子项中出现多个不同状态（如反病毒为 `pass`、沙箱为 `timeout`） | 按既定优先级 `threat > timeout > suspicious > pass > skipped` 聚合父项状态，不会因为多数子项为 `pass` 而"稀释"高优先级异常状态 |
| 邮件详情接口返回的 page key 集合缺失某个子引擎数据 | 前端聚合逻辑对缺失数据的子项按 `skipped`（未检测）兜底展示，不会因缺字段抛出渲染异常 |
| 并发场景（同一邮件被多个管理员同时查看） | 检测流程为只读展示，天然不存在并发写冲突问题 |

#### 3.3.5 关联功能模块

- **上游依赖**：依赖邮件详情接口返回的 `MailLogDetail.sandbox_timeout` 字段与各子引擎命中的 page key 数据；page key 的产生依赖后端 milter 侧对沙箱检测结果的实际标记（前端仅做展示层聚合，不产生检测结论）。
- **下游影响**：阶段3拆分后的子项归属直接服务于功能点四的"处置依据两级归属标签"展示一致性——两处需保持同一套子引擎命名与分类口径，避免检测流程显示"附件沙箱检测"而处置依据显示别的名称造成管理员困惑。
- **配置联动关系**：子项是否出现 `timeout` 状态，最终由功能点二的平台级 `analysis_timeout_seconds` 配置与功能点一规则的实际执行耗时共同决定，前端展示层不参与该判定的产生过程，仅消费后端/mock 数据中已确定的 `sandbox_timeout` 布尔值。
- **接口与数据表关联**：不新增接口，复用既有的邮件详情查询接口返回的字段；`use-detection-stages.ts` 中的分组与判定逻辑属于前端纯计算，无对应数据表。

### 3.4 功能点四：处置依据"附件安全检测 › 子引擎"归属标签

#### 3.4.1 功能概述

**背景与目标**：处置依据（Disposal Basis）卡片是管理员判断"这封邮件为什么被这样处置"的核心信息来源，此前各子引擎的处置依据条目彼此独立展示，缺少统一的父级归属，管理员難以一眼看出"反病毒""附件沙箱""图片识别""加密附件"这几类命中项其实都属于"附件安全检测"这一个更大的能力域。目标是在不改变现有"按子引擎独立筛选"能力的前提下，为这些子引擎的处置依据补充统一的父级分组标签，并新增附件沙箱专属的处置依据条目与"查看规则"路由跳转。

**功能点清单**：
1. **父级分组字段** `moduleGroupZh/En/Th/Ru`：为反病毒、附件沙箱、图片识别、加密附件、基础限制五个子引擎的处置依据元数据（`PolicyMeta`）补充统一取值"附件安全检测"（及对应多语言译文）的父级分组字段，与各自独立的 `moduleZh`（如"附件沙箱检测"）分离存储，互不覆盖。
2. **两级归属展示**：处置依据卡片与详情页依据 `moduleGroupZh` 是否存在，渲染"附件安全检测 › 附件沙箱检测"两级面包屑样式展示；未填写 `moduleGroup*` 的其他既有模块不受影响，仍展示单级模块名。
3. **新增 `ATT-SANDBOX` 处置依据条目**：覆盖两类命中场景的多语言文案——"沙箱分析超时（按规则配置隔离），安全性未知"、"沙箱动态分析检出高危行为，附带行为描述与风险等级"。
4. **`POLICY_ROUTE_OVERRIDE` 路由覆盖映射**：使 `ATT-SANDBOX` 处置依据卡片上的"查看规则"入口不走默认的阶段路由，而是直达附件安全检测抽屉的"沙箱检测"页签（`/security/pipeline?stage3=attachment&stage3Tab=sandboxRules`），管理员可从处置依据一键跳转到命中规则的配置入口。

**关键业务逻辑与数据流转**：处置依据条目的匹配基于邮件详情中记录的 `policy_key`（如 `ATT-SANDBOX`），在 `disposal-basis-config.ts` 的静态映射表中查表得到对应的展示文案、父级分组、跳转路由，属于纯前端静态配置匹配，不涉及额外接口调用。多语言文案根据当前 `locale` 选择对应的 `moduleGroupZh/En/Th/Ru` 字段渲染。

**用户角色与权限边界**：处置依据为只读展示信息，任何有权限查看该邮件详情的角色均看到相同内容；"查看规则"跳转链接指向附件安全检测页面，若目标角色对该页面本身无编辑权限，跳转后仍受功能点一所述的 `readOnly` 权限收敛（能看规则列表但不能编辑），不存在越权配置的风险。

#### 3.4.2 界面布局设计

**页面信息架构**：处置依据信息分布在两个场景——邮件详情"威胁概览"卡片（`threat-summary-card.tsx`）的精简展示与"检测流程"区域（`analysis-section.tsx`）的详细展示，本次改动同步覆盖两处渲染点，保持信息口径一致。

**原型/截图标注**：
- 面包屑样式：父级分组文字（灰色、较小字号）+ 分隔符"›"+ 子引擎名称（正常字号），整体作为处置依据条目标题行的前缀或副标题呈现，不额外占用独立行高。
- "查看规则"入口：以文字链接形式紧邻处置依据描述文案展示，点击后在新的浏览上下文跳转到目标路由（非弹窗，非当前页面替换式跳转的具体形式取决于既有实现的路由跳转方式，本次未改动跳转的呈现形式，仅改动了目标 URL）。

**响应式/自适应规则**：面包屑文字在窄屏下与既有处置依据文案共用相同的换行/截断规则，未额外定义断点。

**视觉一致性要求**：父级分组文字颜色/字号复用项目既有的"次要信息"文字样式（如 `text-muted-foreground text-xs`），不引入新的强调色，确保父级标签在视觉权重上明显低于子引擎名称本身，避免喧宾夺主。

#### 3.4.3 交互设计

**主流程交互**：管理员在邮件详情页浏览处置依据卡片时自然看到两级归属标签，无需额外点击展开；点击"查看规则"文字链接跳转到对应配置页面。

**关键字段 Hover 提示**：**当前两级归属标签本身未配置额外的 Hover 提示**（面包屑文字即完整信息，不存在截断场景，因此暂不需要 Tooltip 补充）；"查看规则"链接的可点击性通过链接下划线/颜色的标准视觉语言表达，未额外附加悬浮说明文案，符合项目其他"查看规则"入口的既有交互习惯（未特殊化处理）。

**状态变化规则**：处置依据卡片本身为静态展示，不存在加载/成功/失败状态变化；仅在邮件详情整体加载完成后一次性渲染。

**批量/单条操作逻辑**：不适用（单条邮件详情的只读展示，不支持批量操作）。

**弹窗/跳转触发条件**：仅"查看规则"链接触发路由跳转，跳转目标由 `POLICY_ROUTE_OVERRIDE` 映射表按 `policy_key` 精确匹配决定；未在映射表中显式声明的 `policy_key` 走默认的 `STAGE_ROUTE` 阶段路由回退逻辑，不会出现跳转目标为空的情况。

### 3.5 功能点五：沙箱超时召回 → 事后处置时间线记录

#### 3.5.1 功能概述

**背景与目标**：邮件详情页"事后处置时间线"记录的是系统针对该邮件实际执行过的处置动作序列（隔离、旁路、审核、退信等），此前缺少"沙箱超时后触发召回"这一执行事实的记录入口，导致管理员即便知道规则配置了"超时后召回"，也无法在时间线上确认该动作是否真的被执行、执行结果是成功还是失败。目标是在满足触发条件时，于事后处置时间线中补充一条可追溯的召回执行记录。

**功能点清单**：
1. **触发条件判定**：仅当该邮件 `sandbox_timeout === true`（功能点三判定出的超时事实）**且**该邮件命中的沙箱规则的超时处置配置 `timeout.actions` 包含 `recall`（功能点一的规则配置）时，才追加该记录；两个条件缺一不出现，避免"配置了召回但其实没超时"或"超时了但规则没配召回"这两类误报场景。
2. **数据字段扩展**：`MailLogDetail` 新增可选字段 `sandbox_recall_result?: 'success' | 'failed'`，作为该邮件是否触发召回及执行结果的落地字段。
3. **事件记录生成**：满足触发条件时，事后处置时间线追加一条 `event_source: 'workflow.sandbox_recall'`、`event_type` 为"附件沙箱超时召回"、`event_result` 取值为 `sandbox_recall_result`（`success`/`failed`）的事件记录。
4. **成功/失败两种结果均支持展示**：`success` 表示召回执行成功，`failed` 表示召回执行失败（如收件人已读取/邮件已被转发等召回失效场景），时间线上以不同的结果徽标区分。

**关键业务逻辑与数据流转**：`event_source: 'workflow.sandbox_recall'` 与既有 `workflow.quarantine`/`workflow.sideline`/`workflow.audit`/`workflow.bounce` 同属一个来源命名体系，天然落入 `analysis-section.tsx` 现有"非 `postfix` 来源即归入事后处置时间线"的过滤逻辑（`events.filter((ev) => ev.event_source !== 'postfix')`），因此**未改动任何时间线渲染代码**，新事件通过既有渲染路径自动展示，仅在事件生成层（mock 数据层，对应后端应为实际的召回执行记录写入逻辑）新增该事件的产生条件。

**用户角色与权限边界**：事后处置时间线为只读展示，任何有权限查看该邮件详情的角色看到相同的时间线记录，不涉及角色差异化的可见性控制。

#### 3.5.2 界面布局设计

**页面信息架构**：事后处置时间线作为邮件详情页的既有区域，本次改动仅在其事件列表中插入一条新记录，不改变该区域整体的卡片位置、标题、事件总数徽标等外层结构。

**原型/截图标注**：
- 事件条目标题行：`{event_source} · {event_type}`，即"workflow.sandbox_recall · 附件沙箱超时召回"，与既有 `workflow.quarantine` 等条目采用完全相同的标题拼接格式，不做特殊化处理。
- 结果徽标：紧邻标题展示 `event_result`（`success`/`failed`），复用既有事件结果徽标的成功/失败双色语义。
- 展开详情：点击/展开该条目后展示"召回动作""执行结果"等字段（复用既有事件详情展示字段的既定映射方式），不新增专属的详情字段展示组件。
- **说明**：此前一轮迭代中已移除该事件详情区域内的"查看召回日志"按钮（因当前无对应的日志详情页可跳转，避免出现"点击后无实际内容"的死链接体验），本次记录该按钮已不存在，避免后续误以为遗漏。

**响应式/自适应规则**：与既有事后处置时间线其他事件条目共用同一套响应式规则，未单独定义。

**视觉一致性要求**：新事件的标题、徽标、展开详情的视觉样式与既有 `workflow.*` 事件完全一致，不引入新的图标、颜色或卡片样式，确保管理员浏览时间线时不会因样式突变而产生"这是不同类型事件"的错误感知。

#### 3.5.3 交互设计

**主流程交互**：管理员浏览邮件详情页时，若该邮件命中触发条件，会在事后处置时间线中看到该条记录按 `event_time` 排入正确的时间顺序位置（不是固定排在最前或最后），点击/展开后查看具体的召回动作与执行结果字段。

**关键字段 Hover 提示**：`event_source` 标题行当前展示原始技术标识符（如 `workflow.sandbox_recall`），**未做中文化 Hover 说明**，这与其他既有 `workflow.*` 事件的展示方式完全一致（现状本身就是裸显示技术标识符，非本次新引入的问题），因此不在本次范围内改动；若后续产品统一决定为所有 `workflow.*` 事件补充 Hover 中文说明，应作为跨事件类型的统一改造，而非仅针对本条新事件单独处理。

**状态变化规则**：事件的 `event_result` 直接决定结果徽标的成功/失败展示，无中间的"处理中"过渡态（召回结果在 mock 数据层已是确定值；对应真实后端场景下，若召回为异步执行，则应在召回真正完成前不生成该事件记录，或补充"处理中"的第三态，这属于后端联调阶段需要明确的语义，本次前端实现未预留"处理中"态的展示分支）。

**批量/单条操作逻辑**：不适用（单条邮件详情的时间线展示，无批量操作）。

**弹窗/跳转触发条件**：本条新增记录不触发任何弹窗或跳转（原有的"查看召回日志"跳转按钮已在前序迭代中移除）。

#### 3.5.4 异常场景罗列

| 场景 | 处理方式 |
| --- | --- |
| `sandbox_timeout === true` 但规则超时配置未勾选 `recall` | 不生成该记录，时间线保持原有事件序列不变（已通过 mock 反例邮件验证） |
| `sandbox_timeout` 为 `false`（未超时） | 不生成该记录，无论规则是否配置了 `recall`（超时是硬性前提条件） |
| 召回执行失败（`sandbox_recall_result: 'failed'`） | 正常生成记录，结果徽标展示失败态，管理员可据此判断需要人工介入处理（如手动联系收件人删除邮件） |
| 事件生成的时间戳早于该邮件的检测/接收时间 | mock 数据层已保证 `event_time` 晚于检测发生时间点，前端渲染依赖数据层保证的时间先后关系，自身不做时间校验兜底 |
| 并发场景（理论上同一封邮件不应触发两次召回） | 当前实现为静态数据展示，字段为单值（非数组），天然不支持同一邮件出现多条召回记录；若后端真实场景存在"召回重试"多次执行的情况，需扩展该字段为事件数组，属于后续需要与后端联调确认的数据结构演进点，本次未预留该扩展 |

#### 3.5.5 关联功能模块

- **上游依赖**：直接依赖功能点三的 `sandbox_timeout` 判定结果与功能点一规则配置的 `timeout.actions` 是否包含 `recall`，两者均已在前序功能点中落地。
- **下游影响**：本功能点是当前"附件沙箱对接"整条链路里最末端的展示环节，不再向其他前端模块传递数据。
- **配置联动关系**：管理员在功能点一的规则抽屉中调整某条规则的超时处置勾选项（增加或移除 `recall`），会直接影响该规则下未来命中邮件是否会在时间线出现该记录；但**对已产生的历史邮件记录不做回溯性变更**（历史事件是产生时的快照，不会随规则配置事后调整而改变已展示内容），这与事后处置时间线"记录历史事实"的语义定位一致。
- **接口与数据表关联**：前端字段为 `MailLogDetail.sandbox_recall_result`，事件写入 mock 层的 `mockEmailDisposalEvents()` 生成逻辑；对应真实后端应在召回执行完成后，将执行结果同步落库到邮件的处置事件表（与其他 `workflow.*` 事件共用同一张事件流水表），而非另起专属表。
