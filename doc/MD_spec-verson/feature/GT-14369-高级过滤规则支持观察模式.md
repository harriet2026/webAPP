# GT-14369 高级过滤规则支持观察模式

## 1. 需求背景

高级过滤规则模块（`AdvancedFilterRulesModule`，安全策略流水线第五阶段）的规则一旦启用（`is_active`），即会按其配置的条件组合与优先级立即执行对应的处置动作（放行/标记放行/隔离/审核/丢弃）。由于该模块支持极其灵活的条件组合（54 种条件项、任意嵌套的条件树），用户在新建规则或调整已有规则的条件组合时，比发信人黑白名单、发信行为管控、内容规则等结构更简单的模块更容易因条件配置不准确而误伤正常邮件或漏拦异常邮件，也更缺少一种"先观察命中情况、再正式生效"的过渡验证手段。

本需求在高级过滤规则模块新增"观察模式"能力：规则开启观察模式后仅记录命中日志，不实际执行规则动作，帮助用户在正式启用前验证规则的影响范围。该能力与"发信人黑白名单"（GT-14265）、"发信行为管控"（GT-14367）、"内容规则"（GT-14368）已落地的观察模式保持一致的交互范式和数据口径。

高级过滤规则模块的规则列表与规则状态切换当前通过真实后端接口（`listAdvancedRules`/`toggleAdvancedRule`）读写，与前述三个模块（读写落在前端 mock 状态）不同。本需求延续既有前端交付原则：`observe_mode` 字段暂无后端承载能力，因此其读写在前端本地 mock 状态中完成，不进入 `listAdvancedRules`/`toggleAdvancedRule`/规则新建保存等真实网络请求，不涉及后端接口改造。

## 2. 需求目标

- 在规则编辑器抽屉（`RuleEditorDrawer`）的"基础设置"标签页（`BasicSettingsTab`），增加观察模式的启用/禁用开关。
- 在规则列表新增"观察模式"表头字段，并支持直接在列表中启用/禁用。
- 观察模式状态与规则的启用/禁用状态（`is_active`）互相独立，两者可分别控制，互不联动、互不重置。
- 复用项目现有国际化框架和 `Switch` 组件形态，不引入新的交互范式。
- 规则效能统计模块补充高级过滤规则的效能数据口径，且效能明细"前往策略配置"可跳转定位到该模块下具体规则的编辑抽屉。
- 不修改高级过滤规则之外的其他功能模块（不含第 7 章记录的关联模块配套变更）。

## 3. 最终实现方案

### 3.1 数据模型

- `RuleWithExtras`（`src/lib/api/advanced-rules.ts`，包装 `Rule` 类型）新增前端专用的只读字段 `observe_mode?: boolean`；该字段不在 `listAdvancedRules` 返回的原始接口响应体中，由 `AdvancedFilterRulesModule` 在渲染 `listItems` 时按规则 `id` 从本地 mock 态注入（`observe_mode: observeModeById[r.id] ?? false`）。
- `RuleForm`（`src/lib/api/rule-form.ts`，`RuleEditorDrawer` 内部表单态）新增可选字段 `observeMode?: boolean`，供"基础设置"标签页读写；该字段不随 `createAdvancedRule`/`updateAdvancedRule` 的请求体一起提交给后端。
- `AdvancedFilterRulesModule` 内新增本地状态 `const [observeModeById, setObserveModeById] = useState<Record<number, boolean>>({})`，作为观察模式状态的唯一前端存储；组件卸载或页面刷新后该状态重置为空（等价于全部规则观察模式关闭），这是本次纯前端 mock 交付的已知边界，与后端持久化后的行为存在差异，待后端接口补齐后需要迁移为真实持久化字段。

### 3.2 规则编辑器抽屉——基础设置标签页（操作级说明）

- **打开抽屉**：用户在规则列表点击"新建规则"（`rules-new-btn`）或某一行的"编辑"操作（`rule-row-edit-${rule.id}`），`RuleEditorDrawer` 以 `open=true` 展开，默认停留在"基础设置"标签页（`basic-settings-tab`）。
- **字段位置与结构**：在"基础设置"标签页的"有效期设置"分组（`basic.sectionValidity`，含 `basic-valid-until` 字段）下方新增一个独立分组"观察模式"（新增 i18n 键 `basic.sectionObserveMode`），结构为：分组标题 + 字段标签 `observeMode` + 帮助文案 `observeModeHint`（沿用内容规则模块的展示方式：标签右侧直接展示帮助文案，不使用 Tooltip）+ 右侧 `Switch` 组件（`data-testid="basic-observe-mode"`）+ Switch 右侧的状态文案（复用 `common.enabled`/`common.disabled`）。
- **默认值填充（新建场景）**：
  1. 用户点击"新建规则"，`AdvancedFilterRulesModule.handleNew` 将 `editingRule` 置为 `null`，`editorOpen` 置为 `true`。
  2. `RuleEditorDrawer` 检测到 `rule` 为 `null`，以空白态初始化 `RuleForm`，`observeMode` 字段默认值为 `false`（关闭）。
  3. 观察模式 Switch 渲染为"关闭"态，右侧状态文案显示"禁用"。
- **回填（编辑场景）**：
  1. 用户点击某一行的"编辑"，或通过效能明细/处置中心携带的 `rule_id` 深链自动定位到该规则的编辑抽屉（见 7.1.1 节）。
  2. `AdvancedFilterRulesModule.handleEdit(rule)` 被调用，其中传入的 `rule` 对象已在 `listItems` 组装阶段携带 `observe_mode` 字段（取自 `observeModeById[rule.id]`，未记录过则为 `false`）。
  3. `RuleEditorDrawer` 依据传入 `rule.observe_mode` 初始化表单的 `observeMode` 字段，观察模式 Switch 按该值渲染为开启或关闭态，右侧状态文案同步显示"启用"或"禁用"。
- **交互——切换开关**：
  1. 用户点击观察模式 Switch。
  2. Switch 视觉状态立即切换（开启 ↔ 关闭），右侧状态文案同步切换为"启用"/"禁用"。
  3. 表单内部字段 `form.observeMode` 的值随之更新（`setForm((f) => ({ ...f, observeMode: v }))`），但不触发提交，也不影响表单内其他标签页（条件树、动作配置、测试分析）以及基础设置内其他字段（名称、优先级、状态、生效范围、有效期、备注）的值。
- **交互——保存**：
  1. 用户点击抽屉底部的"保存"按钮，`RuleEditorDrawer` 先按现有校验规则（名称必填、生效范围必填、优先级范围校验等）完整性检查表单。
  2. 校验通过后，`RuleEditorDrawer` 对后端字段（名称、条件树、动作、优先级、生效范围、有效期、备注等）发起 `createAdvancedRule`/`updateAdvancedRule` 真实网络请求；请求体不包含 `observeMode`。
  3. 请求成功后，`RuleEditorDrawer` 在其 `onSaved` 回调中额外传出本次保存时的 `observeMode` 取值与规则 `id`（新建场景取后端返回的新规则 `id`）。
  4. `AdvancedFilterRulesModule.handleEditorSaved` 依据回调参数更新本地 `observeModeById[savedId] = observeMode`，随后仍按既有逻辑触发 `queryClient.invalidateQueries({ queryKey: rulesQueryKey })` 刷新规则列表。
  5. 抽屉关闭，规则列表对应行（新建则新增一行）重新拉取后按最新的 `observeModeById` 状态渲染观察模式列。

### 3.3 规则列表——观察模式列（操作级说明）

- **列位置**：在规则列表表头新增"观察模式"列（新增 i18n 键 `observeMode`），位于现有"状态"列（`status`，对应 `is_active` 的 Switch）右侧、"处置方式"列（`action`）左侧，列宽 `w-[100px]`，与"状态"列一致；表格 `colSpan` 从 9 调整为 10。
- **单元格渲染**：
  1. 页面渲染规则列表时，每一行按 `rule.observe_mode`（`listItems` 组装阶段注入）渲染观察模式列的 `Switch` 组件：`true` 渲染为开启态，`false` 渲染为关闭态。
  2. Switch 的 `data-testid` 为 `rule-row-observe-${rule.id}`，`aria-label` 使用国际化的"启用观察模式"/"禁用观察模式"文案，保证屏幕阅读器可读。
- **交互——列表内直接切换**：
  1. 用户点击某一行观察模式列的 Switch。
  2. Switch 视觉状态立即切换（开启 ↔ 关闭）。
  3. 该操作调用 `AdvancedFilterRulesModule.handleToggleObserve(rule.id, nextValue)`，仅更新本地 `observeModeById` 状态中对应 `id` 的值，不调用 `toggleAdvancedRule`、不发起任何网络请求、不触发 `queryClient.invalidateQueries`。
  4. 同一行的其余字段（条件、优先级、`is_active`、处置方式、有效期等）保持不变，不重新拉取整张列表。
  5. 操作不需要二次确认，不弹出额外的保存/取消对话框（即时生效于本地 mock 状态）。
- **与其他列的独立性**：切换"观察模式"列不影响"状态"列（`is_active`，绑定 `toggleAdvancedRule` 真实接口）的显示与取值，两者在同一行内并存、互不联动；反之，切换"状态"列触发的 `toggleMutation` 与列表刷新，也不会重置该行本地维护的观察模式取值（`observeModeById` 独立于 `rulesQueryKey` 的查询缓存）。
- **筛选与分页的兼容**：观察模式状态不参与现有的搜索（`search`）、状态筛选（`statusFilter`）、生效范围筛选（`scopeFilter`）与分页（`pageSize`/`currentPage`）逻辑，`filterRules`/切片计算保持不变，仅在单元格渲染时额外读取 `observe_mode`。

### 3.4 国际化

- 在 `advancedRulesFeature` 命名空间下新增 `observeMode`（"观察模式"）、`observeModeHint`（帮助文案，与内容规则同义："启用后规则仅记录命中情况，不实际执行动作，用于验证规则效果"）、`basic.sectionObserveMode`（"观察模式"分组标题）三个键；Switch 状态文案复用已有的 `common.enabled`/`common.disabled` 键，不新增重复的语义键。
- 中文资源使用 UTF-8 编码，不引入 Unicode replacement character 或异常全角问号字符。
- 同步在英文、俄文、泰文资源文件补齐对应翻译，保持四语言 key 集合一致。

### 3.5 Mock 数据与测试

- 前端本地 mock 状态（`observeModeById`）无需额外的 mock 数据文件支撑，组件初始为空对象即代表全部规则观察模式默认关闭；如需要联调时预置若干条规则为"已开启"状态，可在开发环境通过手动切换列表 Switch 达成，不新增专门的 seed 数据。
- 新增/更新单元测试覆盖：
  - `RuleEditorDrawer.test.tsx`（或新建 `BasicSettingsTab.test.tsx`）：新建场景默认关闭、编辑场景按传入 `rule.observe_mode` 回填、切换开关不影响其他字段、保存回调携带 `observeMode`。
  - `AdvancedFilterRulesModule.test.tsx`（如无则新建）：列表渲染观察模式列、`handleToggleObserve` 仅更新本地状态且不触发网络请求、`handleEditorSaved` 正确写入 `observeModeById`。

## 7. 关联功能模块变更

### 7.1 规则效能统计——高级过滤规则效能口径

- **需求背景**：高级过滤规则支持观察模式后，需要在"规则效能统计"模块中看到该模块下规则的效能表现（命中量、动作分布、观察时长等），并支持从效能明细的"前往策略配置"跳转到高级过滤规则模块并自动定位到具体规则的编辑抽屉。
- **实现内容**：
  - `src/lib/api/rule-effectiveness-view.ts` 的 `PolicyModule` 类型新增 `'advanced_filter_rules'`。
  - `src/lib/mock/rule-effectiveness-prototype.ts` 补充该模块的 `CONFIG_PATH_BY_MODULE.advanced_filter_rules = '/security/pipeline?module=advancedRules'`，并为该模块下的效能明细行按具体规则拼接 `config_path = '/security/pipeline?module=advancedRules&rule_id=<该规则的数据库 id>'`；同时补充该模块的可执行动作口径（`accept`/`proceed`/`quarantine`/`audit`/`discard`，与 `ACTION_BADGE_CLASS` 保持一致的语义映射）与若干条示例效能明细行。
  - `src/components/statistics/rule-effectiveness/constants.ts` 的 `POLICY_MODULES` 新增 `advanced_filter_rules`，`MODULE_COLORS` 为其分配一个与现有六个模块（`auth_spoofing`/`similar_detection`/`phishing_detection`/`sender_filter`/`behavior_control`/`content_rules`）互不重复的专属配色，`resolveSubStrategyKeys`/`resolveSubStrategyLabel` 按需补充该模块的子策略解析分支（若该模块不存在子策略概念，则维持模块级展示，不强行拆分）。
- **涉及文件**：`src/lib/api/rule-effectiveness-view.ts`、`src/lib/mock/rule-effectiveness-prototype.ts`、`src/components/statistics/rule-effectiveness/constants.ts`。

#### 7.1.1 点击"前往策略配置"后的交互（操作级说明）

以下以高级过滤规则效能明细行为例，逐步说明点击操作按钮到落地具体规则编辑抽屉的完整链路：

1. **用户操作**：用户在"规则效能统计"页效能明细表某一条 `policy_module = 'advanced_filter_rules'` 的数据行上，点击"前往策略配置"操作按钮。
2. **触发回调**：`RuleEffectivenessPage.handleNavigateToConfig(row)` 被调用（复用现有逻辑，不新增分支）。
   - 若该行携带租户归属信息（`row.backend` 存在）且当前用户是系统管理员，先切换当前查看视角为该租户（`setViewer('tenant')`、`setSelectedTenant(row.backend.tenant_id)`）。
   - 取该行自带的 `row.config_path`（mock 数据中已按具体规则拼接为 `/security/pipeline?module=advancedRules&rule_id=<该规则的数据库 id>`）；若该字段为空则回退到模块级映射 `CONFIG_PATH_BY_MODULE.advanced_filter_rules`（`/security/pipeline?module=advancedRules`，不含 `rule_id`）。
   - 在取到的路径后追加查询参数 `source=rule_effectiveness`，得到最终跳转地址，例如 `/zh/security/pipeline?module=advancedRules&rule_id=1&source=rule_effectiveness`。
   - 调用 `router.push(...)` 完成页面跳转，浏览历史新增一条记录（用于后续"返回"操作回退）。
