4. 数据模型与 API 映射

type RuleType = "receive" | "send"
type MarkPosition = "subjectPrefix" | "bodyTop" | "header" | "multiple"
type MarkStyle = "blueTag" | "orangeWarning" | "plainText" | "custom"
type DisclaimerPosition = "bodyTop" | "bodyBottom" | "header" | "multiple"
type DisclaimerFormat = "auto" | "htmlOnly" | "plainOnly"

interface MarkingRule {
  id: string
  name: string
  type: RuleType            // 接收标记 / 外发声明
  priority: number          // 数字越小越优先（demo/PRD 语义，见 §10 Q1）
  enabled: boolean
  departments: string[]     // 适用部门 ID（接收=收信人维度，外发=发件人维度）
  groups: string[]          // 适用群组 ID；两者皆空 = 全部用户
  markText?: string         // 接收标记：文案，maxLength 50，支持变量
  markPosition?: MarkPosition
  markStyle?: MarkStyle
  customColors?: { bgColor: string; textColor: string; borderColor: string; borderRadius: number }
  disclaimerContent?: string   // 外发声明：内容，计数上限 10240 bytes（demo 按字符数计）
  disclaimerPosition?: DisclaimerPosition
  disclaimerFormat?: DisclaimerFormat
  createdAt: string
  updatedAt: string
}
PRD API / 数据表用途落地映射建议需确认
GET /api/mail-marking/rules规则列表（分页）映射统一规则系统列表接口，page=mail-marking，以 direction/type=receive|send 区分两个 Tab。统一规则的 payload 是否可承载 markStyle/customColors/disclaimerFormat 等扩展字段。
POST/PUT/DELETE /api/mail-marking/rules(/:id)规则增删改复用统一规则 CRUD；「标记」动作按 implement.md 映射为 accept + 添加特定 header，不新增 mark action。正文顶部/底部插入、主题前缀改写需要邮件体改写能力，是否超出现有 accept+header 组合（§10 Q2）。
POST /api/mail-marking/test模拟测试demo 为前端本地模拟（直接取第一条启用规则）；落地若要真实匹配需统一规则 dry-run 接口。是否新增 dry-run API（§10 Q7）。
部门/群组下拉数据源适用对象选择demo 用 mock（6 部门 4 群组）；落地对接网关组织架构/群组策略数据源（LDAP 联系人同步）。部门维度网关现有数据是否具备（§10 Q3）。
mail_marking_rules 表产品设计表非硬性要求；优先落到统一规则表 + page 字段，避免新建独立规则表。规则审计日志与配置回滚（PRD §6.3）沿用统一规则的变更记录。
