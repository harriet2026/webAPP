GT-12772 邮件处置中心-标准SMTP邮件召回失败仍提示成功且召回日志入口未实现问题解决

1. 事后处置时间线 — 事件来源白名单过滤

1.1 方案概述

问题根因原过滤逻辑为黑名单（仅排除 event_source === 'postfix'），导致 antispam（策略裁决）等投递流程事件穿透过滤，在时间线中出现；这类事件的 event_type 在映射表中缺失，进而以原始英文渲染，视觉上误导为"召回成功"
修复方案改为白名单：DISPOSAL_SOURCES = new Set(['admin_api', 'threat_retro_agent'])；过滤逻辑由 ev.event_source !== 'postfix' 改为 DISPOSAL_SOURCES.has(ev.event_source ?? '')
白名单枚举admin_api（管理员手动召回）　threat_retro_agent（威胁回溯智能体发起召回/通知）
排除的来源postfix（Postfix 投递状态）、antispam（策略裁决）及任何其他非处置来源
源码路径analysis-section.tsx 第 162 行 DISPOSAL_SOURCES 常量 + 第 262 行 disposalEvents useMemo
i18n 变化无（仅过滤逻辑，不影响文案）

2. 操作类型 — i18n 复合键映射

2.1 方案概述

问题根因详情展开后「操作类型」栏渲染 ev.event_type 原始英文（recall、notify 等），未经翻译
修复方案新增纯函数 getOperationTypeLabel(source, type, t)；以 "source:type" 复合键查 OPERATION_TYPE_KEY_MAP，再通过项目 i18n 框架 t() 读取中英文翻译；未命中 fallback 到 event_type 原始值
使用复合键原因admin_api:recall 与 threat_retro_agent:recall 的 event_type 同为 recall，单字段无法区分二者的业务语义
删除内容原 OPERATION_TYPE_ZH 硬编码映射表 + translateEventType() 函数（依赖 isZh 标志位）已删除；isZh 变量随之删除
源码路径analysis-section.tsx：OPERATION_TYPE_KEY_MAP 常量 + getOperationTypeLabel 函数
