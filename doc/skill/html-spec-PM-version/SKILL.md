## 文档命名与标识约定

文件名与文档内容名称**严格分离**，两者含义不同：

| 字段 | 含义 | 示例 |
|---|---|---|
| **文件名**（`GT-<N>.html`）| 本文档的 ticket 号，用于文件系统唯一标识 | `GT-126811.html` |
| **需求名称** | 文档内容所描述的需求或优化的业务名称 | `GT-12682-RBL优化` |

同一份文档可以收录多个需求（二级条目），文件名只对应文档本身的 ticket，不等于任何一个需求名称。

> **本技能服务的功能路径必须在调用时明确标注，以下为模板，使用时替换为实际路径。**

## 职责（增量模式）

本技能与全量版 `html-spec-generator` 共享所有规格质量要求（截图、元素粒度、禁止事项等），**唯一的区别在于操作范围**：

- **全量版**：以空白或整体重写的方式生成一个模块的完整规格。
- **本技能（增量版）**：以追加或局部替换的方式，**只描述本次新增或变更的功能片段**，不触碰已有规格中未发生变更的部分。

以 `webapp/` 中正在运行的页面为当前 UI 与可观察行为的事实源，将增量产物输出到：

```text
webapp/doc/html-spec/<模块名>/
```

增量内容按以下优先级选择载体：

1. 若变更属于已有模块 `index.html` 中的某个区域：在该区域内追加或替换对应的 `.interaction-preview` 节（保留区域外内容不变）。
2. 若变更是独立的新状态或新功能块，且主文件已较长：新增 `state-<N>-<描述>.html` 并在主文件目录中添加链接。
3. 若变更属于全新模块：创建新模块目录，走全量生成流程，但仅覆盖该新模块。

每次增量更新后必须：

- 在 `version.json` 中递增 `current_version` 并追加一条历史记录；
- 在历史记录的 `summary` 中清晰描述本次增量内容（"新增 X 功能状态截图"，不得写"增量更新"等无意义摘要）；
- 更新总索引 `index.html` 中该模块卡片的版本号和日期。

以下内容明确禁止（与全量版一致）：

- 从 webapp 提取 `outerHTML` 嵌入规格；
- 在规格中复制 React/Tailwind 业务组件；
- 为按钮、输入框、弹窗、表格等绑定模拟业务交互；
- 用内联 mock、状态机或脚本在规格中重演 webapp；
- 为复制出的组件做 DOM 树逐节点一致性校验；
- **借"增量"名义跳过浏览器验证或减少状态覆盖。**

> 本技能只生成规格，不修改 `webapp/src/`、后端实现、测试用例或原始需求文档，也不自动提交代码。

## 触发条件

用户提出以下请求时使用本技能：

- 为某个新增功能追加 HTML 规格说明；
- 某个页面或组件发生变更，需要更新对应规格中变更的部分；
- 生成版本增量 html_spec、增量规格、追加功能说明；
- 在 webapp 变化后同步已有 HTML 规格中受影响的部分（不全量重写）。

## 事实源与优先级

### 需求裁决顺序

1. 用户当前描述；
2. 当前上下文中可获得的、时间更晚且明确的用户决定；
3. webapp 当前运行态与源码；
4. 其他原始 spec，仅作非权威差异对照。

历史对话不可获得时，明确写"历史对话记录：当前上下文未提供"，不得虚构结论。

### 当前实现事实源

- 浏览器中实际运行的 webapp 是 UI、文案、布局、可见性、禁用态和交互结果的第一事实源。
- `webapp/src/` 是补充事实源，用于确认类型、状态管理、隐藏分支、i18n key、API 调用和浏览器无法直接观察的信息。
- 源码推断与浏览器结果冲突时，当前实现按浏览器结果记录，同时标注冲突。
- 用户目标与 webapp 当前状态冲突时，同时记录"目标要求"和"当前实现"，不得用当前实现覆盖目标。

## 核心产物规则

### 1. 截图式交互预览 + 对应信息

交互预览必须保留，但只能是只读的截图预览。每条关键交互用"触发前截图 → 操作说明 → 触发后截图/状态截图序列"表达；简单交互可以只展示结果态截图并引用前置状态。

每个重要页面状态都必须形成一组完整记录：

| 内容 | 要求 |
|---|---|
| 状态名称 | 明确说明默认态、打开态、选中态、错误态、空态等 |
| 触发路径 | 从哪个页面状态，经什么点击、输入、悬停或权限切换进入 |
| 浏览器截图 | 使用该状态的真实渲染截图，不使用手绘占位图 |
| 可见元素 | 文案、图标、位置、默认值、占位符、状态、禁用条件 |
| 交互结果 | 操作后页面发生什么变化、反馈是什么、如何恢复 |
| 数据/API | 相关字段、请求、响应映射；无法确认时标注待确认 |
| 权限差异 | 对应产品形态和角色下的可见、只读、隐藏情况 |
| 验证依据 | 浏览器操作、DOM/可访问性信息、源码路径或用户决定 |

截图不能替代文字信息，文字信息也不能替代截图。审查者应能从一组"截图 + 表格 + 说明"独立理解该状态。

交互预览的 HTML 容器使用 `.interaction-preview`，内部只放标题、触发路径、顺序编号、`figure/img/figcaption`、说明和表格。所有截图直接铺开显示，不使用轮播、折叠、热点点击或弹层查看。

### 2. 交互预览只使用截图

HTML 规格是只读文档，不是第二套 webapp。生成文件时：

- 不创建 `.component-preview`；
- 可以创建 `.interaction-preview`，但其中只能包含静态截图和对应信息；
- 不嵌入 webapp 组件 HTML/CSS；
- 不复制 Tailwind utility class 来还原业务组件；
- 不加入模拟业务行为的 `onclick`、表单状态或 mock API；
- 不要求在生成后的规格中点击、输入、排序、分页或开关弹窗；
- 不引用 Tailwind CDN；
- 不包含 `<button>`、`<input>`、`<select>`、`<textarea>`、`<form>`、`<details>`、`<summary>` 或 `<script>` 等可交互标签；
- 不保留 `onclick`、`onchange`、`onsubmit`、`addEventListener` 等事件绑定；
- 更新旧规格时直接删除旧组件 DOM、事件脚本、mock 数据和专用交互 CSS，不得仅用 `display:none` 隐藏。

交互必须在真实 webapp 中验证，然后用截图式交互预览和对应信息记录。截图中出现的按钮、输入框等只是像素，不是规格文档中的真实控件。

### 3. 交互预览状态覆盖

按实际功能选择并覆盖重要状态，至少检查：

- 默认态、加��态、空态、正常数据态；
- Hover、Focus、选中、禁用、只读；
- 校验失败、提交失败、权限不足、后端异常；
- 弹窗/抽屉打开态、表单联动态、确认态；
- 排序、分页、筛选、批量操作前后；
- 关键响应式断点；
- 主题、locale、产品形态和角色差异。

**增量版补充**：只需覆盖本次新增或变更功能涉及的状态；与本次变更无关的现有状态不重复截图，但若本次变更影响了某个已有状态，该状态必须重新截图并替换旧截图。

没有该状态或无法安全触发时，注明"不适用"或"无法验证"，不要伪造截图。

### 4. 产品形态 × 角色差异矩阵

页面级规格必须包含 `<section id="form-role-matrix">`，记录当前功能在各形态与角色下的可见性和可编辑性。

**增量版补充**：若已有矩阵存在，只追加或修改本次变更涉及的行/列，不重写未受影响的矩阵内容。

产品形态：

| 简称 | 全称 |
|---|---|
| AI-单 | AI版-单租户 |
| 传统-单 | 传统版-单租户 |
| 云-多 | 云网关-多租户 |
| AI-多 | AI版-多租户 |
| 传统-多 | 传统版-多租户 |

角色：

- 平台管理员；
- 租户管理员。

统一图例：

| 符号 | 含义 |
|---|---|
| ✅ | 显示且可编辑 |
| 🔒 | 显示但只读 |
| ❌ | 隐藏 |
| — | 该形态无此角色 |
| ? | 当前无法验证，必须列入待确认事项 |

每个组件和元素表增加"形态/角色差异"列。无差异时使用 `[Base]`；差异使用 `[Overlay]`、`[单租户]`、`[多租户]` 等标记。

### 5. 逐元素详细度

不要只写"有一个搜索框"。根据元素类型记录足够落地和验收的信息：

- 通用元素：类型、文案、图标、位置、尺寸、默认值、占位符、禁用条件、交互结果、i18n key；
- 输入控件：数据类型、必填、长度、格式、边界值、校验时机和错误文案；
- 表格：列序、列名、字段、宽度、对齐、排序、格式、空值、溢出、固定列；
- 弹窗/抽屉：触发条件、尺寸、标题、字段、按钮、关闭方式、遮罩和焦点行为；
- 状态反馈：loading、toast、错误、空态、重试、成功后刷新或跳转；
- 权限：入口可见性、只读/禁用条件、无权访问结果。

### 6. 输出目录

```text
webapp/doc/html-spec/
├── index.html                         # 总索引
├── assets/                            # 可选共享静态资源
└── <模块名>/
    ├── index.html                     # 模块主规格
    ├── version.json                   # 模块版本元数据
    ├── screenshots/
    │   ├── page-default.png
    │   ├── dialog-open.png
    │   └── validation-error.png
    └── state-<N>-<描述>.html          # 可选；状态很多且主文件过长时使用
```

**增量版规则**：

- 新增截图放入已有 `screenshots/` 目录，命名不与已有截图冲突；
- 不删除仍有效的旧截图；
- 不重命名已有 `state-*.html` 或 `layer-*.html` 文件（保持链接稳定）；
- 只在增量内容确实需要独立文件时才新建 `state-<N>-<描述>.html`。

通用规则（与全量版一致）：

- 根目录只放总索引和共享资源，不平铺模块主文件或截图；
- 优先在模块 `index.html` 中连续展示截图式交互预览；
- 主文件和状态子文件都用 `./screenshots/<文件名>` 引用截图。

### 7. 必备章节（增量模式）

增量更新时，**不重写已有章节**，只在对应章节的末尾追加"本次增量"小节，格式为：

```html
<section id="incremental-<ticket>-<简述>">
  <h3>增量：<ticket> <简述>（<日期>）</h3>
  <!-- 本次变更的截图式交互预览、元素说明、差异、待确认事项 -->
</section>
```

如果本次变更导致已有内容**失效**（例如移除了某功能），需在原有内容处添加删除线标注或 `<del>` 标记，并在增量小节中说明原因，不得静默删除已有内容。

完整页面级规格的必备章节列表（供新模块全量创建时参考）：

1. 元信息与事实源；
2. 产品形态 × 角色矩阵；
3. 组件/区域目录；
4. 功能概述；
5. 页面布局与默认态整页截图；
6. 逐组件/区域的截图式交互预览；
7. 弹窗、抽屉和关键状态截图；
8. 数据模型与 API 映射；
9. 业务逻辑与权限；
10. 交互结果与异常场景；
11. 国际化与响应式；
12. 关联功能模块；
13. 差异标注；
14. 需确认事项；
15. 版本历史。

组件级规格可以省略不适用的页面章节，但仍需包含事实源、状态截图、元素信息、交互结果、差异和待确认事项。

### 8. 文档头部结构

文档**不使用** hero header 区块（深色背景大标题）和"变更卡片总览"区块。页面直接从目录开始，保持简洁。

**禁止的头部元素：**

- `<header class="spec-header">` 深色背景大标题区
- `<div class="change-summary">` 变更点卡片快捷入口区

文档唯一的标识信息（ticket 号、需求名称、日期、commit）在目录区上方以简洁元信息行呈现，或直接体现在目录第一级条目标题中。

### 9. 目录结构规范

目录须体现需求的层级关系，遵循以下三级结构：

```
目录
├── A. 元信息与事实源              ← 固定前缀章节（字母编号）
├── B. 产品形态 × 角色矩阵
│
├── <需求名称>（一级，如 GT-12682-RBL优化）
│   ├── 1. <变更点名称>            ← 二级，数字编号
│   │   ├── 1.1 方案概述           ← 三级，小数点编号
│   │   ├── 1.2 截图式交互预览
│   │   └── 1.3 逐元素说明
│   ├── 2. <变更点名称>
│   │   └── ...
│   └── 3. <变更点名称>
│       └── ...
│
├── C. 差异标注                    ← 固定后缀章节（字母编号）
├── D. 待确认事项
└── E. 版本历史
```

**规则：**

- 固定章节（元信息、矩阵、差异、待确认、版本历史）使用字母编号（A/B/C/D/E）
- 需求名称作为目录**一级**条目，只显示需求名称本身，不加数字前缀
- 需求下的变更点为**二级**，使用数字编号（1/2/3）
- 变更点下的子章节为**三级**，使用小数点编号（1.1/1.2/1.3）
- 同一文档可收录多个需求（多个一级条目），各需求下的变更点编号独立
- 目录中每级条目均为可点击锚点链接，指向对应 `id`

对应 HTML 实现：

```html
<!-- 一级需求条目 -->
<li class="toc-l1"><a href="#gt-12682">GT-12682-RBL优化</a></li>
<ul class="toc-l2-group">
  <!-- 二级变更点 -->
  <li class="toc-change"><span class="toc-num">1</span><a href="#change-1">变更点名称</a></li>
  <ul class="toc-l2-group">
    <!-- 三级子章节 -->
    <li class="toc-l3"><a href="#c1-overview">1.1 方案概述</a></li>
    <li class="toc-l3"><a href="#c1-states">1.2 截图式交互预览</a></li>
  </ul>
</ul>
```

### 10. 方案内容规范

需求方案**只呈现最终选择或实现的方案**，不呈现候选方案对比、被否决的方向或中间讨论过程。

**禁止的内容：**

- 候选方案 A/B/C 的对比表
- "方案一 vs 方案二"的优缺点分析
- 被否决的设计方向描述
- 讨论过程中的过渡态方案

**应包含的内容：**

- 最终实现的方案描述（是什么、为什么这样做）
- 对应的浏览器截图（真实渲染状态）
- 实现涉及的元素、字段、i18n key、数据模型变更
- 差异标注（与历史版本的差异）
- 待确认事项（仍不确定的部分）

### 8. 差异与问题闭环

重生成时，先读取已有规格中的全部 `D-*` 和 `Q-*` 条目，逐项复核：

- `已解决`
- `部分解决`
- `未解决`
- `无法验证`

每项保留原编号和历史描述，并记录：

- 本次状态；
- 复核日期；
- 验证依据；
- 当前结论；
- 处理说明或解决版本。

不得批量写"均已处理"，不得静默删除已解决条目。其他原始 spec 只能帮助说明差异，不能单独证明问题已解决。

**增量版补充**：本次增量引入的新差异和待确认事项，编号须接续现有最大编号（`D-*` / `Q-*`），不得从 1 重新开始。

## 版本管理

每个模块使用 `version.json` 作为版本号权威来源。每次增量更新后：

```json
{
  "module": "dashboard-sidebar-nav",
  "current_version": 3,
  "history": [
    {
      "version": 2,
      "generated_at": "2026-07-27",
      "webapp_commit": "abcdef1",
      "comparison_spec_commit": "not-used",
      "summary": "初始全量规格生成"
    },
    {
      "version": 3,
      "generated_at": "2026-07-30",
      "webapp_commit": "c481bf6",
      "comparison_spec_commit": "not-used",
      "ticket": "GT-12649",
      "incremental": true,
      "summary": "GT-12649：移除侧边栏 VersionFooter，追加移除后默认态截图和差异标注"
    }
  ]
}
```

规则：

- 重生成时读取 `current_version` 后加 1；
- `generated_at` 使用真实日期；
- `webapp_commit` 记录当前仓库中该页面/组件相关代码的短 hash；
- 未读取对照 spec 时，`comparison_spec_commit` 写 `not-used`；
- 增量记录额外填写 `"incremental": true` 和 `"ticket"` 字段；
- `summary` 必须描述本次增量内容，不得写"增量更新"等无意义摘要；
- 已有历史若使用 `demo_commit` / `spec_commit`，保留旧记录，不伪造迁移；
- 技能不执行 `git commit` 或 `git push`。

## 工作流

### Phase 0：确认路径与范围（增量版必须完成）

1. **填写并确认功能路径表**（见文档顶部"功能路径"一节）：
   - 路由路径；
   - 组件路径；
   - html_spec 输出路径；
   - 变更类型（新增 / 变更 / 移除）；
   - 关联 ticket。
   缺少路由路径时停止，请用户补充后再继续。

2. 在 `webapp/src/` 中定位路由、组件、i18n、权限和数据请求代码。

3. **读取已有规格**：
   - 读取模块已有的 `index.html`、状态子文件、`version.json`；
   - 记录所有已有的 `D-*` 和 `Q-*` 编号，确定本次新增编号的起始值；
   - 标记本次增量将影响哪些已有章节或 `.interaction-preview` 节。

4. 如需使用其他原始 spec，明确标记"仅作差异对照，不作为需求依据"。

5. 读取当前目录适用的工程约束，例如 `AGENTS.md`、`DESIGN.md`。

### Phase 1：启动并验证真实 webapp

1. 确认 `http://localhost:3000` 可访问。
2. 未运行时执行：

```bash
cd webapp && npm run dev
```

3. 访问 Phase 0 确认的实际 locale 路由，例如 `http://localhost:3000/zh/dashboard`。
4. 完成登录、租户、产品形态和角色切换等前置条件。
5. **只截取本次增量涉及的状态**；未受影响的已有状态不重复截图。
6. 若本次变更导致已有状态发生变化，该状态必须重新截图。
7. 所有截图保存到模块的 `screenshots/` 目录，建议命名：

```text
<区域>-<状态>-<形态>-<角色>-<视口>.png
```

8. 对可能产生真实写入、删除、发送等副作用的操作：
   - 优��使用安全测试数据或只读路径；
   - 未得到授权时不要执行破坏性操作；
   - 无法安全验证时记录"无法验证"及原因。

### Phase 2：提取对应信息

对本次增量的每条截图式交互预览建立状态记录，至少提取：

1. 截图对应的路由、locale、主题、视口、形态、角色；
2. 触发前置条件与完整操作路径；
3. 页面区域、组件和元素清单；
4. 文案、图标、默认值、校验、禁用和可见性；
5. 操作后的页面变化、反馈、恢复路径；
6. 相关源码路径、i18n key、数据字段、API；
7. 用户目标、历史决定与 webapp 当前状态的差异；
8. 无法从浏览器或源码确认的事项。

同时标记已有规格中哪些内容因本次变更**失效**，需打删除线或添加 `<del>` 标记。

### Phase 3：生成增量 HTML

1. **不创建新的 `index.html`**（已有模块）；在已有文件对应章节末尾插入增量小节 `<section id="incremental-<ticket>-<简述>">`。
2. 若本次变更使某个已有 `.interaction-preview` 节失效，在该节顶部加 `<del>` 标记，并注明被哪个增量替代。
3. 新增截图放入 `screenshots/`，路径使用 `./screenshots/<文件名>`。
4. 若增量内容足够独立且主文件已较长，可新建 `state-<N>-<描述>.html` 并在主文件目录区域添加链接。
5. 更新 `version.json`（`current_version` 加 1，追加历史记录，`incremental: true`）。
6. 更新总索引 `webapp/doc/html-spec/index.html` 中该模块卡片的版本号和日期。

生成的 HTML 必须（与全量版一致）：

- 内嵌文档 CSS，或引用 `webapp/doc/html-spec/assets/` 中的本地共享 CSS；
- 不依赖 Tailwind 或其他业务 UI 框架；
- 不包含复制的 webapp 业务组件；
- 不包含任何 JavaScript、可操作表单控件或模拟业务交互；
- 截图使用相对路径；
- 离线打开时仍可完整阅读。

### Phase 4：验证规格文档（增量范围）

用浏览器打开修改后的文件，验证：

- 新增截图链接有效；
- 增量小节的触发路径和结果信息匹配；
- 已失效内容已打 `<del>` 标记；
- `D-*`、`Q-*` 编号接续，没有重号；
- 版本元信息与 `version.json` 一致；
- 总索引链接有效。

对增量修改的文件执行残留扫描：

```bash
rg -n '<(button|input|select|textarea|form|details|summary|script)\b|component-preview|on(click|change|input|submit|key|mouse)[a-z]*\s*=|addEventListener\s*\(|tailwindcss' webapp/doc/html-spec/<模块>/ -g '*.html'
```

残留扫描应无输出；不能用注释、隐藏节点或无效事件处理器保留旧交互。

## 关键约束

1. 必须通过浏览器验证真实 webapp，不能只读源码。
2. 不修改 webapp 现有实现；产物只写入 `webapp/doc/html-spec/`。
3. 必须生成截图式交互预览，但不生成可操作组件，不提取 `outerHTML`，不复制业务组件。
4. 每个重要状态必须有真实截图、触发路径和对应信息。
5. 无法观察或安全验证的内容必须明确标注，禁止臆造。
6. 用户当前描述优先，webapp 负责说明当前实现，其他 spec 只作差异对照。
7. 规格文件保持静态、无脚本、可离线阅读。
8. 更新旧规格时彻底清除交互控件、事件、mock 和专用样式残留。
9. 不自动提交或推送。
10. **增量约束：只描述本次新增或变更的功能片段，不重写未变更的已有内容；不删除已有内容（失效内容打删除线标注，不静默删除）；`D-*`/`Q-*` 编号接续不重置；`version.json` 每次必须递增。**
