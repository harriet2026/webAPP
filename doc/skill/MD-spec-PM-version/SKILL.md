## 文档命名与标识约定

文件名与文档内容名称**严格分离**：

| 字段 | 含义 | 示例 |
|---|---|---|
| **文件名**（`GT-<N>.md`）| 本文档的 ticket 号，文件系统唯一标识 | `GT-126811.md` |
| **需求名称** | 文档内容描述的需求/优化业务名 | `GT-12682-RBL优化` |

同一份文档可收录多个需求（二级条目）；文件名只对应文档本身 ticket，不等于任何需求名称。

## 与全量版的关系

与全量版 `md-spec-generator` 共享全部规格质量要求（截图、元素粒度、禁止事项等），**唯一区别是操作范围**：本技能以追加/局部替换方式只描述本次新增或变更的功能片段，不触碰未变更部分。

事实源为 `webapp/` 中正在运行的页面；增量内容按以下优先级选择载体：

1. 变更属于已有 ticket Markdown 或模块 `index.md` 的某个区域 → 在该区域内追加/替换对应交互预览小节，区域外内容不变。
2. 变更是独立新状态/新功能块且主文件已较长 → 新增 `state-<N>-<描述>.md` 并在主文件目录中添加链接。
3. 全新模块 → 创建新模块目录，走全量生成流程，但仅覆盖该新模块。

本技能只生成规格：不修改 `webapp/src/`、后端实现、测试用例或原始需求文档，不自动提交代码。

## 事实源与优先级

需求裁决顺序：

1. 用户当前描述；
2. 当前上下文中可获得的、时间更晚且明确的用户决定；
3. webapp 当前运行态与源码；
4. 其他原始 spec，仅作非权威差异对照。

当前实现事实源：

- 浏览器中实际运行的 webapp 是 UI、文案、布局、可见性、禁用态和交互结果的**第一事实源**；必须通过浏览器验证，不能只读源码。
- `webapp/src/` 是补充事实源（类型、状态管理、隐藏分支、i18n key、API）；与浏览器结果冲突时按浏览器记录并标注冲突。
- 用户目标与 webapp 当前状态冲突时，同时记录"目标要求"与"当前实现"，不得用当前实现覆盖目标。
- 历史对话不可获得时明确写"历史对话记录：当前上下文未提供"，不得虚构结论。
- 无法观察或安全验证的内容必须明确标注"无法验证"及原因，禁止臆造、伪造截图。

## PRD 结构（§0–§7，遵循 V8 通用规范）

核心产物是可评审、可开发、可验收的产品需求文档。**章节结构、各小节 Base/Overlay 标记、章节编写细则与可复制模板强制遵循 [references/prd-v8-spec.md](references/prd-v8-spec.md)**（以下简称 V8 规范）；编写或增量更新任何 §0–§7 内容前先阅读该文件。骨架如下：

```text
## 0. 形态与权限矩阵（MO — 全文档唯一事实源）
## 1. 功能概述
   1.1 功能背景与目标 [Base]
   1.2 功能点清单 [Base + Overlay]
   1.3 关键业务逻辑与数据流转 [Base]
   1.4 用户角色与权限边界 [Overlay，引用矩阵]
## 2. 界面布局设计
   2.1 页面信息架构 [Base + Overlay]
   2.2 原型/截图标注 [Base + 差异标注]
   2.3 响应式/自适应规则 [Base]
   2.4 视觉一致性要求 [Base]
## 3. 交互设计
   3.1 关键字段悬浮提示（Tooltip）[Base + Overlay]
   3.2 主流程交互 [Base + Overlay]
   3.3 状态变化规则（加载、空态、成功、失败、部分成功）[Base + Overlay]
   3.4 批量操作与单条操作逻辑 [Base + Overlay]
   3.5 弹窗/抽屉/页面跳转的触发条件 [Base + Overlay]
## 4. 异常场景
   4.1 输入非法或边界值处理 [Base]
   4.2 权限不足/操作冲突提示 [Overlay]
   4.3 后端服务超时/降级表现 [Base]
   4.4 并发操作与数据一致性兜底 [Base]
## 5. 关联功能模块
   5.1 上游依赖 [Base] / 5.2 下游影响 [Base] / 5.3 配置联动关系 [Base]
   5.4 接口与数据表关联说明 [Base + Overlay]
## 6. 技术实现要点
   6.1 核心算法或策略引擎对接 [Base]
   6.2 性能指标（QPS、响应时间、并发量）[Base]
   6.3 数据存储与迁移方案 [Base + Overlay]
   6.4 兼容性要求（信创环境、多租户隔离等）[Overlay]
## 7. 产品经理可验证的测试用例
   7.1 基线功能测试用例 [Base]
   7.2 形态差异测试用例（按矩阵逐行覆盖）[Overlay]
```

### 编写原则（强制，详见 V8 规范第四节）

- **矩阵唯一性**：除 §0 外任何章节涉及权限/入口/可见性，只引用矩阵并标注"详见 §0 矩阵"；
- **差异不重复**：Overlay 只写"与 Base 的不同"，不写"是什么"；§1.1 禁止出现形态限定词；
- **基准形态法**：UI 原型/截图标注以单租户为基准，多租户差异用 `[多租户差异：XXX]` 标签标注，不另画第二套；
- **术语一致性**：形态命名全文档统一（AI-单/传统-单/云-多/AI-多/传统-多），禁止同义替换；
- **禁止隐性假设**："默认/自动/通常/快速"等模糊描述必须量化为具体数值或规则；
- **测试对账**：§7.2 用例与矩阵逐行对应，每行至少一条（TC-O01 [AI-单-平台管理员] 编号规则）；
- **分支完备**：每条交互规则（IA）至少含主流程 + 空数据 + 失败分支，涉权限元素须有权限分支；"当/若…则…"句式，禁止"相应/等/自动处理"类模糊词；IA 编号连续、增量接续（细则见 V8 规范"交互规则（IA）书写规范"）；
- **引用闭环**：章节间引用必须双向标注。

元信息、交互预览、组件目录、差异标注、待确认事项、版本历史属于支撑内容，放入上述章节或固定附录，不得替代 §0–§7 结构。组件级规格可省略不适用章节，但仍须含事实源、状态截图、元素信息、交互结果、差异、待确认事项。

### §0 形态与权限矩阵模板

该矩阵是全文档关于入口、可见性、可编辑性、权限边界的唯一事实源；后续章节只能引用，不得重复定义或冲突。交付前按 V8 规范附录 C 快速核对。

> 图例：✅ 显示且可编辑 | 🔒 显示但只读 | ❌ 隐藏（含直达 URL 拦截返回 403/404） | — 无此角色 | ? 当前无法验证，必须列入待确认事项

| 产品形态 | 平台管理员 | 租户管理员 | 入口路径 | 备注 |
|---|---|---|---|---|
| AI版-单租户 | ✅ | — | 系统管理 > 模块名称 | 独立入口 |
| 传统版-单租户 | ✅ | — | 系统管理 > 模块名称 | 独立入口 |
| 云网关-多租户 | ❌ | ❌ | 租户中心 > 租户管理 > 模块名称 > 下钻 | 无独立入口 |
| AI版-多租户 | ❌ | ❌ | 租户中心 > 租户管理 > 模块名称 > 下钻 | 无独立入口 |
| 传统版-多租户 | ❌ | ❌ | 租户中心 > 租户管理 > 模块名称 > 下钻 | 无独立入口 |

**形态简称**：AI-单、传统-单、云-多、AI-多、传统-多。

- 新增形态或角色时先扩展矩阵，再触发全文档差异包审查。
- 每个组件/元素表必须含"形态/角色差异"列：无差异 `[Base]`；差异用 `[Overlay]`、`[单租户]`、`[多租户]` 或 `[多租户差异：XXX]`。
- 增量更新已有矩阵时只追加/修改本次变更涉及的行列。

## 规格内容规则

### 截图式交互预览

交互预览是只读截图预览，用标准 `![alt](路径)` 引用，图片下方以斜体段落作说明。每条关键交互用"触发前截图 → 操作说明 → 触发后截图/状态截图序列"表达；简单交互可只展示结果态并引用前置状态。

每个重要页面状态形成一组完整记录：

| 内容 | 要求 |
|---|---|
| 状态名称 | 默认态、打开态、选中态、错误态、空态等 |
| 触发路径 | 从哪个页面状态，经什么点击、输入、悬停或权限切换进入 |
| 截图 | 该状态真实渲染截图，不用手绘占位图 |
| 可见元素 | 文案、图标、位置、默认值、占位符、状态、禁用条件 |
| 交互结果 | 操作后页面变化、反馈、恢复方式 |
| 数据/API | 相关字段、请求、响应映射；无法确认标待确认 |
| 权限差异 | 对应形态/角色下的可见、只读、隐藏 |
| 验证依据 | 浏览器操作、DOM/可访问性信息、源码路径或用户决定 |

截图与文字信息互为补充、不可互相替代；审查者应能从一组"截图+表格+说明"独立理解该状态。

**呈现边界**：交互预览用三级/四级标题作容器，内部只允许：一个"状态信息"键值表、`![]()` 截图、斜体说明、元素/字段表。不使用轮播、折叠、热点点击等任何交互式呈现；多图按序平铺，每张前加粗标注"状态 N / <阶段>"。

**状态覆盖**：默认/加载/空/正常数据态；Hover/Focus/选中/禁用/只读；校验失败、提交失败、权限不足、后端异常；弹窗/抽屉打开态、表单联动态、确认态；排序/分页/筛选/批量前后；关键响应式断点；主题、locale、形态与角色差异。

**增量补充**：只覆盖本次新增/变更涉及的状态；无关现有状态不重复截图，但被本次变更影响的已有状态必须重新截图并替换旧引用。没有该状态或无法安全触发时注明"不适用"或"无法验证"。

### 逐元素详细度

不要只写"有一个搜索框"。按元素类型记录到可落地、可验收的程度：

- 通用元素：类型、文案、图标、位置、尺寸、默认值、占位符、禁用条件、交互结果、i18n key；
- 输入控件：数据类型、必填、长度、格式、边界值、校验时机、错误文案；
- 表格：列序、列名、字段、宽度、对齐、排序、格式、空值、溢出、固定列；
- 弹窗/抽屉：触发条件、尺寸、标题、字段、按钮、关闭方式、遮罩、焦点行为；
- 状态反馈：loading、toast、错误、空态、重试、成功后刷新或跳转；
- 权限：入口可见性、只读/禁用条件、无权访问结果。

### 方案内容

只呈现最终选择/实现的方案，不呈现候选对比或被否决方向。

**禁止**：候选方案 A/B/C 对比表、"方案一 vs 方案二"优缺点、被否决方向、讨论过程过渡态。
**应含**：最终方案描述（是什么、为什么）、真实浏览器截图、涉及的元素/字段/i18n key/数据模型变更、差异标注、待确认事项。

### 输出目录

```text
webapp/doc/md_spec-version/
├── GT-<N>【日期】<需求名>.md           # 按 ticket 存放的版本规格
├── assets/GT-<N>/                     # ticket 截图资产
└── <模块名>/
    ├── index.md                       # 模块主规格
    ├── version.json                   # 版本元数据
    ├── screenshots/
    │   ├── page-default.png
    │   ├── dialog-open.png
    │   └── validation-error.png
    └── state-<N>-<描述>.md            # 可选；状态多且主文件过长时使用
```

- 根目录只放总索引和共享资源，不平铺模块主文件或截图；
- 主文件与状态子文件统一用 `./screenshots/<文件名>` 相对路径引用截图；
- 截图命名建议 `<区域>-<状态>-<形态>-<角色>-<视口>.png`。

**增量规则**：新截图放入已有 `screenshots/` 且不冲突命名；不删除仍有效旧截图；不重命名已有 `state-*.md`（保链接稳定）；仅当增量内容确实独立才新建 state 文件。

### 文档头部

不使用 hero 大标题横幅和"变更卡片总览"式快捷入口区块；直接从元信息表格和目录开始。

```markdown
# <页面名称> 规格说明

| 字段 | 内容 |
|---|---|
| 规格版本 | v<N> |
| 生成日期 | <YYYY-MM-DD> |
| 页面路由 | `<zh/route>` |
| webapp 源码 | `<webapp/src/...>` |
| webapp commit | `<short-hash> |
| 需求依据 | 用户当前描述 + 可获得的历史决定 + webapp 当前运行态 |
| 历史对话 | <已使用/当前上下文未提供> |
| 对照 spec | <not-used 或路径；仅作差异对照> |
| 验证环境 | <URL、locale、主题、视口、形态、角色> |

> webapp 同时是原型与实际项目。本规格保留交互预览，但预览仅由真实状态截图和对应信息组成，不包含可操作控件、事件或脚本。
```

### 目录结构

```text
├── A. 元信息与事实源              ← 固定前缀章节（字母编号）
├── B. 产品形态 × 角色矩阵
├── <需求名称>                     ← 一级，无数字前缀，如 GT-12682-RBL优化
│   ├── 1. <变更点名称>            ← 二级，数字编号
│   │   ├── 1.1 方案概述           ← 三级，小数点编号
│   │   ├── 1.2 截图式交互预览
│   │   └── 1.3 逐元素说明
│   └── 2. <变更点名称> ...
├── C. 差异标注                    ← 固定后缀章节（字母编号）
├── D. 待确认事项
└── E. 版本历史
```

- 固定章节用字母编号（A/B/C/D/E）；同一文档可收多个需求，各需求下变更点编号独立；
- 目录为标准 Markdown 链接列表，指向标题锚点。

中文标题锚点规则因渲染器而异（通常小写化、空格转 `-`、保留中文、去标点）。生成后必须在目标渲染环境逐条点击目录链接验证跳转；不生效时允许在对应标题上方插入 `<a id="固定锚点名"></a>` 改用固定锚点，不得引入其他 HTML。

### 差异与待确认事项闭环（D-*/Q-*）

重生成/增量时先读取已有规格全部 `D-*`、`Q-*` 条目，逐项复核并标注：`已解决` / `部分解决` / `未解决` / `无法验证`。每项保留原编号和历史描述，记录：本次状态、复核日期、验证依据、当前结论、处理说明或解决版本。不得批量写"均已处理"，不得静默删除已解决条目；其他原始 spec 只能辅助说明差异，不能单独证明已解决。

**增量补充**：本次新增差异/待确认事项编号接续现有最大编号，不得从 1 重置。

## 版本管理（version.json 为权威来源）

每次增量更新后：`current_version` 加 1，追加历史记录；`summary` 必须描述本次增量内容（如"GT-12649：移除侧边栏 VersionFooter，追加移除后默认态截图和差异标注"），不得写"增量更新"等无意义摘要；同步更新中央索引 `webapp/doc/html-spec/index.html` 中该 ticket/模块条目的版本号、日期和 `/md-spec/version/...` 深链。

```json
{
  "module": "dashboard-sidebar-nav",
  "current_version": 3,
  "history": [
    { "version": 2, "generated_at": "2026-07-27", "webapp_commit": "abcdef1",
      "comparison_spec_commit": "not-used", "summary": "初始全量规格生成" },
    { "version": 3, "generated_at": "2026-07-30", "webapp_commit": "c481bf6",
      "comparison_spec_commit": "not-used", "ticket": "GT-12649", "incremental": true,
      "summary": "GT-12649：移除侧边栏 VersionFooter，追加移除后默认态截图和差异标注" }
  ]
}
```

规则：`generated_at` 用真实日期；`webapp_commit` 记当前相关代码短 hash；未读对照 spec 时 `comparison_spec_commit` 写 `not-used`；增量记录额外加 `"incremental": true` 和 `"ticket"`；旧记录若用 `demo_commit`/`spec_commit` 保留不伪造迁移；技能不执行 `git commit`/`git push`。

## 禁止事项（唯一权威清单）

Markdown 规格是只读文档，不是第二套 webapp：

- 不提取 `outerHTML`/JSX，不复制业务组件标签结构或 Tailwind class 名；
- 不嵌入组件 HTML/JSX 片段、伪代码、mock API、状态机或脚本；
- 不绑定模拟业务交互，不要求点击/输入/排序/分页/开关弹窗；
- 不引用 Tailwind CDN 或任何前端框架资源；
- 不使用 `<button>`、`<input>`、`<select>`、`<textarea>`、`<form>`、`<details>`、`<summary>`、`<script>` 等可交互/可执行标签，不保留 `onclick` 等事件绑定或 `addEventListener`；
- 正文不使用原生 HTML；唯一例外是必要时一个不可交互的 `<a id="锚点名"></a>` 供目录跳转；
- 更新旧规格时直接删除交互控件描述残留、伪代码、mock 数据和过时截图引用，不得用文字"已废弃"掩盖而保留原表格行；
- 不修改 webapp 业务实现；不自动提交或推送；
- **不得借"增量"名义跳过浏览器验证或减少状态覆盖。**

## 工作流

### Phase 0：确认路径与范围

1. 填写并确认功能路径表（见顶部）；缺路由路径即停止。
2. 在 `webapp/src/` 定位路由、组件、i18n、权限、数据请求代码。
3. 读取已有规格：`index.md`、状态子文件、`version.json`；记录已有 `D-*`/`Q-*` 最大编号确定本次起始值；标记本次增量影响的章节/预览小节。
4. 使用其他原始 spec 时明确标记"仅作差异对照，不作为需求依据"。
5. 读取工程约束（`AGENTS.md`、`DESIGN.md` 等）。

### Phase 1：启动并验证真实 webapp

1. 确认 `http://localhost:3000` 可访问；未运行则 `cd webapp && npm run dev`。
2. 访问 Phase 0 确认的 locale 路由，完成登录、租户、形态、角色等前置条件。
3. 只截取本次增量涉及的状态；被本次变更影响的已有状态必须重新截图。
4. 截图存入模块 `screenshots/`，按命名建议 `<区域>-<状态>-<形态>-<角色>-<视口>.png`。
5. 可能产生真实写入/删除/发送副作用的操作：优先安全测试数据或只读路径；未授权不执行破坏性操作；无法安全验证时记录"无法验证"及原因。

### Phase 2：提取对应信息

对每条截图式交互预览提取：路由/locale/主题/视口/形态/角色；触发前置条件与完整操作路径；区域、组件、元素清单；文案、图标、默认值、校验、禁用、可见性；操作后变化、反馈、恢复路径；源码路径、i18n key、数据字段、API；用户目标/历史决定与当前状态差异；无法确认事项。同时标记已有规格中因本次变更**失效**的内容（用 `~~删除线~~` 标注，见 Phase 3）。

交互规则前置：逐元素盘点可交互元素（元素 × 事件），为每条预分配交互规则编号 IA-N（接续文档已有最大编号，不重号）；逐条提取"当/若…则…"分支信息——操作触发的请求、返回值/状态值对应的页面表现（成功/空/失败/权限分支）、反馈与恢复方式。IA 书写细则见 V8 规范"交互规则（IA）书写规范"与附录 A.6。

### Phase 3：生成增量 Markdown

1. 已有 ticket/模块**不新建主规格文件**：在已有文件对应章节末尾插入增量小节：

   ```markdown
   ### 增量：<ticket> <简述>（<日期>）

   <本次变更的截图式交互预览、元素说明、差异、待确认事项>
   ```

2. 已有交互预览小节因本次变更失效时：标题加删除线（如 `### ~~<旧状态标题>~~（已被 <ticket> 替代）`）并注明替代 ticket，不静默删除。
3. 新截图放 `screenshots/`，引用 `./screenshots/<文件名>`。
4. 增量独立且主文件较长时新建 `state-<N>-<描述>.md` 并在主文件目录区域加链接。
5. 更新 `version.json`（见"版本管理"）与中央索引 `webapp/doc/html-spec/index.html`。

生成的 Markdown 必须：标准语法（标题、表格、图片、列表、删除线、加粗、斜体）；不依赖 CSS/Tailwind/业务 UI 框架；无 JS、无可操作表单控件、无复制组件标签；除允许锚点外无原生 HTML；截图相对路径；离线纯文本/Markdown 阅读器可完整阅读核心信息。

### Phase 4：验证规格文档（增量范围）

用浏览器或 Markdown 预览打开修改后文件，验证：新增截图链接有效；增量小节触发路径与结果信息匹配；失效内容已删除线标注；`D-*`/`Q-*` 编号接续无重号；版本元信息与 `version.json` 一致；总索引链接有效；目录锚点在目标渲染环境可正确跳转。

PRD 内容质量关：按 V8 规范第五节的交付检查清单逐项自检（结构完整性 / 基线完整性 / 差异完整性 / 引用一致性四组），本次增量触及的章节必须全部打勾；矩阵有变动时同时按附录 C 核对。

对增量文件执行残留扫描：

```bash
rg -n '<(button|input|select|textarea|form|details|summary|script)\b|on(click|change|input|submit|key|mouse)[a-z]*\s*=|addEventListener\s*\(|tailwindcss|class="' webapp/doc/md_spec-version/<模块>/ -g '*.md'
```

应无输出（允许的 `<a id="...">` 锚点除外）；不得用注释或无效标记保留旧交互痕迹。
