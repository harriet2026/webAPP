子页启用态上报门控：加载完成前不上报乐观默认值

路由：/zh/security/pipeline
组件：useModuleMaster.ts、UrlProtectionPage.tsx、IntentEnginePage.tsx、AttachmentSecurityPage.tsx
变更类型：缺陷修复 · 2026-08-02

1.1 方案概述

阶段3 内容层抽屉的左侧导航（PolicyPipelinePage 渲染）会为每个模块显示一个「圆点 + 摘要」：模块启用时圆点填充、摘要显示能力清单（如「信誉评估/沙箱分析/仿冒检测」）；未启用时圆点空心、摘要显示「未启用」。各模块子页负责把自己的真实启用态通过 onEnabledChange 回调上报给导航。

缺陷根因：URL检测与防护、意图引擎子页通过 useModuleMaster 读取启用态，附件安全检测子页通过其本地 draft 读取。两者在 GET /security/modules（或附件配置）返回之前，都把启用态乐观初始化为 true，并立即经 onEnabledChange 上报。于是点击一个「未启用」模块时，导航先按「已启用」渲染（圆点亮起、摘要显示能力清单），等真实状态加载完成后才翻转回「未启用」——形成用户观察到的「标签先变启用、再闪回未启用」。
最终实现方案：为 useModuleMaster 新增 loaded: boolean 状态，区分「加载中的乐观默认」与「已知的真实状态」；仅当 loaded === true 时子页才向导航上报。URL / 意图子页改用 if (moduleLoaded) onEnabledChange?.(moduleEnabled) 门控上报；附件子页复用其已有的 loading 状态，改为 if (!loading) onEnabledChange?.(draft.enabled)。加载期间子页不再推送乐观值，导航首帧改由父级兜底真值决定（见变更 2）。

父级导航兜底真值：抽屉打开即预取模块开关映射

路由：/zh/security/pipeline
组件：PolicyPipelinePage.tsx
变更类型：缺陷修复 · 2026-08-02

2.1 方案概述

变更 1 让子页在加载完成前不上报，但此时父级 PolicyPipelinePage 中对应模块的本地状态（urlModuleEnabled / attachmentEnabled / intentEngineEnabled）仍为 undefined。原逻辑在 undefined 时会退回 item.functional（恒为 true），因此首帧仍会把「未启用」模块画成启用——虽然不再「闪回」，但首帧依旧不正确。

最终实现方案：父级复用已有的 security-modules 查询（原仅在 stage5 启用），将其 enabled 门控从 stage5Active 放宽为 drawerOpen，使抽屉一打开就预取模块开关映射 securityModulesMap。在导航渲染时，stage3 三个模块（url / attachment / intentEngine）的圆点 dotOn 与摘要 summaryText 判断改为「本地状态 ?? 父级兜底真值」：本地状态存在（含用户未保存的草稿切换）时优先，否则用 securityModulesMap 中的真实持久化值，只有二者都缺失时才退回 item.functional。这样首帧即用真值渲染。 
// PolicyPipelinePage.tsx（导航渲染，简化示意）
const stage3Fallback = securityModulesMap?.[stage3ModuleKey[item.key]];
const urlEnabled = item.key === 'url' ? (urlModuleEnabled ?? stage3Fallback) : undefined;
// …attachment / intentEngine 同理
const dotOn = stage5Enabled !== undefined ? stage5Enabled
  : urlEnabled !== undefined ? urlEnabled
  : /* … */ item.functional;

3

意图引擎条件升级为「多意图 · 双检测模式」独立配置面板

路由：/zh/security/pipeline
组件：ConditionConfigPanel.tsx、serde.ts、expression.ts、catalogue.ts
变更类型：功能优化 · 2026-08-03

3.1 方案概述

「意图引擎」条件（catalogue key comprehensiveEngineResult / 字段 cac_tag）与阶段3 内容层的意图引擎模块同源。该模块的 detection_mode / threshold_segments 均挂在「单个意图」之下（见 types/intent-engine.ts 的 IntentSingleConfig），阶段3 的 IntentDirectionConfig 本身就是 5 个意图（钓鱼 / 涉政 / 垃圾 / 诈骗 / 订阅）各自独立配置。为与引擎 1:1 对齐，该条件从普通枚举单选升级为专属 intentEngine 面板。

最终实现方案：面板采用「可配置多个意图，每意图单条」的列表式结构——
  • 每行 = 一个意图 + 该意图的检测模式：分类优先 classification（命中该意图即匹配）或 分段阈值 threshold（命中该意图且置信度分数落入 [lo, hi] ⊆ [0,1] 区间）；
  • 底部「添加意图」下拉仅列出尚未添加的意图；每行可独立「移除」；同一意图去重（后写覆盖）；
  • 多个意图之间语义为 OR（命中任一配置的意图即匹配）；
  • 取值编码为「意图:模式[:lo,hi]」以 ; 连接，例如 phishing:threshold:0.60,0.90;spam:classification，复用现有 string value 模型 / serde 往返；单个 leaf.operator 固定为 within 伞值，分类 / 阈值细节下沉到 value 编码由面板与预览解析；
  • 旧的单意图值（如 phishing:classification）天然是「只有一条条目」的合法子集，向后兼容、无需迁移。

完整性校验（expression.ts）：至少配置 1 个意图，否则阻断性不完整；任一分段阈值条目端点缺失 → 阻断，端点齐全后再校验「大小顺序 / 超出 [0,1] 范围」提示。表达式预览把每个意图渲染为「意图」（分类优先）或「意图(lo~hi)」（分段阈值）。 

// serde.ts — 多意图列表编解码（复用单条 parse/encode）
//   phishing:threshold:0.60,0.90;spam:classification
parseIntentEngineList(value: string): IntentEngineValue[]   // 按 ';' 切分、去重、丢弃空条目
encodeIntentEngineList(entries): string                     // 以 ';' 连接，同意图去重
export const INTENT_ENGINE_OPERATOR = { classification: 'within', threshold: 'between' };

D-001 · 演示（mock）环境 URL 模块「加载设置失败」，无法在本环境复现「未启用」稳态

状态已知·环境限制
描述在当前演示环境点击「URL检测与防护」详情页会出现 加载设置失败 toast，其总开关无法持久化切换（保持已启用）。因此 4 个内容层模块在本环境均呈启用态，无法在浏览器中复现用户截图（S-1）中的「未启用」稳态来直接对比修复前后。

验证依据S-4 截图右下角 加载设置失败 toast；useModuleMaster 的 getSecurityModules().catch(() => {}) 静默失败分支

D-002 · 附件子页门控字段与 URL/意图子页不同（loading vs loaded），机制不同但效果一致

状态已确认·有意保留

解决版本GT-12723 · 2026-08-02
验证依据UrlProtectionPage.tsx / IntentEnginePage.tsx 使用 moduleLoaded；AttachmentSecurityPage.tsx 使用 !loading

D-003 · security-modules 查询门控由 stage5Active 放宽为 drawerOpen，取数时机提前

状态已确认·预期内
描述useQuery(['security-modules']) 原仅在 stage5 激活时取数，现放宽为抽屉打开（drawerOpen）即取数。这会让该请求在打开任意阶段抽屉时都触发一次（此前仅 stage5）。由于使用 React Query 缓存（同 queryKey），重复打开不会重复请求，额外开销可忽略。
解决版本GT-12723 · 2026-08-02

D-004 · 意图引擎「每意图单条」：同一意图不允许配置多个不同模式 / 多段区间

状态已确认·有意约束
描述多意图面板对同一意图去重（后写覆盖），即一个意图只能有一种检测模式与一段阈值区间，符合引擎 IntentSingleConfig「每意图单份配置」的语义。若未来需要「同一意图配多个阈值区间」（对应引擎 threshold_segments[] 多段），需扩展为「意图 → 多段区间」三级结构，属更大改动。
解决版本GT-12751 · 2026-08-03
验证依据serde.ts parseIntentEngineList 以 Map<intent,idx> 去重；单元测试「dedupes the same intent, keeping the last-written entry」

D-005 · 意图引擎 leaf.operator 固定为 within 伞值，分类 / 阈值细节下沉 value 编码

状态已确认·设计取舍
描述多意图混合模式后，单个 leaf.operator 无法同时表达「分类（within）/ 阈值（between）」两种；故将 operator 固定为 within 伞值（表示「命中所选意图集合之一」），真正的分类 / 阈值细节由 value 编码（意图:模式[:lo,hi]）承载，由面板与表达式预览解析。此举不破坏 leaf 的单 operator 模型，且兼容旧单意图值。
解决版本GT-12751 · 2026-08-03
验证依据ConditionConfigPanel.tsx commit() 恒传 operator: INTENT_ENGINE_OPERATOR.classification（=within）；serde.ts 注释与 codec
