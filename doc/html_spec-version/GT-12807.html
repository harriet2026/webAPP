1

事后处置时间线：事件来源白名单过滤（根本原因修复）

analysis-section.tsx · DISPOSAL_SOURCES

1.1 问题根因

原过滤逻辑为黑名单，仅排除 event_source === 'postfix'，导致 antispam · policy_decided、antispam · quarantine_pending 等投递流程/策略裁决事件穿透过滤，出现在事后处置时间线中，且因这些值不在映射表中，渲染原始英文。

1.2 修复方案

改为白名单：仅保留 admin_api 和 threat_retro_agent 两种来源的事件。

// 修复前（黑名单）
const disposalEvents = useMemo(
  () => events.filter((ev) => ev.event_source !== 'postfix'),
  [events],
);

// 修复后（白名单）
const DISPOSAL_SOURCES = new Set(['admin_api', 'threat_retro_agent']);
const disposalEvents = useMemo(
  () => events.filter((ev) => DISPOSAL_SOURCES.has(ev.event_source ?? '')),
  [events],
);

1.3 白名单来源说明

event_source触发方说明
admin_api管理员手动管理员在详情页或列表页手动发起的召回操作
threat_retro_agent威胁回溯智能体威胁回溯智能体依据配置策略（recall / notify）自动发起的操作
业务边界：事后处置时间线只展示"事后处置动作"，不展示邮件投递流水（postfix）或策略裁决事件（antispam）。
2

操作类型：event_source + event_type 复合键 i18n

analysis-section.tsx · OPERATION_TYPE_KEY_MAP · getOperationTypeLabel

2.1 问题

展开事件详情后，「操作类型」值渲染 ev.event_type 原始英文。且 admin_api:recall 与 threat_retro_agent:recall 的 event_type 同为 recall，单字段翻译无法区分。

2.2 操作类型枚举（完整）

event_sourceevent_type中文（zh）英文（en）触发场景
admin_apirecall管理员召回Admin Recall管理员在详情页或列表页手动发起召回
threat_retro_agentrecall威胁回溯智能体发起召回Threat Retro Agent Recall威胁回溯智能体策略配置为 recall 时自动触发
threat_retro_agentnotify威胁回溯智能体发起通知Threat Retro Agent Notify威胁回溯智能体策略配置为 notify 时自动触发

2.3 实现方案

// analysis-section.tsx
const OPERATION_TYPE_KEY_MAP: Record<string, string> = {
  'admin_api:recall':          'adminApiRecall',
  'threat_retro_agent:recall': 'threatRetroAgentRecall',
  'threat_retro_agent:notify': 'threatRetroAgentNotify',
};

function getOperationTypeLabel(
  source: string | undefined,
  type: string | undefined,
  t: TFn,
): string {
  if (!type) return '—';
  const key = `${source ?? ''}:${type}`;
  const subKey = OPERATION_TYPE_KEY_MAP[key];
  if (!subKey) return type; // fallback 到原始值
  return t(`operationType.${subKey}`);
}

i18n 命名空间：emailDisposal.detail.analysis.operationType.{adminApiRecall | threatRetroAgentRecall | threatRetroAgentNotify}

1. "阻断"重命名为"拒收"（DMARC处置策略）

1.1 方案概述

DMARC 处置策略下拉中，reject 动作的显示文案由「阻断」修改为「拒收」，与内容规则、反病毒引擎语义对齐，统一使用「拒收」表达 SMTP 5xx 拒绝响应，消除模块间文案差异。SPF / DKIM / PTR 共享同一 i18n key，四个协议 Tab 文案同步更新。

字段修改前修改后
i18n keyauthSpoofing.protocolActionShort.rejectkey 不变
zh 文案阻断拒收
描述文案（protocolActionDesc.reject）向发信方返回 SMTP 5xx 拒绝响应（不变）
影响协议SPF / DKIM / DMARC / PTR 共享同一 key，四个协议 Tab 同步更新
修改文件messages/zh.json — authSpoofing.protocolActionShort.reject

1.2 逐元素变更说明

元素类型变更前变更后i18n key源码路径

2. DMARC处置策略新增"进行下一步"选项

2.1 方案概述

修改前 DMARC_ACTIONS 为 4 项（不含 accept），SPF / DKIM / PTR 的 PROTOCOL_ACTIONS 含全部 5 项。本次将 DMARC_ACTIONS 扩充至 5 项，使 DMARC 支持「进行下一步」处置策略；accept 语义为当邮件命中该 DMARC 条件行时，直接传递给流水线下一节点，不做阻断 / 隔离 / 标记。

DMARC_ACTIONS 枚举 ['reject', 'discard', 'quarantine', 'audit']（4 项） ['reject', 'discard', 'quarantine', 'audit', 'accept']（5 项）
新增选项短名 — 进行下一步（authSpoofing.protocolActionShort.accept，key 已存在）
新增选项描述 — 不做处理，传递给下一个协议检查（authSpoofing.protocolActionDesc.accept，key 已存在）
i18n 变更 无需新增 key，相关 key 已存在于 messages/zh.json
