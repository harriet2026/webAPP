# Webapp 跨页面国际化与文本完整性 UI 规格

- 日期：2026-07-28
- 状态：v1，跨页面多语言与字符完整性基线
- 文档类型：跨页面 UI 国际化规范
- 适用范围：`webapp/` 管理控制台、登录页和用户可见门户页
- 上位设计语言：[`DESIGN.md`](../../../DESIGN.md)
- 语言事实源：[`src/i18n/routing.ts`](../../src/i18n/routing.ts)
- 配套布局规范：[Webapp 页面大布局 UI 规格](./2026-07-25-demo-page-layout-ui-spec.md)

## 1. 目的

本规格统一 webapp 的多语言覆盖、字符编码和文本验收要求，避免以下问题：

- 页面只翻译标题，按钮、说明、错误提示或无障碍名称仍混入其它语言；
- 新增 i18n key 只写入部分语言，运行时显示 raw key 或错误 fallback；
- 长文案在英语、泰语或俄语下溢出、遮挡操作区或被无意义截断；
- 翻译源、静态资源、接口解码或字符串截断损坏 Unicode，最终显示
  `U+FFFD` 替换字符；
- 通过前端删除乱码字符掩盖源数据或编码链路缺陷。

本规格中的“必须”是发布门禁，不是建议项。历史原型或 HTML 规格可以把乱码
作为缺陷证据记录，但 webapp 产品页面不得继承该乱码。

## 2. 支持语言

webapp 当前完整支持以下四种 locale：

| 语言 | locale | 路由前缀 | 要求 |
|---|---|---|---|
| 简体中文 | `zh` | `/zh/` | 完整 |
| English | `en` | `/en/` | 完整 |
| ไทย | `th` | `/th/` | 完整 |
| Русский | `ru` | `/ru/` | 完整 |

硬规则：

- 四种语言是同一发布单元，不允许把其中任一种作为长期占位或“后续补齐”；
- 新增、重命名或删除 i18n key 时，必须在
  `messages/{zh,en,th,ru}.json` 同一变更中同步完成；
- 四份消息文件的 key 路径和叶子值类型必须一致，叶子文案不得为空；
- 不允许依赖逐 key 跨语言 fallback。缺失 key、raw key、namespace key
  或错误占位符出现在 UI 中均视为缺陷；
- locale 切换后应保留当前业务路由、query 和可安全保留的页面上下文，
  不得无故跳回首页；
- 根节点 `html[lang]` 必须与当前 locale 一致。当前四种语言均使用
  `dir="ltr"`；未来增加 RTL 语言时须单独补充布局规格。

## 3. 用户可见文案

所有由产品控制的用户可见文本都必须来自翻译层，不得在组件中硬编码某一种
语言。范围至少包括：

- 页面标题、副标题、导航、Tab、按钮、链接和菜单项；
- 表单 Label、placeholder、helper、校验提示和字符计数说明；
- Tooltip、Popover、Dialog、Drawer、Toast 和确认提示；
- 加载、空状态、无权限、离线、错误、成功和部分失败状态；
- 表格列名、筛选项、分页、图例、图表标签、枚举值和状态 Badge；
- `title`、`aria-label`、`aria-description`、图片替代文本和其它无障碍名称；
- 导出入口、打印页以及由前端生成的用户可见文件名。

实现规则：

- i18n key 表达稳定语义，不把某一语言的完整句子直接作为 key；
- 带变量、数量或时间的句子使用翻译参数和 locale-aware formatter，
  不用字符串拼接固定词序；
- 日期、时间、数字、百分比和复数规则跟随当前 locale；业务原始值、邮箱、
  域名、ID 和协议字段不得被翻译；
- 后端稳定错误码由前端映射为本地化文案。不得把后端英文 `message`
  直接当作四语 UI；
- 同一个 UI surface 必须只使用当前语言，不得出现“标题已翻译、说明仍为
  英文”等混合语言状态；
- 翻译必须表达相同业务语义，不得为了适配布局删除限制条件、风险说明或动作
  后果。

## 4. 多语言布局

布局必须容纳真实翻译长度，不能只以中文短文案作为尺寸基线。

- 标题、副标题、状态说明和表单帮助文本默认允许自然换行；
- 按钮应优先通过内边距和内容宽度自然增长；不得用固定像素宽度裁掉译文；
- 标题栏空间不足时按页面布局规范换行，右侧操作不得被覆盖或挤出视口；
- 表格列名可以换行或按列规范截断，但完整内容必须可通过 Tooltip 或详情读取；
- Tab、分段控件和菜单在四语下不得互相覆盖；空间不足时使用规范化的滚动、
  折行或收起方案；
- Tooltip、Dialog 和 Drawer 不得因长译文超出可视边界；
- 省略号只能用于可恢复完整内容的次要文本，错误、风险、权限和操作后果不得
  被不可恢复地截断；
- 字体 fallback 必须覆盖中文、拉丁、西里尔和泰文字符，缺字方框同样视为
  文本完整性缺陷。

四语切换只能改变文案、locale 格式和必要的文本流，不得改变页面语义结构、
组件顺序、操作权限或业务结果。

## 5. Unicode 与 U+FFFD 零容忍

`U+FFFD` 是 Unicode replacement character，通常表示上游字节无法按预期
编码解码。它不是可接受的产品文案，也不是正常的 fallback。

### 5.1 禁止范围

以下位置不得包含字面或转义形式的 `U+FFFD`：

- `messages/{zh,en,th,ru}.json`；
- webapp 产品源码、静态资源和产品自有模板中的用户可见文案；
- 浏览器渲染出的产品导航、页面主体、弹层、Toast、Tooltip 和无障碍名称；
- 前端生成的打印内容、导出标题和文件名；
- 经 API 返回并由 webapp 展示的动态文本。

技术文档、自动化测试和检测器可以使用字符串 `U+FFFD` 描述或检测该问题；
历史原型证据也可以保留原始缺陷，但不得被复制到产品消息文件。

### 5.2 发现后的处理

- 翻译源损坏时，必须根据产品确认文案修复源消息文件，并复查四语对应 key；
- 静态文件编码错误时，必须修正文件编码或生成链路，统一重新生成产物；
- API 数据含 `U+FFFD` 时，应把它视为数据完整性错误并追溯产生位置；
- 在无法立即恢复原文的动态数据场景，UI 使用本地化的“内容无法正确解码”
  状态并保留可追踪错误标识，不直接显示损坏文本；
- 不得使用 `.replace()`、正则删除、空字符串替换或 CSS 隐藏 `U+FFFD`。
  这类处理会造成静默数据丢失，并掩盖真正的编码故障；
- 日志可以记录字段名、来源、request ID 和错误位置，但不得为了排障新增敏感
  正文泄露。

## 6. 编码与字符串处理

- TypeScript、JSON、HTML、CSS、SVG 和产品模板统一保存为 UTF-8；
- HTML 必须声明 UTF-8，服务端响应的 `Content-Type` 必须与实际编码一致；
- JSON 请求和响应按 UTF-8 处理，不得在调用链中以系统默认编码二次转换；
- 不得按 UTF-8 字节下标截断字符串；
- JS 的长度限制、摘要和省略逻辑不得切断 surrogate pair、组合附加符或 emoji
  序列；面向用户的截断优先使用 `Intl.Segmenter` 或等价的 grapheme-aware
  实现；
- 导入、复制粘贴、CSV 和文件名链路必须用包含中文、泰文、西里尔文字、
  组合字符和 emoji 的样例做往返验证；
- 字符解码失败必须显式失败或进入可观测的错误状态，禁止用 replacement
  character 静默继续。

## 7. 测试与验收

### 7.1 静态门禁

每次修改用户可见文案时至少验证：

1. 四份消息 JSON 均可解析；
2. 四语 key 树和叶子类型一致，新增 key 在四语中都有非空译文；
3. 产品消息、源码和静态资源中不存在字面 `U+FFFD`，也不存在 JSON/JS
   转义形式的 `\uFFFD`；
4. 新增用户可见文本已接入翻译层，没有单语字符串或 raw key 泄漏；
5. formatter 的参数名在四语中一致。

可使用以下命令做基础扫描；文档和测试中的检测样例不属于产品文案扫描范围：

```bash
cd webapp
rg -n $'\uFFFD' messages src public
rg -ni -F '\uFFFD' messages src public
```

扫描通过只是必要条件。源文件没有 replacement character，不代表接口运行态
或浏览器 DOM 一定没有。

### 7.2 浏览器矩阵

页面级验收必须覆盖 `zh / en / th / ru`，且不能只检查初始页面标题：

| 场景 | 必测项 |
|---|---|
| 页面初始态 | 标题、导航、筛选、表格、图表和状态文案 |
| 空/加载/错误态 | 无 raw key、无单语 fallback、无 `U+FFFD` |
| 深层交互 | Dialog、Drawer、Popover、Tooltip、Toast、二次确认 |
| 表单 | Label、placeholder、校验、禁用原因和提交结果 |
| 长文案 | 无遮挡、重叠、视口溢出或不可恢复截断 |
| 无障碍树 | accessible name/description 与当前 locale 一致 |
| 动态数据 | Unicode 完整；损坏输入进入明确的本地化错误状态 |

浏览器断言至少包含：

- 主要内容区和当前打开弹层的 `innerText` 不包含 `U+FFFD`；
- 可访问名称不包含 `U+FFFD`、raw key 或其它语言的硬编码文案；
- `html[lang]` 与 URL locale 一致；
- 关键容器在四语切换前后不发生遮挡或非预期横向滚动；
- 对错误态、空态和至少一个深层交互态进行检查，而不只是 happy path。

### 7.3 修复回归

任何 `U+FFFD` 缺陷修复必须增加两层回归：

1. 对损坏来源的静态或单元测试，保证同一 key、模板或解码函数不再产生
   replacement character；
2. 对受影响页面的浏览器测试，保证实际渲染文本及相关弹层不包含
   `U+FFFD`。

## 8. 完成定义（DoD）

新增或整改页面只有同时满足以下条件才算完成：

- [ ] `zh / en / th / ru` 四语文案在同一变更中交付；
- [ ] 产品控制的可见文本和无障碍名称均来自翻译层；
- [ ] 四语 key、参数和叶子类型一致，无空译文；
- [ ] 页面、弹层、状态和错误提示无 raw key、单语 fallback 或混合语言；
- [ ] 消息源、产品源码、静态资源和运行态 UI 均无 `U+FFFD`；
- [ ] 未用删除或替换字符的方式掩盖编码错误；
- [ ] 四语长文案不遮挡、不溢出，核心语义不被截断；
- [ ] 日期、数字、复数和错误码映射遵循当前 locale；
- [ ] 静态门禁、单元测试和四语浏览器矩阵通过。
