# Browser tests

This README indexes the Playwright browser test suites in this directory.
Find the relevant suite below for its coverage, prerequisites, configuration,
and run instructions.

## Available suites

| Suite | Coverage | Guide |
| --- | --- | --- |
| Assessment reports | Phish/Spoof report panels; legacy investigation and email-log pages | [Assessment report tests](#assessment-report-tests) |

## Assessment report tests

The assessment suite checks report states, factors, expandable source text, and
the existing Phish JSON download. It covers the phishing detection (Phish) and
impersonation detection (Spoof) detail panels, and also retains rendering checks
for two legacy pages.

### Page status and test scope

`/[locale]/investigations` and `/[locale]/logs/email` are **dead pages in the
current product flow**. The tests can open them directly by URL, but they are
not active product entrypoints. Passing those tests only demonstrates legacy
page rendering; it does not validate a current user workflow.

| Surface | Frontend route | How to interpret its results |
| --- | --- | --- |
| `drawer` | `/[locale]/agent-center/overview?agent=phishing` or `?agent=spoofing` | Agent detail-panel coverage; Spoof requires the preview flag described below |
| `general` | `/[locale]/investigations` | Legacy dead-page rendering only |
| `mail` | `/[locale]/logs/email` | Legacy dead-page rendering only |

`[locale]` is a language such as `en` or `zh`. The actual investigations route
uses the plural `investigations`. This page status does not remove the backend
investigation or mail-log APIs, which the tests still use to read task data.

The fixture suite includes the legacy-page checks. For live checks of current
agent detail panels, explicitly set `surfaces: ["drawer"]` in each sample.
The live runner currently defaults to all three surfaces when that field is
omitted, so omitting it also runs the dead-page checks.

### Choose a test mode

| Mode | Test and configuration | Data source | Required environment |
| --- | --- | --- | --- |
| Frontend fixtures | `assessment-details.spec.cjs`, `playwright.config.cjs` | Committed synthetic API responses | A separate frontend server; no backend or login credentials |
| Existing product records | `assessment-live.spec.cjs`, `assessment-live.config.cjs` | Actual product APIs | A deployed frontend and backend, login credentials, and existing investigation/mail records |

Both modes are started explicitly with the commands below. They are not included
in `npm test` (the Vitest unit suite) or the current CI entrypoints.

Each configuration runs only its corresponding test file and omits the QC
`globalSetup` and `globalTeardown` hooks. Those hooks normally prepare or reset
shared test tenants, accounts, routes, and login settings. Omitting them lets
these tests run without that environment preparation.

### Install dependencies

Use the repository's Node.js environment. Run from `webapp`:

```bash
npm ci
npm install --no-save --package-lock=false @playwright/test@1.58.2
./node_modules/.bin/playwright install chromium
```

`@playwright/test` is currently an additional dependency, not declared in the
webapp package manifest. The second command installs it without changing the
manifest or lockfile. Chromium also needs its operating-system libraries. The
configurations use Playwright's installed browser by default; the environment
variables below allow an existing compatible Chromium executable instead.

Commands in this assessment guide run from `webapp`. Replace the address and path
placeholders with values for your environment.

### Run with frontend fixtures

The fixture suite reads
[`internal/api/testdata/assessment-responses`](../../../internal/api/testdata/assessment-responses/README.md).
These JSON files were generated by actual API handlers using synthetic test data.
The suite supplies them as browser API responses and supplies synthetic login,
navigation, list, and overview data. It does not log in to a backend.

Coverage includes available, empty, pending, failed, legacy, and unsupported
reports; multiple report subjects; source expansion; and JSON downloads.
Additional UI scenarios check strong legitimate support and HTTP 503 errors.
These scenarios do not modify the committed fixtures.

Start a separate frontend server in another terminal. Choose an available
`10.126.126.x` address from `hostname -I` and an unused port:

```bash
OSGATEWAY_PRODUCT_FORM_SWITCHER=true API_BACKEND_URL=http://127.0.0.1:9 \
  npm run dev -- --hostname <10.126.126.x> --port 33000
```

`OSGATEWAY_PRODUCT_FORM_SWITCHER=true` exposes the Spoof panel needed by the
suite. The unused API proxy address keeps this frontend disconnected from a
backend. The test intercepts expected API requests, disables built-in demo data,
and fails on unexpected API calls, writes, or external traffic. Service workers
and backend WebSockets are blocked.

Run the tests against that frontend:

```bash
ASSESSMENT_FIXTURE_WEB_URL=http://<10.126.126.x>:33000 \
ASSESSMENT_FIXTURE_OUTPUT_DIR=/tmp/osgateway-assessment-browser-unique-run \
  ./node_modules/.bin/playwright test --config tests/browser/playwright.config.cjs
```

| Variable | Meaning |
| --- | --- |
| `ASSESSMENT_FIXTURE_WEB_URL` | Required frontend origin, including scheme and port |
| `ASSESSMENT_FIXTURE_OUTPUT_DIR` | Output directory; defaults to `/tmp/osgateway-assessment-browser`. Set a fresh directory for each run |
| `ASSESSMENT_FIXTURE_CHROMIUM_EXECUTABLE` | Optional absolute path to a compatible Chromium executable |

A cold Next.js development server may spend longer compiling a route than the
45-second test timeout. Open `/en/agent-center/overview`, `/en/investigations`,
and `/en/logs/email` before running the suite. If compilation caused a timeout,
rerun after compilation finishes.

### Run against existing product records

The live suite logs in through `/api/v1/auth/login`, reads actual product APIs,
and compares their results with the rendered reports. It uses no response
fixtures. It checks source contents, retained byte counts and hashes, report
identity, and the Phish JSON download.

Prepare the following before starting:

1. A deployed frontend connected to its intended backend. Use the built Next.js
   image when checking behavior of a deployed build.
2. A test account that can log in directly with username/password and access the
   selected tenant and pages. The runner does not complete a second authentication
   step or create accounts.
3. Existing investigation tasks and their associated email-log records. The
   runner does not send mail, start model tasks, or create test data. Drawer
   searches use the Last 7 days filter, so choose records in that period and a
   subject that identifies the intended record.
4. The `OSGATEWAY_PRODUCT_FORM_SWITCHER=true` frontend flag when testing the
   Spoof panel. This flag also bypasses the normal frontend login gate. The suite
   still performs real API login before rendering and verifies the HttpOnly
   session cookie and authenticated bootstrap response.

Store a login JSON file with `username` and `password`, and a separate sample
manifest, in private Git-ignored files. The manifest identifies existing records
and the expected report state; it does not provision them.

Example manifest structure:

```json
{
  "tenant_id": 1,
  "phase": "published",
  "report_schema_version": 2,
  "locales": ["zh", "en"],
  "samples": [{
    "name": "phishing-report",
    "kind": "phish",
    "subject": "subject of the existing test email",
    "detail_id": "actual-detection-detail-id",
    "task_id": "actual-task-id",
    "mail_log_id": 1,
    "message_uuid": "actual-message-uuid",
    "status": "available",
    "plan_revision": "phish.baseline@6",
    "snapshot_sha256": "actual-published-snapshot-digest",
    "surfaces": ["drawer"]
  }]
}
```

Replace the example values with identities and expectations recorded for your
sample. In particular, `plan_revision` must match that task's actual producing
plan; the example is not a requirement to upgrade historical records.

| Manifest field | Meaning |
| --- | --- |
| `tenant_id` | Required positive tenant ID shared by the samples |
| `phase` | Optional label included in test names; it does not change product state |
| `locales` | Languages to check; defaults to `["en"]`. The UI supports `zh`, `en`, `ru`, and `th` |
| `samples` | Required nonempty list of existing records to check |
| `name`, `kind`, `subject` | Test label, agent kind (`phish` or `spoof`), and the email subject used by drawer searches |
| `task_id` | ID used by `/api/v1/investigations/{task_id}` |
| `mail_log_id`, `message_uuid` | Associated email-log record ID and expected message identity; required for every surface |
| `detail_id` | ID accepted by the agent's detection-detail endpoint; required for `drawer` |
| `status`, `reason` | Expected `assessment_report_status` and optional `assessment_report_reason` |
| `plan_revision` | Expected `assessment_report.origin.plan_revision`; required when `status` is `available` |
| `report_schema_version` | Expected schema, either 1 or 2; a sample value overrides the top-level value, then defaults to 2 |
| `snapshot_sha256` | Optional expected report snapshot digest; preserve the original value when checking the same record after a restart |
| `surfaces` | Use `["drawer"]` for agent detail-panel checks. `general` and `mail` target the dead pages listed above. Omitting this field runs all three |

For a manual Phish task without an agent detection-detail record, this runner
only supports the legacy `general` and `mail` surfaces; it provides no current
product-page coverage for that task. Use those surfaces only when intentionally
checking the legacy pages.

A result without a report can use `status: "not_recorded"` and its expected
`reason`. For available reports, keep the expected schema
and plan consistent with the retained record; the runner does not infer the
expected version from the response it is checking.

Run against the deployed frontend:

```bash
ASSESSMENT_LIVE_WEB_URL=https://<10.126.126.x>:35443 \
ASSESSMENT_LIVE_LOGIN_FILE=/absolute/private/ui-login.json \
ASSESSMENT_LIVE_MANIFEST=/absolute/private/manifest.json \
ASSESSMENT_LIVE_OUTPUT_DIR=/absolute/private/browser-published \
  ./node_modules/.bin/playwright test --config tests/browser/assessment-live.config.cjs
```

| Variable | Meaning |
| --- | --- |
| `ASSESSMENT_LIVE_WEB_URL` | Required frontend origin, including scheme and port |
| `ASSESSMENT_LIVE_LOGIN_FILE` | Required path to the login JSON file |
| `ASSESSMENT_LIVE_MANIFEST` | Required path to the sample manifest |
| `ASSESSMENT_LIVE_OUTPUT_DIR` | Required output directory; use a fresh directory for each run |
| `ASSESSMENT_LIVE_CHROMIUM_EXECUTABLE` | Optional absolute path to a compatible Chromium executable |

The live runner allows normal login and reads from the selected origin. Other
writes, external requests, and WebSockets are blocked and audited. It does not
restart services or erase data. Traces and video are disabled; the configuration
accepts self-signed HTTPS certificates for the test environment.

### Read the results

Both modes write `results.json` and an `artifacts/` directory below their selected
output directory. Attachments include screenshots and per-test network audits.
The live suite also retains actual API results and Phish JSON downloads, which
may contain mail content; keep that output with the private test data.

A fixture run verifies frontend behavior for the supplied synthetic responses.
A live run verifies the selected existing records, report contents, and their UI
representation. Neither run measures model accuracy or proves SMTP delivery.
Report `drawer` results separately from `general` and `mail`: passing dead-page
checks must not be counted as current product-page coverage.
When the Spoof preview flag is used, the result covers that preview panel with
real API authentication, rather than default production panel visibility or the
normal frontend login gate.
